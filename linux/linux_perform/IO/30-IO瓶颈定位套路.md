# 30 | 如何迅速分析出系统 I/O 的瓶颈？

原文：[time.geekbang.org/column/article/79001](https://time.geekbang.org/column/article/79001)

I/O 篇总复习。先分清**文件系统**和**磁盘**两套指标，不要跨场景横比（随机 vs 顺序、有无 RAID、本地 vs 网络）。

## 文件系统指标

| 类 | 看什么 |
|----|--------|
| 空间 | `df -h`；这是 FS 展示量，含元数据，RAID10 只能看到约一半容量 |
| inode | `df -i`，小文件会先把 inode 用光 |
| 缓存 | 页缓存、dentry、inode、具体 FS 的 slab；`/proc/meminfo`、`slabtop` |
| 文件 I/O | IOPS / 延迟 / 吞吐；Linux **没有**现成命令直接给，靠系统调用、eBPF 或基准测试间接看 |

## 磁盘指标

使用率（文中写超过 60% 就要警惕）、IOPS、吞吐、响应时间，加上 Buffer。IOPS 是合并后发给盘的请求数，单次大小不固定。

随机/顺序：`strace` 看偏移是否连续，或 `blktrace`。

## 先跑这三个

```bash
iostat -d -x 1
vmstat 1
pidstat -d 1
```

然后：

```text
iostat 确认盘有瓶颈
  → pidstat 找进程
      → 用户进程：strace -f + lsof（或 filetop / opensnoop）
         → 结合应用原理（日志、临时文件、SQL、AOF…）
      → 内核线程 / Swap 升：转去内存分析
```

短时 `%util` 100% 报警后现场没了：要靠监控留历史（专栏后文 53、54），`sar -d` 看不到进程。

## 案例对应工具（过一遍能回忆）

| 场景 | 工具链 |
|------|--------|
| 狂打日志 | top → iostat → pidstat → strace + lsof |
| 子线程写临时文件 | 上面 + `strace -f` / filetop + opensnoop |
| MySQL 全表扫 | 定位到 `.MYD` → `EXPLAIN` / 慢查询 |
| Redis AOF | lsof 看到 `.aof` + `fdatasync` → 改 `appendfsync` |
