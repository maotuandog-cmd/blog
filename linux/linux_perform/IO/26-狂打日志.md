# 26 | 如何找出狂打日志的「内鬼」？

原文：[time.geekbang.org/column/article/77885](https://time.geekbang.org/column/article/77885)

生产只开警告/错误日志。排查时临时开 debug，事后忘了调回去，就会把盘打满。当黑盒：从资源指标走进应用，别先翻源码。

## 套路

```text
top          → iowait 高、某进程略占 CPU
iostat -d -x → %util≈100%、await 秒级、队列很长
pidstat -d   → 谁在写（kB_wr/s）
strace -p    → write(fd, ...) 多大
lsof -p      → fd 对应哪个路径
调日志级别 / 改配置重启
```

`strace` 可能要 `echo 0 > /proc/sys/kernel/yama/ptrace_scope`。

## 案例现象

- CPU0：sys 6%、**wa 90%+**；python 只占约 6% CPU，方向是 I/O 不是算力
- `buff/cache` 很大；`iostat` 写 32MB/s、`w_await` 7s、`aqu-sz` 1100、`%util` 99%
- `pidstat` 里 python 写 **45MB/s+**（比 iostat 的 32MB 大：先入页缓存，盘上还在消化）
- `jbd2`、`kworker` 的 iodelay 更大：它们是文件系统/内核干活的，根子仍是大量写
- `strace`：`write(3, ..., 300MB)`；`lsof`：fd 3w → `/tmp/logtest.txt`

「log.1 / log.2」是**文件名轮转**，内容并不回滚。

## 处理

源码默认 INFO，每次打 300MB。发 `SIGUSR2` 把级别升到 WARNING 后，`logger.info` 不再落盘，iowait 和 `%util` 回 0。没有动态接口就改配置重启。

课后：这些 cache 主要是**写文件的 Page Cache（Cache）**，不是裸盘 Buffer。`vmstat` 的 cache 列、`pcstat` 对那个日志文件都能对上。
