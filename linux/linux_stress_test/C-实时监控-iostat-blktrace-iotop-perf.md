================================================================
C.1 iostat — 平均延迟 (sysstat 工具集)
================================================================

原文: md:692, md:1291
```
iostat -xz 1 5
```
也是原文 9.3 监控告警的核心命令

----------------------------------------------------------------
C.1.1 安装
----------------------------------------------------------------
```
# Debian/Ubuntu
apt-get install sysstat

# RHEL/CentOS
yum install sysstat
```

----------------------------------------------------------------
C.1.2 选项全解
----------------------------------------------------------------

  -x   显示扩展统计 (核心, 必加)
  -d   只显示 disk (不显示 CPU)
  -z   隐藏无活动的设备 (zero activity)
  -p ALL  按设备路径展示 (而非原始主次号)
  -m    数值用 MB/s (默认 KB/s)
  -N    用 LVM/LUKS 的逻辑名展示 (kernel 5.x+)
  1     刷新间隔 (秒)
  5     采样次数 (缺省=无限循环)

实战常用:
```
iostat -xz 1                    # 每秒刷新, 无限循环 (后台监控)
iostat -xz 1 5                  # 5 次后退出 (脚本)
iostat -xz -p ALL 1 5           # 按 /dev/sda 路径展示
iostat -xz -m -p ALL 1 5        # MB/s 单位
iostat -d -x -N 1 5             # 显示 LVM 逻辑卷
iostat -x 1 5 -o /tmp/iostat.txt  # 输出到文件
```

----------------------------------------------------------------
C.1.3 输出列详解
----------------------------------------------------------------

  r/s, w/s      每秒读/写请求数
  rkB/s, wkB/s  每秒读/写数据量 (默认 KB, -m 后是 MB)
  rrqm/s, wrqm/s 每秒合并的读/写请求数 (合并率高说明上层 I/O 碎片)
  %rrqm, %wrqm  合并率
  r_await       读请求平均延迟 (ms)  ← 原文关注指标
  w_await       写请求平均延迟 (ms)
  aqu-sz        平均活跃请求数
  rareq-sz      平均读请求大小 (扇区)
  wareq-sz      平均写请求大小 (扇区)
  svctm         服务时间 (已被废弃, 不要再看)
  %util         设备利用率  ← SSD/NVMe 上 100% 不一定瓶颈

⚠️ SSD/NVMe 上 %util=100% 不代表饱和
  HDD: %util=100% → 一定满负荷
  SSD: %util=100% + r_await < 1ms → 健康
  SSD: %util=100% + r_await > 5ms → 真的饱和了

----------------------------------------------------------------
C.1.4 关键告警阈值 (原文 md:1307-1315)
----------------------------------------------------------------

  指标                HDD 告警阈值      SSD 告警阈值
  ────────────────────────────────────────────────
  平均读延迟 r_await   > 20 ms          > 1 ms
  P99 读延迟 (需 btt)  > 50 ms          > 5 ms
  设备利用率 %util     > 90% 持续 5min   > 95% 持续 5min

P99 延迟 iostat 看不到, 需用 btt 或 fio json (B 类已讲)

----------------------------------------------------------------
C.1.5 与工作负载模式的解读
----------------------------------------------------------------

  看到                                诊断方向
  ───────────────────────────────────────────────
  %util 高 + r_await 高               设备真的忙, 升级或加盘
  %util 低 + r_await 高               上层调度阻塞, 看 blktrace
  r_await 高 + w_await 低             读路径有问题, 看 Page Cache
  rrqm/s + wrqm/s 高                  上层 I/O 太碎, 应用调优
  aqu-sz > 1                          请求在排队 (NVMe 上很常见)

================================================================
C.2 blktrace — 内核 I/O 子系统栈追踪
================================================================

原文: md:697-699, md:1299
为什么需要 blktrace:
  iostat 只能告诉你"设备慢了"
  blktrace 告诉你"慢在哪一段":
    bio 提交 → 调度器合并 → 设备处理 → 完成

----------------------------------------------------------------
C.2.1 安装
----------------------------------------------------------------
```
# Debian/Ubuntu
apt-get install blktrace

# RHEL/CentOS
yum install blktrace
# btt 是 blktrace 包里的工具
```

----------------------------------------------------------------
C.2.2 标准三段式 (原文 md:697-699)
----------------------------------------------------------------
```
blktrace -d /dev/nvme0n1 -o trace
# ① blktrace 抓 trace 到目录 trace.* (按 CPU 分文件)

blkparse -i trace -d trace.bin
# ② blkparse 合并 + 解析 + 二进制输出

btt -i trace.bin
# ③ btt 分析 I/O 延迟分布
```

----------------------------------------------------------------
C.2.3 输出解读 — btt 的核心指标
----------------------------------------------------------------

  Q2Q   队列到队列 (request 提交延迟)
  Q2G   队列到分发 (request 提交到设备开始处理)
  G2I   分发到插入 (设备内部排队)
  I2D   插入到下发 (设备实际启动)
  D2C   下发到完成 (设备处理时间)
  Q2C   总延迟 (队列到完成, 最重要的数字)

  D2C 大 = 设备本身慢 (NVMe 通常 10-50 μs)
  Q2C - D2C 大 = 内核软件栈开销大 (调度器、bio 合并)

----------------------------------------------------------------
C.2.4 简化管道 (原文 md:1299, 一次性观察)
----------------------------------------------------------------
```
blktrace -d /dev/nvme0n1 -o - | blkparse -i - -o trace.txt
# 输出文本格式, 可 grep / awk 处理
# 等价于: trace.txt 是人能读的 trace
```

----------------------------------------------------------------
C.2.5 常用选项
----------------------------------------------------------------
```
blktrace -d /dev/nvme0n1 -w 30
# -w N  只采 N 秒

blktrace -d /dev/sda -a write -a read
# -a  只看特定操作 (write/read/flush/discard/fsync/...)

blktrace -d /dev/nvme0n1 -b 4096
# -b  每个 trace event 的缓冲区大小

blktrace -l
# 列出可 trace 的事件类型 (QFQ, insert, issue, complete, etc.)
```

----------------------------------------------------------------
C.2.6 实战: 找出"为什么延迟高"
----------------------------------------------------------------

场景: iostat 显示 r_await = 5ms (NVMe 应该 < 100us)

  1. 抓 30 秒 trace
     blktrace -d /dev/nvme0n1 -w 30 -o trace

  2. 分析 Q2C vs D2C
     btt -i trace.bin

  3. 如果 D2C 占大头 → 设备忙 (加盘/换盘)
     如果 Q2Q/Q2G 占大头 → 内核调度 (改 I/O 调度器, 用 none)

C.3 iotop — 进程级 I/O 归因 (扩展)
================================================================

原文未列, 但选型/监控必备
用途: 找出"哪个进程吃了 IOPS"

----------------------------------------------------------------
C.3.1 安装
----------------------------------------------------------------
```
apt-get install iotop
yum install iotop
```

----------------------------------------------------------------
C.3.2 使用
----------------------------------------------------------------
```
iotop
# 默认刷新 1s, 类似 top
# 列: PID PRIO USER DISK READ DISK WRITE SWAPIN IO COMMAND

iotop -o
# -o  只显示有实际 I/O 的进程 (默认会显示所有进程)

iotop -b -n 5 -t
# -b  批模式 (脚本用)
# -n N  采样 N 次后退出
# -t  加时间戳

iotop -P
# -P  按 PID 而非线程显示

iotop -a
# -a  显示累计 I/O (从启动到现在的总量)
```

----------------------------------------------------------------
C.3.3 与 ps/lsof 联动
----------------------------------------------------------------

找出谁在写某个文件:
```
lsof /path/to/file
# 找到 PID 后:
iotop -P -p <pid>
```

================================================================
C.4 perf — 内核级事件采样 (扩展)
================================================================

原文未列, 但细粒度分析利器
用途: 用 perf trace 跟踪某个进程的 syscall I/O 路径

----------------------------------------------------------------
C.4.1 安装
----------------------------------------------------------------
```
apt-get install linux-tools-common linux-tools-$(uname -r)
yum install perf
```

----------------------------------------------------------------
C.4.2 跟踪某个进程的 I/O
----------------------------------------------------------------
```
perf trace -p <pid>
# 显示进程的所有 syscall, 包括 read/write/pwrite64/fsync
# 看到每个 write 调用的字节数 + 延迟

perf trace -e read,write,fsync -- <command>
# 跟踪某个命令的 I/O syscall
```

----------------------------------------------------------------
C.4.3 块设备 I/O 事件采样
----------------------------------------------------------------
```
perf stat -e block:block_rq_issue,block:block_rq_complete -a sleep 10
# 统计 10 秒内的块设备 I/O 事件数

perf record -e block:block_rq_issue -a -g
perf script
# 录制 + 解析 (与 blktrace 类似, 但 perf 更通用)
```

================================================================
C.5 监控组合拳 — 选型验证完整流程
================================================================

场景: 新盘上线后想确认性能
  1. 后台持续 iostat (告警用)
     iostat -xz 1 600 > /tmp/iostat.log &
     # 跑 10 分钟

  2. 期间跑 fio 压测
     fio --name=verify ... (B.2 任意一段)

  3. 同时观察 iotop 找到热点进程
     iotop -P -o

  4. 压测结束后用 blktrace 分析延迟构成
     blktrace -d /dev/nvme0n1 -w 30 -o /tmp/trace
     btt -i /tmp/trace.bin

  5. 用 perf 看具体进程 syscall 延迟
     perf trace -p $(pgrep -n mysqld)  # 数据库进程

================================================================
C 类命令 → 决策节点
================================================================

iostat 趋势   → 看是否触发 F 类告警阈值
blktrace      → 慢在"内核"还是"设备"→ 选择优化方向:
                设备慢: 加盘/换盘
                内核慢: 改 I/O 调度器/绑核/调 Page Cache
iotop         → 找出"罪魁祸首"进程, 应用层调优
perf trace    → 确认是 syscall 慢还是 fsync 太频繁
