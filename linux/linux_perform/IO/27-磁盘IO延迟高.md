# 27 | 为什么磁盘 I/O 延迟很高？

原文：[time.geekbang.org/column/article/78409](https://time.geekbang.org/column/article/78409)

单词热度 API 要等几分钟；连本机 `df` 都卡。方向仍是 I/O，但 **`strace -p` 看不到 write**。

## 现象

- iowait 94%，python 约 14% CPU（I/O 优先，别被 CPU 带跑）
- `iostat`：`%util` 98%、写 32MB/s、`w_await` 18 秒
- `pidstat -d`：同一 python 写 300MB/s+，**iodelay 却是 0**——自己写得欢，把别人（含系统命令）堵死

## 为什么 strace 是空的

**默认不跟线程。** 写文件在子线程里。

```bash
strace -fp <pid>          # 跟所有线程
pstree -p <pid>           # 找 TID 再 strace -p <tid>
```

不是因为 Python 解释器，也不是因为 Docker。工具输出对不上时先查默认选项。

## 新工具（bcc）

| 工具 | 看什么 |
|------|--------|
| `filetop -C` | 每线程读写次数/大小、文件名（没有路径） |
| `opensnoop` | 内核 `open`：PID、完整路径 |

案例：线程 514 先写大量 `N.txt` 再读；`opensnoop` 看到 `/tmp/<uuid>/0.txt` … `999.txt`，目录用完就删，所以 `ls` 经常「No such file」。

源码：每个请求 mkdir → 写 1000 个临时文件 → 再读回来数词 → `rmtree`。盘当草稿纸。

## 优化

内存够就把数据放内存（案例另一个接口 `/popular/word`：3 分钟 → 8 秒）。先用最简单的办法止血，再用 Trie 等算法继续抠。

生产上 `perf record -e 'fs:*'` 开销比 strace 小，但是统计不是逐次调用。简单场景 `lsof -p` 有时一步就够。
