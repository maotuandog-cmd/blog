可以。你现在已经把 WAL 的核心概念过了一遍，所以这次我不把 Shared Buffer 讲成“缓存是什么”，而是直接从 **PostgreSQL 18 源码实现的角度，把它当成一个完整系统讲透**。

先给你一句最重要的结论：

> **Shared Buffer Manager 本质上是在 PostgreSQL 进程之间维护一个“可并发访问、可淘汰、可持久化”的 Page Cache。**
> 
> 它解决的不只是“把磁盘页放内存”，而是同时解决：  
> **Page 定位、缓存命中、并发访问、Pin、淘汰、脏页、IO、WAL 顺序、后台刷盘、异步 IO。**

PostgreSQL 18 里，这套东西还因为 AIO 子系统的引入，IO 路径比以前更值得研究。([PostgreSQL](https://www.postgresql.org/docs/18/release-18.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: E.6. Release 18"))

```text
                 Shared Buffer

    │
    ▼
```


这最后一条就是你之前学过的 **WAL 与 Shared Buffer 的连接点**。

# 二、Shared Buffer 到底存的是什么？

假设：

```text
shared_buffers = 1GB
BLCKSZ = 8KB
```

那么大约：

```text
1GB / 8KB
≈ 131072 buffers
```

也就是 PostgreSQL 预先建立大约 13 万个 buffer slot。

但是千万不要理解成：

```text
Buffer 1 → table A page 1
Buffer 2 → table A page 2
Buffer 3 → table A page 3
```

**不是固定映射。**

实际上：

```text
Buffer 1234
    ↓
现在可能装：
    relation A / block 100

过一段时间：
    relation B / block 5000

再过一段时间：
    relation C / block 20
```

所以 Shared Buffer 本质上是：

```text
固定数量的内存槽位
+
动态 Page → Buffer 映射
+
淘汰机制
```

`shared_buffers` 控制的就是 PostgreSQL 用于 shared memory buffer 的这部分空间；通常一个 buffer 对应 `BLCKSZ` 大小的数据页，而 `BLCKSZ` 通常是 8KB。([PostgreSQL](https://www.postgresql.org/docs/18/runtime-config-resource.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: 19.4. Resource Consumption"))

# 三、一个 Buffer 实际上不是一个东西

这是源码阅读非常重要的一点。

很多人第一次看 PostgreSQL Buffer Manager，会把：

```text
Buffer
```

理解成：

```text
8KB 内存
```

其实不完整。

更准确：

```text
                    Buffer
                      │
            ┌─────────┴─────────┐
            │                   │
       BufferDesc            Buffer Page
       元数据                  数据
```

例如：

```text
BufferDesc
├── Buffer ID
├── BufferTag
├── state
│   ├── refcount / pin
│   ├── usage_count
│   ├── dirty
│   ├── valid
│   ├── IO state
│   └── ...
└── synchronization
         
              │
              ▼

       ┌──────────────────┐
       │ PostgreSQL Page  │
       │                  │
       │  PageHeader      │
       │  Tuple           │
       │  Tuple           │
       │  Free Space      │
       │  ...             │
       └──────────────────┘
             8KB
```

所以你以后看源码的时候一定要分清：

> **BufferDesc 是“这个 buffer 怎么管理”。**
> 
> **Buffer Page 是“这个 buffer 里面装什么数据”。**

# 四、BufferTag：Shared Buffer 怎么知道自己缓存的是哪个 Page？

这是整个 Buffer Manager 的第一个核心。

磁盘上的 Page 有逻辑身份：

```text
tablespace
database
relation
fork
block number
```

PostgreSQL 内部可以理解成：

```text
BufferTag
    │
    ├── RelFileLocator
    │     ├── tablespace
    │     ├── database
    │     └── relation
    │
    ├── ForkNumber
    │
    └── BlockNumber
```

例如：

```text
BufferTag =
(
    tablespace = 1663,
    database   = 16384,
    relation   = 16390,
    fork       = MAIN,
    block       = 123
)
```

它代表：

```text
某个 relation
的 main fork
的第 123 个 block
```

所以：

> **BufferTag 是 Page 的逻辑身份证。**

而：

```text
Buffer ID
```

只是：

> **它当前住在哪个 Shared Buffer 槽位。**

比如：

```text
BufferTag
   │
   │ hash
   ▼
Buffer Mapping Hash Table
   │
   ▼
Buffer ID = 5231
   │
   ▼
BufferDesc[5231]
   │
   ▼
真正的 8KB Page
```

这就是：

```text
Page identity
      ↓
Buffer Mapping
      ↓
Buffer slot
```

# 五、所以 Buffer Manager 最核心的问题其实是：

假设执行器想访问：

```text
relation A
block 100
```

它首先要问：

> **这个 Page 已经在 Shared Buffer 里面了吗？**

于是：

```text
ReadBuffer()
    │
    ▼
构造 BufferTag
    │
    ▼
BufTableLookup()
    │
    ├──── HIT ────→ Buffer
    │
    └──── MISS
```

这就是 Shared Buffer 最核心的一条路径。

源码主要从：

```text
src/backend/storage/buffer/bufmgr.c
```

开始看。

而 Page Tag → Buffer ID 的映射主要在：

```text
src/backend/storage/buffer/buf_table.c
```

# 六、Hit 是最简单的一条路径

假设：

```text
SELECT ...
```

需要：

```text
relation A / block 100
```

Buffer Manager：

```text
ReadBuffer()
    │
    ▼
BufferTag
    │
    ▼
BufTableLookup()
    │
    ▼
找到 Buffer 5231
    │
    ▼
Pin Buffer
    │
    ▼
返回 Buffer 5231
```

然后 executor/access method 就可以访问：

```text
Buffer 5231
    │
    ▼
8KB Page
```

这就是：

```text
shared hit
```

`EXPLAIN (BUFFERS)` 中的：

```text
shared hit
```

就是这种“页面已经在 PostgreSQL shared buffer cache 中，因此避免了一次底层读取”的情况。([PostgreSQL](https://www.postgresql.org/docs/18/sql-explain.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: EXPLAIN"))

# 七、为什么需要 Pin？

这里是 Buffer Manager 第二个非常重要的概念。

假设：

```text
Backend A
正在使用 Buffer 5231
```

这时候：

```text
Backend B
发现 Buffer 5231 可以淘汰
```

如果没有保护机制：

```text
A 正在读 Page A
        ↓
B 把 Buffer 5231 换成 Page B
        ↓
A 突然读到 Page B
```

直接炸。

所以 PostgreSQL 引入：

```text
Pin
```

可以理解成：

> **我现在正在使用这个 Buffer，你不能拿它做 replacement。**

于是：

```text
Buffer 5231

refcount / pin count = 3

Backend A ──┐
Backend B ──┼──→ Buffer 5231
Backend C ──┘
```

只要：

```text
pin count > 0
```

replacement 就不能拿它当 victim。

这里有一个源码细节很值得你注意：

**PG18 内部不是简单地直接 `buf->refcount++`。**

它还有 private refcount 等机制，目的是减少多个 backend 对共享状态频繁更新造成的竞争。

所以你后面真正读源码时，会看到比“引用计数 +1”复杂很多的实现。

---

# 八、Pin 和 Usage Count 千万不要混

这是理解 PostgreSQL replacement 的关键。

有两个完全不同的概念：

### Pin

表示：

> **现在有人正在用我。**

决定：

```text
能不能被淘汰？
```

---

### Usage Count

表示：

> **最近有没有被频繁访问。**

决定：

```text
淘汰的时候，我应该优先留下还是优先被淘汰？
```

例如：

```text
Buffer A
pin = 0
usage_count = 5

Buffer B
pin = 0
usage_count = 0
```

A 没人在用，但最近非常热门。

B 也没人用，但很久没人访问。

那么 replacement 更倾向于：

```text
淘汰 B
```

所以：

```text
Pin
    = 当前正在使用

Usage Count
    = 最近活跃程度
```

这是两个维度。

PG18 的 `pg_buffercache` 甚至可以直接看到：

```text
usagecount
pinning_backends
isdirty
bufferid
relfilenode
relblocknumber
```

所以这些不是概念模型，而是可以从系统里观察到的真实 Buffer Manager 状态。([PostgreSQL](https://www.postgresql.org/docs/18/pgbuffercache.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: F.25. pg_buffercache — inspect PostgreSQL buffer cache state"))

不在 Shared Buffer。

```text
      │

MISS
      │
      ▼
找一个 victim buffer
```

这里进入：

```text
freelist.c
```

核心函数：

```text
StrategyGetBuffer()
```

# 十、PostgreSQL 并不是简单的 LRU

这是一个非常容易产生误解的地方。

很多资料会告诉你：

> PostgreSQL Buffer 是 LRU。

严格来说这是不准确的。

PG 的核心 replacement 是：

> **Clock Sweep**

同时还有：

> **Buffer Access Strategy / Ring Buffer**

PG18 文档也明确描述了 Buffer Access Strategy：对于大量顺序访问页面的操作，可以建立一个有限大小的 ring，并循环复用这些 buffer，从而避免把大量其他有用页面驱逐出 shared buffers。([PostgreSQL](https://www.postgresql.org/docs/18/glossary.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: Appendix M. Glossary"))

---

# 十一、Clock Sweep 怎么工作？

假设：

```text
Buffer 0   usage = 3
Buffer 1   usage = 0
Buffer 2   usage = 1
Buffer 3   usage = 5
Buffer 4   usage = 0
```

有一个：

```text
clock hand
```

不断向前扫描。

大致可以理解：

```text
             clock hand
                 ↓
      ┌──────┐
      │ Buf0 │ usage=3
      └──────┘
          ↓
      ┌──────┐
      │ Buf1 │ usage=0  ← candidate
      └──────┘
          ↓
      ┌──────┐
      │ Buf2 │ usage=1
      └──────┘
          ↓
      ┌──────┐
      │ Buf3 │ usage=5
      └──────┘
```

如果发现：

```text
pin > 0
```

跳过。

如果：

```text
usage_count > 0
```

降低 usage_count，再继续扫。

最终找到：

```text
pin = 0
usage_count = 0
```

就可以成为 victim。

所以它不是：

```text
每次维护一个完整 LRU 链表
```

而是：

```text
Clock Sweep
+
usage_count
```

这对 PostgreSQL 这种高并发数据库来说成本更低。

---

# 十二、为什么还要 Ring Buffer？

因为存在一种很典型的场景：

```sql
SELECT * FROM huge_table;
```

假设：

```text
shared_buffers = 8GB

huge_table = 500GB
```

如果完全按照普通 replacement：

```text
读取 500GB
    ↓
不断装入 shared buffers
    ↓
不断驱逐原来的缓存
```

可能把原本很热门的数据全部冲掉。

这就是：

> **Buffer Pool Pollution**

所以 PostgreSQL 对某些操作使用：

```text
Buffer Access Strategy
```

例如：

- 大表顺序扫描
    
- VACUUM
    
- COPY
    
- CREATE TABLE AS
    
- CREATE INDEX
    
- CLUSTER
    

官方文档也明确列出了这些用途。([PostgreSQL](https://www.postgresql.org/docs/18/glossary.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: Appendix M. Glossary"))

---

# 十三、Ring 的思想

比如建立：

```text
Ring:

Buffer 100
Buffer 101
Buffer 102
Buffer 103
Buffer 104
```

扫描：

```text
Page A → Buffer100

Page B → Buffer101

Page C → Buffer102

Page D → Buffer103

Page E → Buffer104

Page F → Buffer100

Page G → Buffer101
```

也就是：

```text
循环复用有限的一小批 buffer
```

这样：

```text
500GB sequential scan
```

不会天然把：

```text
整个 shared_buffers
```

都污染。

PostgreSQL 18 的 `VACUUM` 还提供 `BUFFER_USAGE_LIMIT` 来控制这种 Buffer Access Strategy ring 的大小。官方文档明确指出，过大的 ring 可能驱逐其他有用的 shared buffers。([PostgreSQL](https://www.postgresql.org/docs/18/sql-vacuum.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: VACUUM"))

```text
Page A
```

不在 cache。

Buffer Manager 找到了：

```text
Buffer 5231
```

作为 victim。

但是：

```text
Buffer 5231
```

可能里面还有：

```text
Page B
```

# 十五、Clean Buffer 最简单

如果：

```text
Page B
```

没有被修改：

```text
dirty = false
```

那么：

```text
Buffer 5231
    │
    ▼
直接丢掉 Page B
    │
    ▼
装入 Page A
```

因为磁盘上已经有最新版本。

# 十六、Dirty Buffer 就复杂了

假设：

```text
Disk:
Page B = old

Shared Buffer:
Page B = new
```

那么：

```text
dirty = true
```

此时不能直接：

```text
Page B → 丢掉
```

否则修改丢失。

所以必须：

```text
Buffer 5231
    │
    ▼
Flush Page B
    │
    ▼
Data File
```

# 十七、这里就重新接回你之前学的 WAL

这是整个 PostgreSQL Storage Engine 最漂亮的一条链。

假设：

```text
Page B
```

被修改。

Page Header 中有：

```text
PageLSN = X
```

这个 Page 对应的 WAL：

```text
LSN X
```

必须先 durable。

所以写 Page 的时候：

```text
FlushBuffer(Page B)
        │
        ▼
Get PageLSN
        │
        ▼
XLogFlush(PageLSN)
        │
        ▼
WAL durable
        │
        ▼
smgr write data page
        │
        ▼
disk
```

即：

> **WAL 必须先于 Data Page 落盘。**

你之前学的 WAL 到这里就真正和 Shared Buffer 接上了。

# 十八、所以 Shared Buffer 和 WAL 的职责完全不同

可以这样理解：

```text
Shared Buffer
    负责：
    “Page 现在在哪里、怎么缓存、怎么修改、什么时候淘汰”

WAL
    负责：
    “这些修改怎么保证 crash recovery”
```

它们组合起来：

```text
              UPDATE
                 │
                 ▼
           Shared Buffer
                 │
                 ├── Page 修改
                 │
                 ├── Dirty
                 │
                 └── PageLSN
                       │
                       ▼
                      WAL
                       │
                       ▼
                 durable WAL
                       │
                       ▼
                Data Page flush
```

# 十九、Dirty Page 并不会马上写磁盘

这是另一个特别重要的概念。

执行：

```sql
UPDATE ...
```

并不是：

```text
UPDATE
 ↓
write data file
```

而更像：

```text
UPDATE
  │
  ▼
Buffer Page 修改
  │
  ▼
MarkBufferDirty()
  │
  ▼
Dirty Buffer
```

然后数据页可能过一段时间才真正写到磁盘。

写出的时机可能包括：

```text
Background Writer
Checkpointer
Buffer Replacement
其他需要 flush 的场景
```

官方文档对 background writer 的定义就是：它周期性地从 shared memory 写出 dirty data pages，用于平滑昂贵的 IO，避免形成大的 IO 峰值。([PostgreSQL](https://www.postgresql.org/docs/18/glossary.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: Appendix M. Glossary"))

# 二十、所以 Shared Buffer 里会同时存在三种非常重要的状态

你可以脑子里建立：

```text
               Page
                │
        ┌───────┴────────┐
        │                │
      Clean            Dirty
        │                │
        │                ▼
        │          WAL must be durable
        │                │
        │                ▼
        │             Flush
        │                │
        ▼                ▼
     可直接淘汰        可写回后淘汰
```

而无论 clean/dirty：

```text
Pin > 0
```

的时候都不能随便淘汰。

# 二十一、Buffer Descriptor 的 state 是整个系统的“控制中心”

源码里你会看到：

```text
BufferDesc
```

以及它的：

```text
state
```

这个 state 不是简单的：

```c
enum {
    EMPTY,
    VALID,
    DIRTY
}
```

这种模型。

实际上是各种 bit/state 信息组合起来管理。

概念上可以理解成：

```text
BufferDesc.state
│
├── Tag valid
├── Page valid
├── Dirty
├── IO in progress
├── IO error
├── Just dirtied
├── Refcount / pin
├── Usage count
└── ...
```

因此一个 Buffer 可以处于类似：

```text
未使用
  ↓
IO_IN_PROGRESS
  ↓
VALID
  ↓
DIRTY
  ↓
FLUSH
  ↓
CLEAN
  ↓
REUSE
```

注意：

> 这是为了理解建立的状态机模型，不是源码里存在这么一个简单 enum。

# 二十二、为什么 IO_IN_PROGRESS 很重要？

假设：

```text
Backend A
请求 Page X
```

发现：

```text
Page X 不在 Buffer
```

于是：

```text
Buffer 100
```

开始读取：

```text
Disk → Buffer100
```

此时：

```text
IO_IN_PROGRESS
```

这时候：

```text
Backend B
```

又请求：

```text
Page X
```

它不能傻乎乎再：

```text
Disk → Buffer101
```

再读一遍。

正确逻辑应该是：

```text
Page X
   │
   ▼
发现 Buffer100 正在 IO
   │
   ▼
等待 IO
   │
   ▼
IO完成
   │
   ▼
使用 Buffer100
```

所以：

> **Buffer Manager 不只是 cache，它还是 Page IO 的并发协调器。**

# 二十三、PG18 在 IO 这里又发生了一个重要变化

这个你读 PG18 源码的时候一定要注意。

PostgreSQL 18 引入了新的 AIO subsystem。官方 release note 把它列为 PG18 的重要新能力。([PostgreSQL](https://www.postgresql.org/docs/18/release-18.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: E.6. Release 18"))

所以你在 PG18 的 Buffer Manager 里会看到类似：

```text
StartReadBuffer()
StartReadBuffers()
WaitReadBuffers()
AsyncReadBuffers()
```

也就是说：

以前你脑子里容易形成：

```text
ReadBuffer()
    ↓
read()
    ↓
return
```

这种模型。

PG18 更接近：

```text
Start IO
   │
   ▼
IO running
   │
   ├──────────→ CPU 可以继续做其他事情
   │
   ▼
Wait IO
   │
   ▼
IO complete
```

所以如果你接下来深入 PG18 源码，**IO 路径一定要单独学习**，不能完全照着 PG14/PG15 的老资料理解。

# 二十四、Buffer Manager 还有几种非常重要的锁/并发机制

这里很容易乱。

你至少要分清四个东西。

---

## 1. Buffer Mapping Lock

负责：

```text
BufferTag
   ↓
Buffer ID
```

也就是：

```text
Buffer Mapping Hash Table
```

的并发访问。

对应：

```text
buf_table.c
```

---

## 2. Buffer Header State

管理：

```text
refcount
usage_count
dirty
valid
IO state
...
```

也就是：

> **BufferDesc 自己的管理状态。**

---

## 3. Buffer Content Lock

这个是：

> **保护 8KB Page 内容。**

比如两个 backend：

```text
Backend A
修改 Page

Backend B
同时修改 Page
```

需要 content lock 来保护页面内容。

所以：

```text
Buffer Pin
≠
Buffer Content Lock
```

这是你后面学习 PostgreSQL 锁的时候一定要分清的。

---

## 4. Buffer Strategy Lock

用于保护 replacement strategy 中的一些共享状态，例如：

```text
clock sweep position
```

等。

---

# 二十五、完整的 Page Read 流程

现在把刚才所有东西串起来。

假设：

```sql
SELECT * FROM t WHERE ...
```

需要：

```text
relation t
block 123
```

---

### 第一步：构造 BufferTag

```text
(tablespace,
 database,
 relation,
 fork,
 block=123)
```

---

### 第二步：查 Buffer Mapping

```text
BufTableLookup(tag)
```

---

### 第三步：如果 HIT

```text
Buffer found
    │
    ▼
PinBuffer
    │
    ▼
检查 Page 状态
    │
    ▼
return Buffer
```

结束。

---

### 第四步：如果 MISS

```text
BufferAlloc / GetVictimBuffer
```

开始找 victim。

---

### 第五步：找 victim

进入：

```text
freelist.c
```

然后：

```text
StrategyGetBuffer()
```

可能：

```text
Buffer Access Strategy Ring
```

也可能：

```text
Clock Sweep
```

---

### 第六步：检查 victim

假设：

```text
Buffer 5231
```

里面原来是：

```text
Page B
```

检查：

```text
pin?
dirty?
IO?
```

---

### 第七步：如果 dirty

```text
Page B
   │
   ▼
PageLSN
   │
   ▼
XLogFlush(PageLSN)
   │
   ▼
smgrwrite()
   │
   ▼
data file
```

---

### 第八步：复用 Buffer

```text
Buffer 5231
```

重新绑定：

```text
BufferTag = Page A
```

也就是：

```text
old tag
   ↓
remove

new tag
   ↓
insert
```

---

### 第九步：启动 Page Read

```text
data file
    ↓
Page A
    ↓
Buffer 5231
```

PG18 这里可能经过新的 AIO/read start/wait 路径。

---

### 第十步：IO 完成

设置类似：

```text
BM_VALID
```

确保 Page 是有效的。

---

### 第十一步：返回

```text
Buffer 5231
   ↓
executor
```

然后 executor/access method 使用：

```text
8KB Page
```

---

# 二十七、那后台进程在这里扮演什么角色？

你可以把 Shared Buffer 周围的角色理解成：

```text
                    Shared Buffers
                         │
          ┌──────────────┼───────────────┐
          │              │               │
          ▼              ▼               ▼
      Backend       Background       Checkpointer
                      Writer
          │              │               │
          │              │               │
          └──────────────┼───────────────┘
                         ▼
                      Data File
```

### Backend

主要负责：

```text
读 Page
修改 Page
Pin
Unpin
必要时参与 flush
```

---

### Background Writer

主要负责：

```text
提前写一部分 dirty buffers
```

目标是：

> **平滑 IO。**

而不是等 backend 真正需要 victim 的时候才大量写盘。

---

### Checkpointer

Checkpoint 的时候负责：

```text
把 checkpoint 所要求的 dirty pages 写出去
```

从而形成恢复点。

# 二十八、为什么 PostgreSQL 还需要 OS Page Cache？

这个问题你之前问 WAL 的时候其实已经碰到过。

很多人会认为：

```text
PostgreSQL Shared Buffer
```

就是：

```text
全部内存缓存
```

实际上不是。

典型 Linux 环境：

```text
PostgreSQL Backend
      │
      ▼
Shared Buffers
      │
      ▼
read/write
      │
      ▼
Linux Page Cache
      │
      ▼
Disk
```

所以数据可能存在：

```text
PostgreSQL shared buffer
```

同时也可能存在：

```text
OS page cache
```

这就是为什么 PostgreSQL 官方建议 `shared_buffers` 不要简单地把机器 RAM 全吃掉；数据库还依赖 OS cache。PG18 文档给出的通用起点是专用数据库服务器上约 25% RAM，并指出超过约 40% RAM 通常未必更好，具体仍取决于 workload。([PostgreSQL](https://www.postgresql.org/docs/18/runtime-config-resource.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 18: 19.4. Resource Consumption"))
