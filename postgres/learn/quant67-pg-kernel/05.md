可以。我们这次不讲 WAL 的边角，而是把 **PG 18 Shared Buffer / Buffer Manager 的整体实现**从架构到源码调用链完整串起来。

我先给你一个结论：

> **Shared Buffer 本质上不是“一个缓存数组”，而是一套由 Buffer Descriptor、Buffer Tag/Hash Table、Pin/UsageCount、Victim Selection、IO 状态机、Dirty 管理和后台刷盘共同组成的页缓存系统。**

PG 18 的 `bufmgr.c` 已经包含了 `ReadBuffer`、`StartReadBuffer/WaitReadBuffers`、`MarkBufferDirty`、victim 获取、flush 等大量核心逻辑；buffer replacement 则主要在 `freelist.c`，lookup table 在 `buf_table.c`。([GitHub](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/bufmgr.c?utm_source=chatgpt.com "postgres/src/backend/storage/buffer/bufmgr.c at master · postgres/postgres · GitHub"))

# 二、Shared Buffer 到底存的是什么？

假设：

```conf
shared_buffers = 1GB
BLCKSZ = 8KB
```

那么大约：

```text
1GB / 8KB
≈ 131072 buffers
```

也就是：

```text
Shared Buffer Pool

Buffer 0
Buffer 1
Buffer 2
...
Buffer 131071
```

每个 buffer 对应一个 PostgreSQL page。

但是不能简单理解成：

```text
Buffer 0 = table A block 0
Buffer 1 = table A block 1
...
```

**不是固定映射。**

今天：

```text
Buffer 100
    ↓
table A block 20
```

之后可能：

```text
Buffer 100
    ↓
table B block 500
```

因为 buffer 是动态复用的。

所以 PG 必须额外维护：

> “当前哪个 relation/block 在哪个 buffer？”

这就是 Buffer Tag + Buffer Mapping Hash Table。

# 三、Buffer Descriptor 才是管理核心

可以把：

```text
Buffer Page
```

理解成：

```text
真正的 8KB 数据
```

而：

```text
BufferDesc
```

是：

```text
这 8KB 数据的身份证 + 状态信息
```

```text
├── Buffer Tag

│    └── block
│
├── state
│    ├── refcount
│    ├── usage_count
│    ├── dirty
│    ├── valid
│    ├── IO in progress
│    └── ...
│
└── locks / synchronization
```

而真正的：

```text

```

是另外的内存区域。

可以画成：

```text
             BufferDesc #1234
            ┌───────────────┐
            │ tag           │
            │ state         │

            │               │
```

# 四、Buffer Tag 是整个系统的“地址”

才是：

而：


只是：

> “它目前在 Shared Buffer 的哪个槽位”。

这是两个完全不同的概念。

# 八、为什么找到 Buffer 以后还要 Pin？

这是 Shared Buffer 非常重要的概念。

假设：

```text
Backend A
    ↓
Buffer 500
```

正在使用。

同时：

```text
Backend B
```

需要一个新的 buffer。

如果 Buffer Manager 发现：

```text
Buffer 500
```

很久没用，于是：

```text
“我把 500 淘汰掉。”
```

那 Backend A 就炸了。

所以 Backend A：

```text
Pin(Buffer 500)
```

意味着：

> **这个 buffer 当前有人正在使用，不能被 replacement。**

# 九、PinCount 是什么？

假设：

```text
Backend A → Pin Buffer 100
Backend B → Pin Buffer 100
Backend C → Pin Buffer 100
```

那么：

```text
refcount = 3
```

可以粗略理解成：

```text
PinCount / refcount
```

不过 PG 18 内部已经是比较复杂的状态打包和 private refcount 管理，不要简单认为所有 pin 都只是一个裸 `int`。

源码里 `PinBuffer()` 会更新 refcount，同时也会影响 usage count。PG 18 的实现对默认策略和 ring strategy 的 usage count 更新也做了区分。([Fossies](https://fossies.org/dox/postgresql-18.6/bufmgr_8c_source.html?utm_source=chatgpt.com "postgresql: src/backend/storage/buffer/bufmgr.c Source File - doxygen documentation | Fossies Dox"))

# 十、Pin 和 UsageCount 千万不要混

这是 Shared Buffer 初学者最容易混淆的两个东西。

### Pin

回答：

> **现在有没有人正在使用？**

例如：

```text
refcount = 2
```

表示：

```text
现在有 2 个引用者
```

因此不能被淘汰。

---

### UsageCount

回答：

> **这个 buffer 最近是不是比较活跃？**

例如：

```text
usage_count = 5
```

意味着：

```text
replacement 时不要轻易选它
```

所以：

```text
Pin
    → 当前正在用

UsageCount
    → 最近活跃程度
```

# 十一、Buffer Miss

如果：

```text
BufTableLookup()
```

没找到：


那么：

```text
Buffer Miss
```

流程变成：

```text
ReadBuffer
    │
    ▼
BufferTag
    │
    ▼
BufTableLookup
    │
    ├── HIT
    │
    └── MISS
          │
```

这时候真正进入：

# 十二、PG 怎么找 victim？

这里是：

```text
src/backend/storage/buffer/freelist.c
```

核心：

```c
StrategyGetBuffer()
```

PG 18 仍然采用 clock-sweep 思路，并且 `StrategyGetBuffer()` 首先可以尝试使用某个 `BufferAccessStrategy` 的 ring；否则进入全局 victim selection。源码注释明确说明它只要求选出的 buffer 当前没有被 pin。([GitHub](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/freelist.c?utm_source=chatgpt.com "postgres/src/backend/storage/buffer/freelist.c at master · postgres/postgres · GitHub"))

所以：

```text
Buffer Miss
    │
    ▼
StrategyGetBuffer()
    │
    ├── 有特殊 strategy？
    │       │
    │       ▼
    │     Ring
    │
    └── 普通情况
            │
            ▼
       Clock Sweep
```

# 十三、为什么叫 Clock Sweep？

假设：

```text
Buffer 0  usage=3
Buffer 1  usage=0
Buffer 2  usage=2
Buffer 3  usage=0
Buffer 4  usage=1
```

有一个 clock hand：

```text
              clock hand
                   ↓
0      1      2      3      4
│      │      │      │      │
3      0      2      0      1
```

扫过去。

如果：

```text
refcount > 0
```

直接不能用。

如果：

```text
usage_count > 0
```

通常降低 usage_count，然后继续扫。

最后找到：

```text
refcount = 0
usage_count = 0
```

的 buffer。

# 十四、但 PG 18 已经不是“简单 Clock Sweep”

源码里你会看到：

```c
StrategyGetBuffer()
```

和：

```c
ClockSweepTick()
```

以及：

```c
GetBufferFromRing()
```

所以更准确地说：

```text
BufferAccessStrategy
        │
        ├── Ring Strategy
        │
        └── Default Strategy
                 │
                 ▼
            Clock Sweep
```

PG 18 的 `StrategyGetBuffer()` 明确先尝试 ring strategy，然后再走常规策略。([GitHub](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/freelist.c?utm_source=chatgpt.com "postgres/src/backend/storage/buffer/freelist.c at master · postgres/postgres · GitHub"))

# 十五、为什么要有 Ring？

这个设计非常重要。

例如：

```sql
VACUUM
```

或者：

```text
大型顺序扫描
```

可能访问：

```text
page 1
page 2
page 3
...
page 1000000
```

如果全部塞进普通 Shared Buffer：

```text
大量冷数据
    ↓
把热点 page 顶掉
```

非常糟糕。

所以 PG 可以给某些操作：

```text
BufferAccessStrategy
```

建立一个小 ring：

```text
Ring:

A → B → C → D
    ↑       │
    └───────┘
```

不断复用。

所以：

```text
大型 sequential scan
```

可以避免把整个 Shared Buffer 池污染掉。

# 十六、找到了 victim 以后怎么办？

假设：

```text
Buffer 500
```

被选中。

首先要确认：

```text
refcount == 0
```

然后 pin 它，防止竞争者抢走。

PG 18 的 `GetVictimBuffer()` 调用 `StrategyGetBuffer()` 后，会将选中的 buffer pin 住，然后检查是否 dirty；源码中还会处理并发使用导致的重新选择。([Doxygen PostgreSQL](https://doxygen.postgresql.org/bufmgr_8c.html?utm_source=chatgpt.com "PostgreSQL Source Code: src/backend/storage/buffer/bufmgr.c File Reference"))

流程：

```text
StrategyGetBuffer()
       │
       ▼
选中 Buffer 500
       │
       ▼
Pin
       │
       ▼
检查 Dirty
       │
       ├── clean
       │     ↓
       │   直接复用
       │
       └── dirty
             ↓
          Flush
             ↓
          再复用
```

# 十七、Dirty 是什么？

假设：

```text
磁盘：

Page A = old
```

读入：

```text
Shared Buffer:

Page A = old
```

然后：

```sql
UPDATE
```

修改：

```text
Shared Buffer:

Page A = new
```

此时：

```text
Disk:
old

Buffer:
new
```

所以 buffer：

```text
DIRTY
```

也就是：

> **Buffer 内容和磁盘内容不一致。**

# 十八、谁负责设置 Dirty？

典型：

```c
MarkBufferDirty(buffer);
```

例如：

```text
heap_update()
    ↓
修改 page
    ↓
MarkBufferDirty()
```

然后：

```text
Shared Buffer
    │
    └── dirty = true
```

注意：

> `MarkBufferDirty()` 并不意味着“马上写磁盘”。

PG 18 的源码注释也明确说明，标记 dirty 后，磁盘写入会延迟到 buffer replacement 或 checkpoint 等时机。([GitHub](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/bufmgr.c?utm_source=chatgpt.com "postgres/src/backend/storage/buffer/bufmgr.c at master · postgres/postgres · GitHub"))

# 十九、这时候 WAL 又回来了

这就是你之前学 WAL 的东西。

假设：

```text
Buffer PageLSN = 1000
```

现在准备把这个 dirty page 写磁盘。

不能直接：

```text
write(data page)
```

必须先：

```text
XLogFlush(1000)
```

确保：

```text
WAL flush LSN >= 1000
```

然后才能：

```text
write data page
```

所以 Shared Buffer 的 flush 路径：

```text
Dirty Buffer
     │
     ▼
PageLSN
     │
     ▼
XLogFlush(PageLSN)
     │
     ▼
WAL durable
     │
     ▼
smgr / Storage Manager
     │
     ▼
Data File
```

这就是：

> **Shared Buffer 和 WAL 真正连接起来的地方。**

# 二十、FlushBuffer 是核心函数之一


你以后读源码，这两个函数值得重点看。PG 18 的 `bufmgr.c` 明确把 flush buffer 作为 buffer manager 的核心内部路径。([GitHub](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/bufmgr.c?utm_source=chatgpt.com "postgres/src/backend/storage/buffer/bufmgr.c at master · postgres/postgres · GitHub"))

# 二十三、后台进程又是怎么参与的？

# 二十六、Buffer 的状态其实是一个状态机

你可以这样理解：

```text
              空闲
               │
               │ read
               ▼
          IO_IN_PROGRESS
               │
               ▼
             VALID
               │
          ┌────┴────┐
          │         │

          │         │
          ▼         │

               │
```

# 二十七、IO_IN_PROGRESS 非常重要

假设：

```text
Backend A
    ↓
Buffer 100
    ↓
开始 read
```

此时：

```text
BM_IO_IN_PROGRESS
```

Backend B 又访问：

```text
同一个 page
```

它不能再：

```text
重新从磁盘 read 一遍
```

而是：

```text
发现 IO 正在进行
       ↓
等待
       ↓
IO 完成
       ↓
检查 BM_VALID
       ↓
继续使用
```

PG 18 已经把 read buffer 拆成：

```text
StartReadBuffer()
WaitReadBuffers()
```

甚至支持多 buffer read。`bufmgr.c` 的入口注释和实现都体现了这种“启动 IO / 等待 IO”分离的设计。([GitHub](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/bufmgr.c?utm_source=chatgpt.com "postgres/src/backend/storage/buffer/bufmgr.c at master · postgres/postgres · GitHub"))

这对理解 PG 18 的 IO 并发优化非常重要。

# 二十八、PG 18 的一个学习重点：异步/批量 Buffer IO

这点值得特别提醒你。

如果你以前看过 PG 14/15 的 Buffer Manager，不要直接把旧源码模型套到 PG 18。

PG 18 的 `bufmgr.c` 已经有：

```text
StartReadBuffer()
StartReadBuffers()
WaitReadBuffers()
AsyncReadBuffers()
```

这样的接口。([GitHub](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/bufmgr.c?utm_source=chatgpt.com "postgres/src/backend/storage/buffer/bufmgr.c at master · postgres/postgres · GitHub"))

所以现在的模型不只是：

```text
ReadBuffer()
    ↓
read()
    ↓
return
```

还可以：

```text
StartReadBuffers()
       │
       ├── Buffer A
       ├── Buffer B
       ├── Buffer C
       └── Buffer D
              │
              ▼
          async IO
              │
              ▼
       WaitReadBuffers()
```

这个是 PG 18 Shared Buffer 源码值得重点看的新变化之一。

# 三十、为什么 Buffer Mapping 和 Victim Selection 必须分开？

这是设计上很漂亮的一点。

### Buffer Mapping

解决：

> **这个 page 在哪里？**

```text
Tag → Buffer
```

### Replacement

解决：

> **我要把哪个 buffer 踢出去？**

```text
Buffer Pool → Victim
```

两个问题完全不同。

所以 PG 分成：

```text
buf_table.c
```

和：

```text
freelist.c
```

然后由：

```text
bufmgr.c
```

把它们串起来。

# 三十一、Shared Buffer 最重要的几个锁/并发点

源码往下读，你会碰到：

```text
BufferDesc spinlock
Buffer content lock
Buffer mapping lock
buffer_strategy_lock
```

它们解决的问题不一样。

简单理解：

### Buffer Descriptor state

保护：

```text
refcount
usage_count
dirty
valid
IO state
```

---

### Buffer Content Lock

保护：

```text
8KB page 内容
```

也就是说：

```text
Backend A
    │
    ▼
content lock
    │
    ▼
修改 page
```

防止其他 backend 同时修改同一 page 内容。

---

### Buffer Mapping Lock

保护：

```text
BufferTag → Buffer ID
```

也就是 hash table。

---

### Buffer Strategy Lock

保护：

```text
Clock Sweep / strategy state
```

PG 18 的 `StrategyGetBuffer()` 和 `ClockSweepTick()` 里可以看到这部分并发控制。([GitHub](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/freelist.c?utm_source=chatgpt.com "postgres/src/backend/storage/buffer/freelist.c at master · postgres/postgres · GitHub"))

# 三十二、所以“Buffer Lock”和“Page Lock”不是一回事

这以后一定会碰到。

```text
Buffer Descriptor Lock
        ↓
管理 buffer 状态

Content Lock
        ↓
保护 page 内容

Tuple Lock
        ↓
保护 tuple 并发修改

LWLock
        ↓
其他共享结构
```

不要把：

```text
Buffer Pin
Buffer Content Lock
Tuple Lock
```

混成一个东西。

# 三十三、还有一个很重要的东西：Private Refcount

这个是源码细节，但你现在开始看 Shared Buffer 源码就会碰到。

Backend 并不是每次：

```text
Pin
```

都直接频繁地修改共享内存中的 refcount。

PG 有：

```text
PrivateRefCount
```

机制。

可以粗略理解：

```text
Backend
   │
   ├── 私有 refcount
   │
   ▼
Shared Buffer Descriptor
   │
   └── 全局 refcount/state
```

目的是降低：

```text
atomic operation
cache line contention
```

这也是为什么你在源码里看到：

```c
GetPrivateRefCount()
PinBuffer()
UnpinBuffer()
```

会感觉比简单的：

```c
buf->refcount++
```

复杂很多。
