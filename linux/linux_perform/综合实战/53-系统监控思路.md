# 53 | 套路篇：系统监控的综合思路

原文：[time.geekbang.org/column/article/87980](https://time.geekbang.org/column/article/87980)

瓶颈来了才登录，现场往往已经没了。要靠监控把指标存下来，出事立刻告警。核心是**全面、可量化**的指标：系统资源 + 应用内部。

## USE 法（Brendan Gregg）

把资源压成三类，任一类过高就可能是瓶颈：

| | 含义 |
|--|------|
| Utilization 使用率 | 服务时间或容量占比，100% = 用尽 |
| Saturation 饱和度 | 繁忙程度，常看等待队列；100% = 接不了新请求。内存饱和看换页：`sar -B` |
| Errors 错误数 | 出错事件个数 |

硬件（CPU/内存/盘/网）和软件（fd、连接数、conntrack）都能套。fd/连接/conntrack 从 proc/sys 采。日志、进程占用、缓存量仍要采，只是当辅证。

应用侧更常用 **RED**：Rate（QPS）、Errors、Duration（延迟）。

## 监控系统五块

采集 → 存储（时序库）→ 查询处理 → 告警 → 可视化。常见 Zabbix / Nagios / Prometheus。

Prometheus：

- **采集**：Pull（目标出 HTTP）或 Push（经 Pushgateway）；服务发现适合 K8s
- **存储**：TSDB，按时间索引、追加写
- **查询**：PromQL
- **告警**：AlertManager，分组/抑制/静默减噪音
- **展示**：自带 Web UI 单调，配 Grafana

ARM / 虚拟机 / 容器都能监，前提是 exporter 支持。连环故障（swap → 堆积 → 句柄 → CPU）归因还是要懂原理，不是再加一张图就行。
