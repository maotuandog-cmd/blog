# 54 | 套路篇：应用监控的一般思路

原文：[time.geekbang.org/column/article/88423](https://time.geekbang.org/column/article/88423)

USE 管资源，管不了应用——CPU 很低照样能被锁或 RPC 拖死。应用黄金指标是 **请求数、错误率、响应时间**（RED）。

还要三层把瓶颈圈出来：

1. **进程资源**：CPU/内存/I/O/网，把系统瓶颈和进程对上
2. **应用之间调用**：频率、错误、延迟，看调用链哪一段
3. **内部核心逻辑**：关键步骤耗时和错误——必须应用自己暴露 metrics（框架常自带；Prometheus 有 Java client；php-fpm 开 status）

跨服务再用全链路跟踪（Zipkin / Jaeger / Pinpoint / SkyWalking）：入口生成 TraceID，一路带着。能画拓扑，一眼看到是 Redis 超时。链路看跨组件整体，日志看单组件细节，互补。

## 日志

指标是时段内的数，适合实时告警；日志是某时刻的字符串，要索引才能查。同样接口不同参数可能完全不同的坑，上下文在日志里。

经典 **ELK**：Logstash 采集预处理 → Elasticsearch 索引 → Kibana 看板。Logstash 吃资源，紧时用 **Fluentd / Filebeat**（EFK）。可加 Kafka，再用 Spark 滤错误日志做即时告警。
