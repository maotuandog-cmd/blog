# Shared Buffer 第一阶段只学 6 个东西

不要一上来就看 `bufmgr.c` 几千行。

先把这 6 个概念搞明白：

### 1. Buffer

一个 Shared Buffer 本质上就是：

```text
一个内存里的 PostgreSQL Page
```

例如：

```text
shared_buffers = 1GB
BLCKSZ = 8KB
```

大约：

```text
1GB / 8KB
≈ 131072 个 buffer
```

所以：

```text
Shared Buffers
+-------+-------+-------+-------+
| Buf 0 | Buf 1 | Buf 2 | ...   |
+-------+-------+-------+-------+
    │
    ▼
  8KB
  Page
```

---

# 2. Buffer Descriptor

这是 Shared Buffer 最核心的东西之一。

**Buffer ≠ Buffer Descriptor。**

可以先理解成：

```text
Buffer Descriptor
        │
        ├── 管理信息
        │
        └── 指向/对应一个真正的 8KB buffer
```

一个 descriptor 里面会有类似：

```text
BufferDesc
├── buffer id
├── tag
├── state
│    ├── refcount
│    ├── usage_count
│    ├── dirty
│    └── ...
└── ...
```

其中：

```text
tag
```

非常重要。

因为 PG 必须回答：

> **“磁盘上的哪个 page，现在在 Shared Buffer 的哪个位置？”**

---

# 3. Buffer Tag

例如：

```text
table = 16384
block = 100
fork = MAIN
```

可以形成一个 tag：

```text
+----------------------+
| RelFileNode           |
| ForkNumber            |
| BlockNumber           |
+----------------------+
```

所以：

```text
磁盘 page：

relation 16384
fork main
block 100
```

可能现在位于：

```text
Shared Buffer #5321
```

于是：

```text
                 Buffer Hash Table

(Relation 16384,
 MAIN,
 Block 100)
          │
          ▼
     Buffer #5321
          │
          ▼
       8KB page
```

这就是 Buffer Manager 最重要的职责之一：

> **磁盘 page ↔ shared buffer 的映射。**

---

# 4. Buffer Mapping Hash Table

接下来你一定会遇到：

```text
BufTable
```

以及：

```text
BufferMapping
```

PG 不能每次：

```text
SELECT page
```

都扫描：

```text
131072 个 buffer
```

否则性能会非常差。

所以有：

```text
Buffer Tag
    │
    ▼
Hash
    │
    ▼
Buffer Mapping
    │
    ▼
Buffer ID
```

例如：

```text
(table A, block 100)
          │
          ▼
       hash()
          │
          ▼
       bucket 123
          │
          ▼
       Buffer 5321
```

于是：

```text
ReadBuffer()
```

第一件重要的事情就是：

> **这个 page 已经在 shared buffer 里了吗？**

如果在：

```text
hit
```

如果不在：

```text
miss
```

---

# 5. PinCount

这个特别重要。

假设 backend A 正在使用：

```text
Buffer #100
```

它不能允许 Buffer Manager 把这个 buffer 随便淘汰掉。

所以：

```text
PinCount
```

可以理解成：

> **当前有多少人正在使用这个 buffer。**

例如：

```text
Backend A
    │
    ▼
Pin Buffer 100

Backend B
    │
    ▼
Pin Buffer 100
```

那么：

```text
PinCount = 2
```

只要：

```text
PinCount > 0
```

这个 buffer 通常就不能被 replacement。

---

# 6. UsageCount

这个和：

```text
LRU
```

有关，但 PostgreSQL 并不是简单 LRU。

PG 使用的是：

> **Clock Sweep**

核心会涉及：

```text
usage_count
```

粗略理解：

```text
Buffer A usage_count = 5
Buffer B usage_count = 1
Buffer C usage_count = 0
```

Clock Sweep 找 victim 时：

```text
usage_count > 0
    ↓
减一
    ↓
继续找
```

最终倾向于选择：

```text
usage_count = 0
```

且：

```text
pin_count = 0
```

的 buffer。

所以 Shared Buffer 的 replacement 算法你后面会看到：

```text
StrategyGetBuffer()
```

这是非常值得源码级研究的函数。

---

# 然后你就可以理解一次 SELECT

例如：

```sql
SELECT * FROM t WHERE id = 1;
```

最终需要：

```text
ReadBuffer()
```

大致：

```text
              ReadBuffer()
                   │
                   ▼
              Buffer Tag
                   │
                   ▼
            Buffer Hash Table
                   │
             ┌─────┴─────┐
             │           │
            HIT        MISS
             │           │
             ▼           ▼
        找到 Buffer    找 victim
                         │
                         ▼
                    如果 dirty
                         │
                         ▼
                    Flush Buffer
                         │
                         ▼
                    从磁盘 read
                         │
                         ▼
                    放入 Buffer
```

---

# 再然后你就能理解一次 UPDATE

这个和我们刚才讲的 WAL 就真正连接起来了。

```sql
UPDATE t SET a = 100 WHERE id = 1;
```

大致：

```text
找 page
   │
   ▼
ReadBuffer()
   │
   ▼
Shared Buffer
   │
   ▼
修改 page
   │
   ├──────────────┐
   │              │
   ▼              ▼
PageLSN         Dirty
   │              │
   │              ▼
   │        Buffer Manager
   │              │
   │              ▼
   │         以后再写磁盘
   │
   ▼
WAL
```

然后你之前学的 WAL Rule 就接上了：

```text
             UPDATE
                │
        ┌───────┴────────┐
        ▼                ▼
   修改 Buffer       生成 WAL
        │                │
        │                ▼
        │             LSN=500
        │                │
        ▼                ▼
PageLSN=500        WAL Flush=500
        │                │
        └───────┬────────┘
                ▼
        Buffer 可以安全落盘
```

这时候你会真正理解：

> **为什么 Buffer Manager 不能脱离 WAL 单独学习。**

# 所以答案是：可以，而且现在非常适合。

你现在的学习路径可以从：

```text
WAL
 │
 ├── PageLSN
 ├── FPI
 ├── WAL Buffer
 ├── Write
 └── Flush
       │
       ▼
========================
       │
       ▼
Shared Buffer
 │
 ├── Buffer
 ├── BufferDesc
 ├── Buffer Tag
 ├── BufTable
 ├── Pin
 ├── Dirty
 ├── UsageCount
 ├── Clock Sweep
 ├── ReadBuffer
 └── FlushBuffer
       │
       ▼
Storage Manager
       │
       ▼
     磁盘
```

**我建议下一步直接从 `ReadBuffer()` 开始。**

因为 `ReadBuffer()` 是 Shared Buffer 的入口之一。我们可以拿一个非常具体的例子：

```sql
SELECT * FROM test WHERE id = 1;
```

然后从：

```text
ReadBuffer()
 → Buffer Tag
 → BufTableLookup()
 → Buffer Hit / Miss
 → StrategyGetBuffer()
 → Pin
 → IO
 → MarkBufferValid()
```

逐个源码函数走一遍。

这比先讲一堆 Shared Buffer 理论更容易真正把源码吃进去。
