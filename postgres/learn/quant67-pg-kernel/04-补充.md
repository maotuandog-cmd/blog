可以。这次我不按文章目录讲，而是**沿着 PostgreSQL 内核真正执行的一条 UPDATE/INSERT 路径讲**，把你最关心的：

> **修改 Page → 生成 WAL Record → XLogInsert → WAL Buffer → WAL Writer → XLogWrite → OS → fsync → WAL Segment**

完整串起来。

你可以直接用客户端的**朗读/语音播放**来听下面这段。我会尽量按照“老师带着看源码”的方式讲。

---

# 🎙️ 第一部分：先把最重要的认知建立起来

我们假设执行：

```sql
INSERT INTO t VALUES (1, 'hello');
```

你脑子里不要先想 WAL Segment。

先想 PostgreSQL 内部其实同时存在两个东西：

```text
                    PostgreSQL
                         │
             ┌───────────┴───────────┐
             │                       │
         Data Page                WAL Record
             │                       │
       shared_buffers            WAL Buffer
             │                       │
       Dirty Page              WAL Segment
             │                       │
         table file              pg_wal
```

也就是说：

**数据本身走一条路。**

**数据的“修改描述”走另外一条路。**

比如一个 heap page：

```text
8KB Page
┌──────────────────────────────┐
│ Page Header                  │
│                              │
│ tuple 1                      │
│ tuple 2                      │
│ tuple 3  ← INSERT 修改这里   │
│                              │
└──────────────────────────────┘
```

执行 INSERT 后，这个 Page 首先被修改的是：

**shared_buffers 里的内存页面。**

不是磁盘上的 `.1`、`.2`、`.3` 文件。

这时候这个 Buffer 被标记成：

**dirty buffer。**

与此同时，PostgreSQL 必须生成一条 WAL：

> “我刚才对哪个 page 做了什么修改。”

这两件事必须联系起来。

而这个联系最重要的东西之一就是：

**LSN。**

---

# 🎙️ 第二部分：LSN 到底是什么？

LSN：

**Log Sequence Number。**

你不要把它简单理解成一个普通整数。

它实际上表示：

> **WAL 日志流中的一个位置。**

比如：

```text
WAL
─────────────────────────────────────────────>

1000       1100       1200       1300
│          │          │          │
Record A   Record B   Record C   Record D
```

如果某个 Data Page：

```text
pd_lsn = 1200
```

它的意思可以粗略理解成：

> 这个 Page 已经反映到了 WAL 的 1200 这个位置。

所以：

**Page 和 WAL 之间，是通过 LSN 建立关系的。**

这非常重要。

---

# 🎙️ 第三部分：真正修改 Page 的时候发生什么？

我们继续：

```sql
INSERT INTO t VALUES (1, 'hello');
```

执行到 heap access method。

最终它会找到：

```text
Buffer
   ↓
Page
```

然后修改 Page。

比如：

```text
原来：

┌────────────────────┐
│ tuple A            │
│ tuple B            │
│                    │
└────────────────────┘


INSERT

↓


现在：

┌────────────────────┐
│ tuple A            │
│ tuple B            │
│ tuple C            │
└────────────────────┘
```

此时 PostgreSQL 会：

```text
Page 修改
   ↓
Page Mark Dirty
```

但是注意：

**现在还不能把这个 Page 随便刷到磁盘。**

因为 WAL 还没有安全。

这就是：

> **Write Ahead。**

所以 PostgreSQL 内部必须保证：

```text
WAL LSN 对应的数据
        ↓
必须先于 Data Page 落盘
```

---

# 🎙️ 第四部分：那 WAL Record 是怎么构造出来的？

这就是你问的重点。

PG 源码里面有：

```c
XLogBeginInsert();
```

然后：

```c
XLogRegisterBuffer();
```

然后：

```c
XLogRegisterData();
```

最后：

```c
XLogInsert();
```

这几个函数你一定要建立概念。

源码里的 `xloginsert.c` 明确说明：

> 构造 WAL Record 从 `XLogBeginInsert()` 开始，然后通过一系列 `XLogRegister*()` 注册数据，最后由 `XLogRecordAssemble()` 组装。 ([GitHub](https://github.com/postgres/postgres/blob/master/src/backend/access/transam/xloginsert.c?utm_source=chatgpt.com "postgres/src/backend/access/transam/xloginsert.c at master · postgres/postgres · GitHub"))

所以我们可以想象：

```text
XLogBeginInsert()
       │
       ▼
“我要开始构造一条 WAL”
       │
       ▼
XLogRegisterBuffer()
       │
       ▼
“我要修改这个 Page”
       │
       ▼
XLogRegisterData()
       │
       ▼
“这是具体修改内容”
       │
       ▼
XLogInsert()
       │
       ▼
真正进入 WAL Buffer
```

---

# 🎙️ 第五部分：XLogRegisterBuffer 到底注册了什么？

假设：

```text
heap page
relfilenode = 16384
fork = MAIN
block number = 100
```

那么 WAL 必须知道：

> 我要修改的是哪个页面？

所以 WAL Record 里面会带：

```text
Block 0

Relation
Fork
Block Number
```

然后还有：

> 这个页面到底修改了什么？

例如：

```text
INSERT tuple
offset = 5
tuple data = ...
```

所以你可以把一条 WAL Record 想象成：

```text
┌──────────────────────────────┐
│ XLogRecord Header             │
├──────────────────────────────┤
│ Block Header                  │
│ relation                      │
│ fork                          │
│ block number                  │
├──────────────────────────────┤
│ Block Data                    │
│                               │
│ INSERT 的具体信息             │
├──────────────────────────────┤
│ Main Data                     │
└──────────────────────────────┘
```

实际结构比这个复杂，但你学习源码的时候先这么理解。

---

# 🎙️ 第六部分：XLogRecord Header

一条 WAL Record 最前面有：

```c
XLogRecord
```

里面非常重要的字段：

```text
xl_tot_len
xl_xid
xl_prev
xl_info
xl_rmid
xl_crc
```

我们一个一个说。

---

## xl_tot_len

就是：

> 这一整条 WAL Record 有多长。

比如：

```text
120 bytes
```

那么恢复的时候读取 WAL：

```text
读取 header
   ↓
知道 record 长度
   ↓
读取完整 record
```

---

## xl_xid

谁产生了这个 WAL。

也就是：

> Transaction ID。

---

## xl_prev

这个非常有意思。

它指向：

> 前一条 WAL Record。

所以 WAL Record 在逻辑上形成：

```text
Record A
   ↓
Record B
   ↓
Record C
   ↓
Record D
```

恢复的时候可以按照 WAL 顺序不断向前推进。

---

## xl_rmid

这个非常关键。

它告诉 PostgreSQL：

> **这条 WAL 应该交给哪个 Resource Manager。**

例如：

```text
RM_HEAP
RM_BTREE
RM_XACT
RM_XLOG
```

假设：

```text
xl_rmid = RM_HEAP
```

Recovery 看到之后：

```text
WAL Record
    ↓
RM_HEAP
    ↓
heap redo
```

如果：

```text
RM_BTREE
```

那就：

```text
B-tree redo
```

所以：

> **RMID 决定“谁负责解释这条 WAL”。**

文章里的源码也列出了例如 `RM_HEAP_ID`、`RM_BTREE_ID` 等 Resource Manager。([土法炼钢 · 系统与基础设施](https://quant67.com/post/db/postgresql-kernel/04-wal-internals/04-wal-internals.html "〖PG 内核〗WAL 内部机制：从事务提交到磁盘刷写 | 土法炼钢 · 系统与基础设施"))

---

# 🎙️ 第七部分：CRC 是干什么的？

还有：

```text
xl_crc
```

也就是：

**CRC32C。**

为什么需要它？

因为 WAL 是数据库恢复的生命线。

如果：

```text
WAL Record
```

在写磁盘、存储、传输过程中损坏：

恢复的时候绝不能把错误数据当成正确 WAL。

所以：

```text
写 WAL
   ↓
计算 CRC
   ↓
写入
```

恢复：

```text
读 WAL
   ↓
重新计算 CRC
   ↓
比较
   ↓
正确？
   │
   ├── YES → 继续恢复
   │
   └── NO  → 报错
```

所以 WAL Record 自身带校验。

---

# 🎙️ 第八部分：然后是 Block Header

这也是非常重要的一层。

因为：

**一条 WAL Record 不一定只修改一个 Page。**

例如一次操作可能同时修改：

```text
Heap Page
+
Index Page
```

所以一条 WAL Record 里面可以有：

```text
Block 0
Block 1
Block 2
...
```

比如：

```text
WAL Record
│
├── Block 0
│     └── heap page
│
├── Block 1
│     └── index page
│
└── main data
```

这就是为什么 WAL Record 不是简单的：

```text
header + data
```

而是：

```text
header
+
多个 block reference
+
block data
+
main data
```

---

# 🎙️ 第九部分：Full Page Write，也就是 FPW

这里一定要理解。

假设：

```text
Checkpoint
   ↓
Page A
   ↓
第一次修改
```

这时候 PostgreSQL 可能会把：

**整个 Page 的镜像**

放进 WAL。

也就是：

```text
WAL Record

Header
+
Block Header
+
8KB Full Page Image
```

为什么？

因为担心：

```text
Data Page 8KB
```

写磁盘的时候突然断电。

可能出现：

```text
前 4KB：新
后 4KB：旧
```

这就是：

**Page Tear。**

如果 WAL 里面有完整 Page：

恢复的时候：

```text
WAL
 ↓
Full Page Image
 ↓
直接恢复整个 Page
```

就不需要相信磁盘上那个可能已经撕裂的 Page。

源码里的 `XLogRegisterBuffer()` 也明确支持 `REGBUF_FORCE_IMAGE`、`REGBUF_NO_IMAGE` 等标志；PG 的 WAL 构造代码会根据这些信息决定是否包含 page image。([Doxygen PostgreSQL](https://doxygen.postgresql.org/xloginsert_8h_source.html?utm_source=chatgpt.com "PostgreSQL Source Code: src/include/access/xloginsert.h Source File"))

---

# 🎙️ 第十部分：现在进入最核心的 XLogInsert

好了。

现在 Page 已经改了。

WAL 信息也已经准备好了。

调用：

```c
XLogInsert()
```

真正进入：

```text
XLogInsertRecord()
```

这个时候发生什么？

可以先记：

```text
XLogInsert
     ↓
构造 Record
     ↓
Reserve WAL Space
     ↓
得到 LSN
     ↓
Copy Record
     ↓
WAL Buffer
```

文章给出的源码路径也是：

```text
XLogInsert()
   ↓
XLogInsertRecord()
   ↓
ReserveXLogInsertLocation()
   ↓
CopyXLogRecordToWAL()
```

([土法炼钢 · 系统与基础设施](https://quant67.com/post/db/postgresql-kernel/04-wal-internals/04-wal-internals.html "〖PG 内核〗WAL 内部机制：从事务提交到磁盘刷写 | 土法炼钢 · 系统与基础设施"))

---

# 🎙️ 第十一部分：ReserveXLogInsertLocation

这里是理解 PostgreSQL WAL 并发写入的关键。

假设现在有：

```text
Backend 1
Backend 2
Backend 3
Backend 4
```

同时执行：

```sql
INSERT
UPDATE
DELETE
```

那么大家都会生成 WAL。

如果 PostgreSQL 只有一个全局锁：

```text
             WAL
              ↑
      ┌───────┼───────┐
      │       │       │
     B1      B2      B3
```

那会产生巨大竞争。

所以 PostgreSQL 有：

**WALInsertLock。**

可以粗略理解成：

```text
WALInsertLock 0
WALInsertLock 1
WALInsertLock 2
...
```

让多个 Backend 能并行进行 WAL insertion。

PG 源码中 WAL insertion 使用多个 insertion lock slot 来支持并发；文章按 PG17 源码分析为 8 个 slot。([土法炼钢 · 系统与基础设施](https://quant67.com/post/db/postgresql-kernel/04-wal-internals/04-wal-internals.html "〖PG 内核〗WAL 内部机制：从事务提交到磁盘刷写 | 土法炼钢 · 系统与基础设施"))

---

# 🎙️ 第十二部分：最重要的一个概念——Reserve

注意：

**Reserve 不是 Copy。**

这是很多源码初学者最容易搞错的地方。

假设：

```text
WAL Buffer
```

现在：

```text
0 ────────────────────────────── 1MB
```

Backend 1 要写：

```text
100 bytes
```

Backend 2 要写：

```text
200 bytes
```

可能先做：

```text
B1 reserve:
[0 -------- 100]

B2 reserve:
[100 ---------------- 300]
```

也就是：

**先把 WAL 空间划给不同 Backend。**

得到：

```text
LSN range
```

然后 Backend 再把自己的 Record 拷进去。

---

# 🎙️ 第十三部分：为什么 Reserve 和 Copy 要分开？

因为并发。

比如：

```text
B1 reserve 0-100
B2 reserve 100-300
B3 reserve 300-500
```

然后：

```text
B1 正在 copy
B2 已经 copy 完
B3 还没 copy
```

此时 WAL Writer 不能因为 B2 完成，就直接把：

```text
100-300
```

写出去。

因为：

```text
0-100
```

还没有完成。

所以 WAL Writer 必须遵守：

> **WAL 必须按照 LSN 连续推进。**

不能出现：

```text
已经写：
100-300

但是：
0-100
还没完成
```

否则磁盘上的 WAL 就出现空洞。

所以 PostgreSQL 内部有一个非常重要的概念：

**所有 insertion slot 必须保证 WAL 的连续性。**

---

# 🎙️ 第十四部分：Record Copy 到 WAL Buffer

Reserve 完成以后：

```text
CopyXLogRecordToWAL()
```

真正把内容复制到：

**WAL Buffer。**

于是：

```text
Backend
   │
   │ memcpy
   ▼
WAL Buffer
```

现在注意：

> **此时 WAL 只是进入 PostgreSQL 的共享内存。**

还没有持久化。

这个区别极其重要。

---

# 🎙️ 第十五部分：WAL Buffer 到底是什么？

你可以把它理解成：

> PostgreSQL 在 shared memory 中维护的一片 WAL 环形缓冲区。

类似：

```text
WAL Buffer

┌─────────────────────────────────────────────┐
│ Record A │ Record B │ Record C │ free ... │
└─────────────────────────────────────────────┘
                         ↑
                       insert
```

不断往前走。

最终：

```text
insert position
```

不断增长。

但是 Buffer 空间有限。

所以会不断发生：

```text
旧 WAL
 ↓
写出去
 ↓
释放 WAL Buffer 空间
 ↓
继续写新的 WAL
```

---

# 🎙️ 第十六部分：现在 WAL Writer 登场

这里就进入你特别问的：

**flush writer / WAL writer。**

后台有一个：

**WAL Writer Process。**

它不是负责产生 WAL 的。

这是非常重要的区别。

---

## Backend 做什么？

Backend：

```text
业务 SQL
 ↓
修改 Page
 ↓
生成 WAL
 ↓
XLogInsert
 ↓
写 WAL Buffer
```

---

## WAL Writer 做什么？

WAL Writer：

```text
WAL Buffer
 ↓
发现有 WAL 可以写
 ↓
XLogWrite()
 ↓
WAL Segment
```

也就是说：

> **Backend 主要负责 WAL generation/insertion。**

> **WAL Writer 主要负责后台写 WAL。**

官方文档也明确区分了 `XLogInsertRecord`、`XLogFlush`、`XLogWrite`：`XLogInsertRecord` 把 WAL Record 放入 shared WAL buffers，而 `XLogWrite` 负责把 WAL Buffer 写出去。([PostgreSQL](https://www.postgresql.org/docs/17/wal-configuration.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 17: 28.5. WAL Configuration"))

---

# 🎙️ 第十七部分：但是这里有一个大坑

很多人理解成：

```text
Backend
 ↓
WAL Buffer
 ↓
WAL Writer
 ↓
Disk
 ↓
COMMIT
```

**不完全对。**

因为：

**COMMIT 不能完全依赖 WAL Writer。**

假设：

```text
Backend
 ↓
INSERT
 ↓
WAL Buffer
```

然后：

```text
COMMIT
```

用户期待：

> COMMIT 成功以后，即使机器断电，数据也不能丢。

那怎么办？

如果 WAL Writer 还没刷：

```text
WAL Buffer
```

怎么办？

所以：

**同步提交的时候，Backend 自己可能触发 XLogFlush。**

也就是说：

```text
Backend
   │
   ├──────────────→ WAL Buffer
   │
   │
   └── COMMIT
          │
          ▼
      XLogFlush()
          │
          ▼
       XLogWrite()
          │
          ▼
        fsync
```

这就是为什么：

> **COMMIT 延迟和 WAL 存储延迟高度相关。**

---

# 🎙️ 第十八部分：XLogFlush 到底在干什么？

假设：

```text
当前事务最后一条 WAL：

LSN = 50000
```

COMMIT 必须保证：

```text
WAL flushed >= 50000
```

所以：

```c
XLogFlush(50000);
```

可以理解成：

> “请你保证 WAL 至少安全到 50000。”

然后 PostgreSQL 看：

```text
当前已经 flush 到：

45000
```

那么：

```text
45000 → 50000
```

这一段必须写出去。

---

# 🎙️ 第十九部分：XLogWrite

接下来：

```text
XLogFlush
    ↓
XLogWrite
```

`XLogWrite()` 才是真正负责把 WAL Buffer 中的数据写向 WAL 文件的关键函数之一。官方文档明确指出，WAL Writer、`XLogFlush`，以及 WAL Buffer 空间不足时的 `XLogInsertRecord` 都可能调用 `XLogWrite`。([PostgreSQL](https://www.postgresql.org/docs/17/wal-configuration.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 17: 28.5. WAL Configuration"))

所以：

```text
WAL Buffer
     │
     ▼
XLogWrite()
     │
     ▼
write()
     │
     ▼
OS kernel cache
```

注意：

**write 到 OS cache ≠ 数据已经真正落到稳定存储。**

这一步必须和后面的 sync 分开理解。

---

# 🎙️ 第二十部分：fsync 到底发生在哪？

这取决于：

```text
wal_sync_method
```

常见的：

```text
fdatasync
fsync
open_datasync
open_sync
```

例如：

```text
XLogWrite()
   ↓
write()
   ↓
Kernel Page Cache
   ↓
issue_xlog_fsync()
   ↓
fdatasync/fsync
   ↓
Storage
```

官方文档也明确说明：使用 `fdatasync`、`fsync` 等方式时，`XLogWrite` 先把 WAL 写到 kernel cache，然后由 `issue_xlog_fsync` 做同步；`open_datasync` / `open_sync` 的语义有所不同。([PostgreSQL](https://www.postgresql.org/docs/17/wal-configuration.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 17: 28.5. WAL Configuration"))

所以你一定要把这几个概念拆开：

```text
memcpy
   ↓
WAL Buffer

write()
   ↓
Kernel Page Cache

fsync/fdatasync
   ↓
要求 OS/存储设备完成持久化
```

---

# 🎙️ 第二十一部分：所以一次 COMMIT 到底是什么过程？

我们现在完整走一次。

假设：

```sql
BEGIN;

INSERT INTO t VALUES (1, 'hello');

COMMIT;
```

真正脑补：

```text
① 找到 Heap Page
       ↓
② Pin Buffer
       ↓
③ Lock Buffer
       ↓
④ 修改 Page
       ↓
⑤ Mark Buffer Dirty
       ↓
⑥ XLogBeginInsert()
       ↓
⑦ XLogRegisterBuffer()
       ↓
⑧ XLogRegisterData()
       ↓
⑨ XLogInsert()
       ↓
⑩ XLogInsertRecord()
       ↓
⑪ ReserveXLogInsertLocation()
       ↓
⑫ 得到 WAL LSN
       ↓
⑬ CopyXLogRecordToWAL()
       ↓
⑭ WAL Buffer
       ↓
⑮ PageSetLSN()
       ↓
⑯ 事务继续执行
       ↓
⑰ COMMIT
       ↓
⑱ 生成 COMMIT WAL Record
       ↓
⑲ XLogInsert()
       ↓
⑳ XLogFlush()
       ↓
㉑ XLogWrite()
       ↓
㉒ write()
       ↓
㉓ fsync/fdatasync
       ↓
㉔ WAL 持久化
       ↓
㉕ COMMIT 返回
```

**这一条链你一定要吃透。**

---

# 🎙️ 第二十二部分：那 Data Page 呢？

注意！

刚才：

```text
WAL 已经落盘
```

并不意味着：

```text
Data Page 已经落盘
```

完全可能：

```text
WAL
████████████████████████
       已经持久化

Data Page
████████
       还在 shared_buffers
```

这是 PostgreSQL WAL 的核心设计。

因为：

> **WAL 已经安全了，所以 Data Page 可以晚一点写。**

---

# 🎙️ 第二十三部分：那 Data Page 什么时候写？

主要由：

```text
Background Writer
Checkpointer
Buffer Manager
```

等机制参与。

最终：

```text
Dirty Page
   ↓
write data file
```

但 PostgreSQL 有一个铁律：

```text
Data Page LSN = X
```

那么：

```text
WAL flush position
```

必须至少：

```text
>= X
```

也就是：

> **数据页不能跑到 WAL 前面。**

这就是：

# Write Ahead

真正的含义。

---

# 🎙️ 第二十四部分：为什么 Page 上要有 pd_lsn？

现在就知道答案了。

假设：

```text
Page A

pd_lsn = 1000
```

表示：

> 这个 Page 已经应用到 WAL 1000。

恢复的时候：

```text
WAL 900
```

发现：

```text
Page pd_lsn = 1000
```

那么：

> 900 已经反映过了。

所以不能再重放。

而如果：

```text
WAL 1200
```

那么：

```text
1200 > 1000
```

说明：

> Page 还没应用到 1200。

所以需要 REDO。

这就是：

```text
WAL LSN
    ↓
Page pd_lsn
    ↓
决定是否需要 redo
```

# 🎙️ 第二十五部分：最后讲一个非常容易混淆的东西

你现在可能会问：

> “既然有 WAL Writer，为什么还需要 XLogFlush？”

答案就是：

**WAL Writer 是后台异步写。**

而：

**XLogFlush 是同步提交路径上的强制推进。**

可以这么理解：

```text
                 WAL Buffer
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
      WAL Writer             Backend
      后台异步                 COMMIT
          │                     │
          │                     ▼
          │                 XLogFlush
          │                     │
          └──────────┬──────────┘
                     ▼
                  XLogWrite
                     │
                     ▼
                 WAL Segment
                     │
                     ▼
               fsync/fdatasync
                     │
                     ▼
                  Storage
```

所以生产环境里：

> **WAL Writer 不应该被理解成“COMMIT 的唯一写 WAL 的人”。**

这是非常重要的。

# 🎙️ 第二十六部分：把 WAL 的物理结构再串一遍

你可以想象磁盘：

```text
$PGDATA/pg_wal/

000000010000000000000001
000000010000000000000002
000000010000000000000003
...
```

这些就是：

**WAL Segment。**

Segment 是 WAL 的文件组织。

而文件里面：

```text
Segment
│
├── WAL Page
│
├── WAL Page
│
├── WAL Page
│
├── WAL Page
│
└── ...
```

里面存：

```text
WAL Record
WAL Record
WAL Record
WAL Record
...
```

所以层级关系：

```text
WAL Stream
    │
    ├── Segment
    │      │
    │      ├── WAL Page
    │      │      ├── Record
    │      │      ├── Record
    │      │      └── Record
    │      │
    │      └── ...
    │
    └── Segment
```

注意：

**WAL Record ≠ WAL Page ≠ WAL Segment。**

这三个一定不要混。

# 🎙️ 最后，用一个真实的“时序动画”结束

你可以把整个 PostgreSQL WAL 想成下面这个动画：

```text
T1：Backend 修改 Page

Backend
   │
   └──────► shared_buffers
                 │
                 ▼
             Dirty Page
```

然后：

```text
T2：构造 WAL

Backend
   │
   ├── XLogBeginInsert
   ├── XLogRegisterBuffer
   ├── XLogRegisterData
   │
   ▼
XLogInsert
```

然后：

```text
T3：Reserve

WALInsertLock
      │
      ▼
Reserve WAL Space
      │
      ▼
得到 LSN
```

然后：

```text
T4：Copy

WAL Record
    │
    ▼
WAL Buffer
```

这时候：

```text
Page：
内存里已经修改

WAL：
内存里也已经存在

Disk：
两边都可能还没真正落盘
```

然后：

```text
T5：COMMIT

COMMIT
   │
   ▼
XLogFlush
   │
   ▼
XLogWrite
   │
   ▼
write()
   │
   ▼
Kernel
   │
   ▼
fsync()
   │
   ▼
Storage
```

于是：

```text
WAL
████████████████████
       安全
```

然后：

```text
COMMIT
   ↓
返回客户端
```

但是：

```text
Data Page
仍然可能：

shared_buffers
```

过一会儿：

```text
Checkpoint
    │
    ▼
Dirty Page
    │
    ▼
Data File
    │
    ▼
Storage
```

于是：

```text
WAL：已经安全
Data Page：也已经安全
```

# 🎙️ 你现在最应该记住的 10 个词

如果你准备继续啃 PostgreSQL WAL 源码，我建议先把这 10 个词完全搞懂：

```text
1. LSN
2. XLogRecord
3. Block Header
4. RMGR
5. FPW
6. XLogInsert
7. WALInsertLock
8. WAL Buffer
9. XLogWrite
10. XLogFlush
```

其中最关键的一条关系是：

```text
修改 Page
   ↓
生成 WAL Record
   ↓
XLogInsert
   ↓
Reserve WAL LSN
   ↓
Copy 到 WAL Buffer
   ↓
XLogFlush / WAL Writer
   ↓
XLogWrite
   ↓
write
   ↓
fsync/fdatasync
   ↓
WAL 持久化
```

而**下一层**就是你真正想深入 PostgreSQL 内核的话最值得看的：

> **`XLogInsertRecord()` → `ReserveXLogInsertLocation()` → `CopyXLogRecordToWAL()` → `AdvanceXLInsertBuffer()` → `XLogWrite()`**

这几个函数串起来以后，你会真正明白 **WAL Buffer 为什么是环形的、WAL Page 为什么有 8KB、跨 WAL Page/Segment 时怎么处理、多个 Backend 同时写 WAL 为什么不会乱序，以及 WAL Writer 到底怎么判断“哪些 WAL 可以安全写出去”。**

这些内容在你给的文章和 PG 源码里都有对应实现；官方文档也明确指出 `XLogInsertRecord` 负责进入 WAL buffers，而 `XLogWrite`/`issue_xlog_fsync` 负责写出和同步。([PostgreSQL](https://www.postgresql.org/docs/17/wal-configuration.html?utm_source=chatgpt.com "PostgreSQL: Documentation: 17: 28.5. WAL Configuration"))

**如果你要继续“语音听源码课”，下一节我建议就专门讲这几个函数，拿一条假设 `INSERT` 的 WAL Record，按 `LSN = 0/100/200...` 画出 WAL Buffer 的内存布局，一格一格讲 `Reserve → Copy → Flush → Write → Sync`。那一节会比现在这节更接近真正读 PG 内核源码。**
