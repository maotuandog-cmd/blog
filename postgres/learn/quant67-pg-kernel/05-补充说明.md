
可以。你这份材料其实已经把 PostgreSQL 18.6 的 Buffer Manager 主线梳理得比较完整了。**如果把“一个 buffer 是如何被管理的”抽象出来，核心不是“8KB 内存块”，而是一个“槽位（slot）+ 状态机 + 引用计数 + 淘汰策略 + I/O 状态”的生命周期。**

# 〇、先纠正一句：unpin 不会把 slot 丢回 freelist

实现正文：[[05-buffer-manager]] 第 5 节。这里专门拆开一个常见误区——把 Buffer Pool 想成「slot 串在 freelist 上，用完再挂回去」。

可以先接受这张总图：

```text
                shared_buffers
        ┌──────────────────────────┐
        │ Buffer 0 │ Buffer 1 │ ...│
        │  slot    │  slot    │     │
        └──────────────────────────┘
             ↑
             │ Buffer Descriptor（state 里塞着 refcount / usagecount / flags）
             │
       ┌─────┴──────┐
       │ refcount   │  现在有没有人 pin
       │ usagecount │  最近热不热（clock 消耗它）
       │ flags      │  DIRTY / VALID / TAG_VALID …
       └────────────┘

Freelist（常常是空的）
   ↓
[从未用过 / 刚失效的 Buffer] → […] → […]
```

整体思路对：**descriptor + freelist/clock-sweep**。要改的是 freelist 在生命周期里的位置，以及 clock 减的到底是哪一个计数。

## 0.1 「slot 串在 freelist」——启动时对，跑热了不对

每个 slot 对应一个固定的 `buf_id` / `BufferDesc`。**只有「还没装过有效页」或「已经从哈希里摘掉、可以立刻拿来用」的槽才会进 freelist。**

启动：`BufferManagerShmemInit` 把 16384 个空槽全串进 `firstFreeBuffer`。第一次缺页：`StrategyGetBuffer` 先偷看 freelist，有货就弹出。

```text
需要 Page X
   ↓
BufTableLookup
   ↓
找到了？
 ┌───┴───┐
 Yes     No
  ↓       ↓
Pin 直接用   StrategyGetBuffer
                ↓
             Freelist 非空？── Yes → 弹出一个 slot
                ↓ No
             Clock Sweep 找 victim
                ↓
             （若 dirty：FlushBuffer）
                ↓
             这个 slot 装 Page X
```

**用完不会重新挂回 freelist。** `UnpinBuffer` 只把共享 `refcount` −1。页还在槽里、哈希里还有 tag，下次命中还是同一格。真正 `StrategyFreeBuffer` 的场合很少：DROP/TRUNCATE 失效、`BufferAlloc` 抢槽失败把牺牲页还回去、极少数 VACUUM 旧路径。池子用热之后 `firstFreeBuffer` 通常是 −1，日常全靠 clock。

Freelist 是 **「还没进入缓存生命周期的空槽快速通道」**，不是整个 Buffer Pool 的队列。

## 0.2 `refcount` 和 `usagecount` 是两回事

「clock 一轮一轮减少引用次数」这句话要改成：

> **Clock sweep 减的是 `usagecount`，不是 `refcount`。**

```text
refcount（state 低 18 位）
    ↓
“现在还有没有人 pin 着这个 buffer？”
（跨后端的共享计数；本后端另有 PrivateRefCountArray[8]）

usagecount（接着 4 位，上限 BM_MAX_USAGE_COUNT = 5）
    ↓
“这个 buffer 最近有没有被 pin 过？”
```

```text
Buffer A
refcount   = 0
usagecount = 5
```

没人 pin，但最近很热。**不能因为 refcount=0 就立刻淘汰。**

谁把 usage 加回去：默认策略的 `PinBuffer` 在**第一次**共享 pin 时，usage 不到 5 就 +1。同一后端再 pin 只加私有计数，usage 不动。Ring（`BAS_BULKREAD` / `BAS_VACUUM`）最多把 usage 抬到 1，避免大扫描把整池钉热。

## 0.3 Clock Sweep 扫的是数组，不是链表

物理上不是 `B0 → B1 → B2` 一条链，而是 `nextVictimBuffer` 单调加、对 `NBuffers` 取模（`ClockSweepTick`）。脑图画成环更顺：

```text
                  Clock Hand
                      ↓
B0   B1   B2   B3   B4   B5   …  （下标 0 .. NBuffers-1）
```

假设：

```text
B0: refcount=1
B1: refcount=0 usagecount=3
B2: refcount=0 usagecount=0
B3: refcount=0 usagecount=5
B4: refcount=0 usagecount=1
```

扫过去（`freelist.c` 的 `StrategyGetBuffer`）：

```text
B0  refcount > 0          → 跳过（连 usage 都不减）
B1  ref=0, usage=3        → usage-- 变成 2，继续
B2  ref=0, usage=0        → victim，带着 header 锁返回
```

完整规则：

> Clock 跳过正在 pin 的 buffer；没 pin 但 `usagecount > 0` 的把 usage −1；找到 `refcount=0 && usagecount=0` 才当 victim。usage=5 的热页最多要绕 **6 圈**（`BM_MAX_USAGE_COUNT+1`）才肯动。整圈都 pin 着 → `ERROR: no unpinned buffers available`。

有 ring 时 `StrategyGetBuffer` **先**问私有环，环给不出再 freelist，再 clock。这是第三条路，别把所有缺页都画进全局 clock。

## 0.4 找到 victim 之后才换页

Clock 只选出「可以动的槽」。`GetVictimBuffer` 还要：立刻 pin 住（防别人再 pin）、看 `BM_DIRTY`。

```text
Buffer 42 里原来是 Page A
refcount=0  usagecount=0
        │
        ▼
dirty？ ── Yes → 条件拿 content_lock SHARED
        │              ↓
        │         FlushBuffer（永久页先 XLogFlush(pd_lsn)）
        │              ↓
        No        从哈希摘掉 Page A 的 tag
        │              │
        └──────────────┘
                ↓
        Buffer 42 装 Page B（此时还没有 BM_VALID，读盘在后面）
```

脏页刷不掉（content lock 拿不到、ring 策略拒绝会被 WAL 卡住）就 unpin 再换一个，不是死等。

## 0.5 用完只 unpin，槽留在池里

不要记成「用完 → slot → freelist」。更接近：

```text
Buffer Slot
    │
  pin / 使用     refcount > 0     Clock 绝对跳过
    │
  unpin          refcount = 0
    │
  留在 Buffer Pool + 哈希里     ← 下次同 tag 直接命中
    │
  Clock Sweep    usagecount--
    │
  usagecount = 0
    │
  成为 victim →（dirty 则写回）→ 被新 Page 覆盖
```

一句话版：

> `shared_buffers` 是很多 buffer slot，每个 slot 有 Buffer Descriptor。空闲槽走 freelist 快速拿；缺页且 freelist 空时 Clock Sweep 找 victim。Clock 看两件事：正在 pin 的跳过，没 pin 的逐渐降低 `usagecount`，`refcount=0 && usagecount=0` 才覆盖。脏页先写回。**page 用完通常只是 unpin，不会立刻回 freelist。refcount 管现在有没有人在用，usagecount 管最近是不是经常用，Clock 消耗的是 usagecount。**

后面第 8、9、14、15 节是同一套机制的展开；第 5 节 ring、第 11 节 `FlushBuffer` 接 WAL。

# 一、先建立一个最重要的认识：Buffer ≠ Page

这是理解整个 Buffer Manager 的第一关。

一个 PostgreSQL Buffer 实际上可以理解成：

```text
Buffer ID
   │
   ├── BufferDesc
   │      ├── BufferTag
   │      ├── state
   │      ├── refcount
   │      ├── usage_count
   │      ├── flags
   │      └── content_lock
   │
   └── BufferBlock
          └── 8KB Page
```

所以：

**Buffer 是“管理对象”，Page 是“数据对象”。**

例如：

```text
buffer 123
   │
   ├── desc[122]
   │      tag = (1663, 16384, 16385, MAIN, 100)
   │      refcount = 2
   │      usage_count = 3
   │      VALID = 1
   │      DIRTY = 1
   │
   └── block[122]
          8KB
          ┌────────────────────┐
          │ Page Header        │
          │ ItemId[]           │
          │ tuple              │
          │ tuple              │
          └────────────────────┘
```

文件明确把这三层拆开了：`BufferDescriptors` 管身份/状态/锁，`BufferBlocks` 是真正的 8KB 页，哈希表负责 `tag → buf_id`。

# 二、一个 Buffer 从出生到死亡，到底经历什么？

我建议你把生命周期记成下面这条线：

```text
                   PostgreSQL 启动
                         │
                         ▼
                 BufferManagerShmemInit
                         │
                         ▼
              ┌─────────────────────┐
              │     空 Buffer 槽     │
              │ VALID=0             │
              │ TAG_VALID=0         │
              │ DIRTY=0             │
              │ refcount=0          │
              └──────────┬──────────┘
                         │
                         │ 需要读取某个磁盘块
                         ▼
                  BufferAlloc(tag)
                         │
                 ┌───────┴───────┐
                 │               │
               命中              未命中
                 │               │
                 ▼               ▼
             PinBuffer       GetVictimBuffer
                 │               │
                 │         找一个 refcount=0
                 │               │
                 │         ┌─────┴─────┐
                 │         │           │
                 │       clean        dirty
                 │         │           │
                 │         │       FlushBuffer
                 │         │           │
                 │         └─────┬─────┘
                 │               │
                 │         删除旧 tag
                 │               │
                 │               ▼
                 │          写入新 tag
                 │               │
                 └───────┬───────┘
                         │
                         ▼
                    StartBufferIO
                         │
                         ▼
                       读盘
                         │
                         ▼
                    BM_VALID = 1
                         │
                         ▼
                    用户访问 Page
                         │
                  ┌──────┴──────┐
                  │             │
                只读            修改
                  │             │

                  │             │
                  ▼             ▼
                 UnpinBuffer
                       │
                       ▼
               refcount → 0
                       │
                       ▼
                等待未来淘汰
                       │
                 ┌─────┴─────┐
                 │           │
              再次命中      Clock 选中
                 │           │
                 │           ▼
                 │       FlushBuffer
                 │           │
                 │           ▼
                 │        槽重用
                 └───────────┘
```

这就是一个 Buffer 的完整生命。

# 三、第一步：Buffer 槽是怎么创建出来的？

PostgreSQL 启动的时候，并不是：

> “把整个数据库文件读进 shared_buffers。”

而只是建立一堆**空槽位**。

例如：

```text
shared_buffers = 128MB

NBuffers = 16384

BufferDesc[0]
BufferDesc[1]
BufferDesc[2]
...
BufferDesc[16383]

BufferBlock[0] 8KB
BufferBlock[1] 8KB
...
BufferBlock[16383] 8KB
```

刚启动：

```text
Buffer #100

tag = INVALID
VALID = 0
TAG_VALID = 0
DIRTY = 0
refcount = 0
usage_count = 0
```

然后这些空槽进入 freelist。

所以 Buffer Manager 启动阶段解决的是：

> **“我有多少个可以装 Page 的槽？”**

而不是：

> **“我要缓存哪些 Page？”**

你的材料也明确指出 `BufferManagerShmemInit` 只创建空槽、串进 freelist，并不读取表页。

# 四、第二步：用户要一个磁盘块

比如：

```sql
SELECT * FROM users WHERE id = 100;
```

最终需要：

```text
relation = users
block = 123
```

Buffer Manager 把它转换成：

```text
BufferTag
(
    spcOid,
    
    dbOid,
    relNumber,
    forkNum,
    blockNum
)
```

然后：

```text
BufferTag
    │
    ▼
BufTableHashCode()
    │
    ▼
128 个 partition 之一
    │
    ▼
BufTableLookup()
```

这里的哈希表非常关键：

```text
                 BufferTag
                     │
                     ▼
              ┌─────────────┐
              │ hash table  │
              └──────┬──────┘
                     │
             tag → buf_id
                     │
                     ▼
                  buffer 42
```

也就是说：

**Buffer Manager 并不是扫描 16384 个 Buffer 找页面。**

它首先问：

> “这个磁盘块现在在哪个 Buffer？”

哈希表直接告诉它：

```text
users block 123
      ↓
buf_id = 42
```

材料中给出的 `BufferAlloc` 路径就是：

```text
InitBufferTag
    ↓
BufTableHashCode
    ↓
分区锁
    ↓
BufTableLookup
```

命中以后直接 Pin。

# 五、命中以后发生什么？——Pin

假设：

```text
users block 123
      ↓
buffer 42
```

现在 backend 要使用它：

```text
PinBuffer(buffer 42)
```

最关键的变化：

```text
refcount:
    0 → 1
```

如果已经有两个 backend 在使用：

```text
refcount = 2
```

第三个 backend：

```text
refcount = 3
```

所以：

```text
refcount = 当前有多少人“占着这个 Buffer”
```

例如：

```text
              Buffer 42
                  │
       ┌──────────┼──────────┐
       │          │          │
    Backend A  Backend B  Backend C
       │          │          │
       └──────────┼──────────┘
                  ▼
              refcount=3
```

这也是为什么：

> **有 pin 的 Buffer 不能被淘汰。**

否则：

```text
Backend A:
    我正在访问 users block 123

Clock:
    我把 buffer 42 换成 orders block 999
```

Backend A 手上的 Page 指针瞬间就变成另外一页了。

所以 Pin 的本质不是“加锁”。

而是：

> **告诉 Buffer Manager：这个槽现在不能换成别的 Page。**

文件也特别强调：**Pin 不是锁，Pin 只保证这个槽还是这块磁盘页。**

# 六、content lock 又是什么？

这里非常容易混。

实际上 Buffer 有两层完全不同的保护：

```text
                  Buffer
                     │
        ┌────────────┴────────────┐
        │                         │
       Pin                    content_lock
        │                         │
        ▼                         ▼
  “这个槽不能换页”          “Page 内容不能乱改”
```

例如：

### Pin

```text
refcount = 1
```

表示：

> 这个 Buffer 不能被 Clock 淘汰。

### content lock

```text
LockBuffer(buffer, BUFFER_LOCK_SHARE)
```

表示：

> 我现在要读取 Page 内部的数据，不希望有人同时修改。

所以典型访问：

```text
PinBuffer()
    ↓
LockBuffer(SHARED)
    ↓
读取 tuple / xmin / xmax
    ↓
UnlockBuffer()
    ↓
继续持有 pin
    ↓
使用 tuple 指针
    ↓
UnpinBuffer()
```

材料给出的规则也是这个意思：扫描页需要 `pin + 共享 content lock`；修改页需要 `pin + 独占 content lock`。

# 七、如果没命中，真正关键的来了：找谁出去？

假设：

```text
BufTableLookup(tag)
        ↓
       MISS
```

现在 Buffer Manager 必须：

> **找一个 Buffer 槽给新 Page。**

这就是：

```text
GetVictimBuffer()
        ↓
StrategyGetBuffer()
```

而这里 PostgreSQL 的核心思想不是 LRU。

而是：

> **Clock Sweep + usage_count + pin。**

# 八、Clock 是怎么判断“谁该死”的？

可以把每个 Buffer 简化成：

```text
Buffer 0   ref=0 usage=5
Buffer 1   ref=1 usage=2
Buffer 2   ref=0 usage=0
Buffer 3   ref=0 usage=3
Buffer 4   ref=0 usage=0
```

Clock 指针：

```text
                         clock
                           ↓
0 → 1 → 2 → 3 → 4 → 0 → ...
```

规则非常简单：

### 情况 1：正在被 Pin

```text
refcount > 0
```

直接跳过：

```text
if pin > 0:
    continue
```

因为有人正在使用。

---

### 情况 2：没人 Pin，但是 usage_count > 0

例如：

```text
refcount = 0
usage_count = 3
```

Clock 不杀。

而是：

```text
usage_count:
3 → 2
```

然后继续走。

---

### 情况 3：没人 Pin，并且 usage_count = 0

```text
refcount = 0
usage_count = 0
```

这才是真正的 victim。

```text
victim = buffer
```

文件中把这三种情况总结得很清楚：`pin > 0` 跳过；`pin == 0 && usage > 0` 将 usage 减一；`pin == 0 && usage == 0` 才牺牲。

---

# 九、所以 usage_count 到底是什么？

可以把它理解成：

> **“这个 Buffer 最近有多热。”**

例如一个热点 Buffer：

```text
buffer 10
usage_count = 5
```

即使：

```text
refcount = 0
```

也不会马上被踢掉。

Clock 每扫一次：

```text
5
↓
4
↓
3
↓
2
↓
1
↓
0
```

直到变成 0 才可能被淘汰。

所以它不是 LRU。

更准确地说：

```text
                    最近使用
                       │
                       ▼
                 usage_count
                       │
              ┌────────┴────────┐
              │                 │
           热页                 冷页
           5                    0
              │                 │
              ▼                 ▼
        多绕几圈保护          可以淘汰
```

你的材料特别指出：usage 上限为 5，热页需要多轮 clock sweep 才会被淘汰，因此这是一个**近似的 clock 算法，而不是 LRU**。

# 十、找到 victim 以后，还不能直接覆盖

这是整个 Buffer Manager 最容易被忽略的一点。

假设：

```text
Buffer 42

tag = users block 123
DIRTY = 1
refcount = 0
```

Clock 认为：

```text
可以淘汰
```

但是：

```text
DIRTY = 1
```

意味着：

```text
Buffer 里面的数据
        ≠
磁盘上的数据
```

如果直接：

```text
Buffer 42 ← orders block 999
```

那么 users block 123 的修改就丢了。

所以必须：

```text
victim
   │
   ├── clean ──→ 直接重用
   │
   └── dirty ──→ FlushBuffer()
```

# 十一、FlushBuffer 是 Buffer 生命周期的“落盘点”

可以把它看成：

```text
                Buffer
                  │
             BM_DIRTY=1
                  │
                  ▼
             FlushBuffer
                  │
                  ▼
              XLogFlush
                  │
                  ▼
              smgrwrite
                  │
                  ▼
              磁盘 Page
                  │
                  ▼
             BM_DIRTY=0
```

而这里最重要的是：

```text
XLogFlush(LSN)
      ↓
smgrwrite(Page)
```

也就是：

> **WAL 先于数据页落盘。**

材料中的 FlushBuffer 路径明确是：

```text
StartBufferIO
    ↓
读取 LSN
    ↓
永久页 XLogFlush(lsn)
    ↓
checksum
    ↓
smgrwrite
```

这就是 Buffer Manager 和 WAL Manager 的关键交汇点。

# 十二、然后这个 Buffer 才真正“死亡”

假设：

```text
Buffer 42

旧：
tag = users/block123
VALID = 1
DIRTY = 1
refcount = 0
```

经过 Flush：

```text
DIRTY = 0
```

然后：

```text
InvalidateVictimBuffer()
```

从哈希表删除：

```text
users/block123 → buffer42
```

变成：

```text
buffer42
    ↓
无旧 tag
无 VALID
无 DIRTY
无 TAG_VALID
```

这时它才是一个真正干净的空槽。

然后：

```text
BufferAlloc
    ↓
buffer42.tag = orders/block999
    ↓
TAG_VALID = 1
    ↓
usage_count = 1
    ↓
StartBufferIO
    ↓
读 orders/block999
```

这就是**槽位复用**。

注意一个特别关键的思想：

> **Buffer 并不是“永久绑定”某个磁盘块。**

它只是：

```text
一个可以不断换主人身份的槽位
```

生命周期可能是：

```text
buffer42
  ↓
users block 123
  ↓
淘汰
  ↓
orders block 999
  ↓
淘汰
  ↓
index block 17
  ↓
淘汰
  ↓
...
```

而 `buf_id` 本身始终不变。

# 十四、为什么 refcount 和 usage_count 要同时存在？

这是 Buffer Manager 设计里非常漂亮的一点。

两个东西解决的是两个不同问题：

```text
refcount
    ↓
“现在有没有人在用？”

usage_count
    ↓
“最近有没有人用过？”
```

比如：

```text
Buffer A:
refcount = 3
usage = 0

Buffer B:
refcount = 0
usage = 5
```

A：

> 当前有人使用，绝对不能淘汰。

B：

> 当前没人使用，但是最近非常热，也不要马上淘汰。

所以：

```text
refcount → 当前生命周期保护
usage     → 最近访问历史保护
```

这两个维度结合起来，就形成了 PostgreSQL 的 Buffer Replacement 基础。

# 十五、Unpin 后 Buffer 并没有消失

这是另一个很重要的认识。

比如：

```text
Backend A
    ↓
Pin buffer 42
    ↓
refcount = 1
    ↓
读取 Page
    ↓
Unpin
```

并不是：

```text
Buffer 42 消失
```

而是：

```text
refcount:
1 → 0
```

Buffer 还在：

```text
Buffer 42
tag = users/block123
VALID = 1
DIRTY = 0
usage_count = 3
refcount = 0
```

此时它进入：

> **“可以被未来 Clock 淘汰，但现在还继续缓存”**

的状态。

所以：

```text
Unpin ≠ Evict
```

而是：

```text
Unpin
  ↓
refcount = 0
  ↓
成为可淘汰候选
  ↓
未来 Clock 决定是否淘汰
```

# 十六、修改一个 Page 时，Buffer 是怎么知道它脏了？

例如：

```sql
UPDATE users SET name='Tom' WHERE id=100;
```

执行过程中：

```text
PinBuffer
    ↓
LockBuffer(EXCLUSIVE)
    ↓
修改 Page
    ↓
MarkBufferDirty
```

于是：

```text
state

BM_VALID = 1
BM_DIRTY = 1
```

但注意：

**MarkBufferDirty 并不会立刻写磁盘。**

所以此时：

```text
                    内存
                  Buffer 42
                     │
                     │
                users/block123
                     │
                  modified
                     │
                     ▼
                 DIRTY=1
                     │
                     │
                     │
                     ▼
                    磁盘
              users/block123
              还是旧版本
```

这其实就是数据库性能的重要来源之一：

> 修改 Page 时先改内存，不需要每次 UPDATE 都同步写 8KB 磁盘。

# 十七、那么谁负责最终刷脏？

这里实际上有三个角色：

```text
                  Dirty Buffer
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
    Backend         BGWriter      Checkpointer
```

### 1. Backend

自己正好需要一个 victim：

```text
GetVictimBuffer
    ↓
发现 DIRTY
    ↓
FlushBuffer
```

所以：

> Buffer 不够用时，Backend 可能被迫自己刷脏。

---

### 2. Background Writer

提前帮你刷一些：

```text
clock 前面
    ↓
找 dirty buffer
    ↓
FlushBuffer
```

目的是：

> 尽量减少真正缺 Buffer 时 Backend 自己写盘的概率。

---

### 3. Checkpointer

Checkpoint 时负责更系统性地刷：

```text
BufferSync
    ↓
扫描 NBuffers
    ↓
找 checkpoint 时 dirty 的 buffer
    ↓
排序
    ↓
逐渐 FlushBuffer
```

材料明确区分了这三个角色，而且指出 bgwriter **并不保证所有脏页都落盘**，这个职责属于 checkpointer。

## 我认为最值得记住的一句话

> **PostgreSQL 的 Buffer Manager 本质上是在管理“可复用的 Page 槽位”，而不是简单管理一堆内存。**

一个槽位的核心生命周期就是：

```text
空槽
 ↓
绑定 BufferTag
 ↓
Pin
 ↓
I/O
 ↓
VALID
 ↓
被访问
 ↓
可能 DIRTY
 ↓
Unpin
 ↓
Clock 判断
 ↓
Clean → 直接回收
Dirty → WAL Flush → 写盘
 ↓
删除旧 Tag
 ↓
重新绑定新的 BufferTag
```

而整个系统靠 **`BufferTag + BufTable` 管身份、`refcount` 管“现在谁在用”、`usage_count + Clock` 管淘汰、`content_lock` 管 Page 并发修改、`DIRTY + FlushBuffer` 管持久化**。这几个模块拼起来，才是一个完整的 Buffer Manager。

如果你接下来是准备**真正读 PG18.6 源码**，我建议下一步不要继续泛泛看理论，而是沿着这一条实际调用链啃：

```text

        ↓

        ↓

        ↓
BufferAlloc
        ↓
BufTableLookup
        ↓
GetVictimBuffer
        ↓
StrategyGetBuffer
        ↓
Clock Sweep
```

然后再从另一边追：

```text

        ↓

        ↓

        ↓

        ↓

```

这样你会把 **“读 Buffer” 和 “淘汰 Buffer” 两条线在 `BufferAlloc/GetVictimBuffer` 汇合起来**，整个 PG Buffer Manager 基本就通了。材料里给出的 PG18.6 实际 seqscan 调用链正是这一条。

# 二十、Shared Buffer 的共享内存构成

前面把 Buffer 拆成了「管理对象 vs 数据对象」。这里按 `BufferManagerShmemInit()` 把共享内存里**实际有几块、按下标怎么对齐**写清楚。

启动时铺开的，大小都是 `NBuffers`（`shared_buffers / 8KB`），**同一个下标 i 对上同一格**：

```text
下标 i = 0 .. NBuffers-1

BufferDescriptors[i]     BufferDesc：这个 slot 的元数据（cacheline 对齐）
BufferBlocks[i * 8KB]    真正的 page 内容
BufferIOCVArray[i]       等 IO 完成的条件变量
CkptBufferIds[i]         checkpoint 排序用
```

slot 和 page 的对应就是：

```text
BufHdrGetBlock(bufHdr)
    = BufferBlocks + buf_id * BLCKSZ
```

页头上的 LSN：

```text
BufferGetLSN(bufHdr) = PageGetLSN(那 8KB)
```

另外两块**不属于单个 slot、但属于 Buffer Manager**：

```text
BufTable            BufferTag → buffer id 的分区哈希表
StrategyControl     freelist 头尾、nextVictimBuffer（clock 指针）
```

所以不要把下面这些词混成一个「slot」：

```text
Buffer ID      索引。BufferDesc[i] 和 BufferBlocks[i] 用同一个下标对齐
BufferTag      「这是磁盘上哪一块 logical page」
               (spcOid, dbOid, relNumber, forkNum, blockNum)
               不是单靠 blockNum；rel A block 100 ≠ rel B block 100
BufferDesc     控制块。「这个 Buffer 当前是什么状态」
               tag / state(refcount, usage_count, DIRTY, VALID, IO…)
               content_lock / freeNext
BufferBlocks   page frame。「8KB 数据实际放在哪」
BufTable       BufferTag → Buffer ID，不是「按 block 查找」
```

> **Buffer ID 是索引；BufferDesc 是控制块；BufferBlocks 是 page 存储区。** `BufferDesc` 本身不保存 8KB page。

`state` 是一个 32-bit 原子字：18 bit refcount + 4 bit usage_count + flags。Pin、dirty、usage 都落在这里，不落在 8KB 页里。

18.6 找可用槽的顺序（`StrategyGetBuffer`）：

```text
BufferAccessStrategy ring     VACUUM / COPY / 大顺序扫，只用一小圈
        ↓ 没有
freelist                      启动时空槽全在这；跑热后常常是空的
        ↓ 没有
clock-sweep                   稳态满池后的主路径
                              nextVictimBuffer % NBuffers
                              找 refcount=0 且 usage_count=0
```

Clock-sweep **只负责选 victim，自己不刷盘**。victim dirty 时，由 `GetVictimBuffer()` 调 `FlushBuffer()`。

版本限定（这份源码是 18.6，不要和 master 混）：

> PG 18.6 **仍有传统 freelist**（先 freelist，没有再 clock-sweep）。  
> `Remove freelist, always use clock-sweep` 是 **2025-09-05 进 master / PG 19** 的提交，没有进 `REL_18_STABLE`。

# 二十一、WAL Buffer 是另一套完全不同的体系

`shared_buffers` 和 `wal_buffers` **不共用** replacement、不定同一个 pin、也不在同一块内存里。

```text
shared_buffers                         wal_buffers
     │                                      │
     ▼                                      ▼
数据库 page（8KB heap/index）            WAL record（日志字节流）
BufferTag → BufTable → Buffer ID        LSN → append-only 字节流
BufferDesc[id] + BufferBlocks[id]       XLogCtl->pages（环形）
```

`XLogCtl` 是 WAL 子系统的**共享控制结构**（insert / write / flush 状态），不是 WAL Buffer 本身。真正承载 WAL bytes 的是 `pages`。

WAL 在 `XLogCtl` 里，核心是：

```text
XLogCtl
 ├── Insert.CurrBytePos     下一个 WAL record 预留到哪
 ├── pages                  wal_buffers 个 8KB 页，环形缓存
 ├── xlblocks[]             每个 WAL buffer 页对应的 LSN 上界
 ├── logInsertResult        已插入到 WAL buffer 的位置
 ├── logWriteResult         已 write 到 OS / WAL 文件的位置
 └── logFlushResult         已 fsync / fdatasync 的位置
```

路径：

```text
Backend 构造 WAL record
    → XLogInsert()              对外 API（AM 走这个）
    → XLogInsertRecord()        预留空间，拷进 wal_buffers，得到 LSN
    → XLogWrite()               写到 pg_wal 段文件（通常先进 OS cache）
    → issue_xlog_fsync()        真正持久化
```

谁来推进，必须拆开：

```text
backend
    COMMIT（默认同步提交）→ XLogFlush(commit LSN)
    刷 dirty page      → FlushBuffer 里 XLogFlush(PageLSN)

walwriter
    周期性 XLogBackgroundFlush()
    也负责 async commit（synchronous_commit=off 时
    COMMIT 只 XLogSetAsyncXactLSN，不立刻 flush）
```

**walwriter 不是唯一刷 WAL 的进程。** 更不是「所有 WAL 都由一个 flush 进程负责」。

---

# 二十二、两条链的唯一硬连接：PageLSN

```text
             WAL record @ LSN
                    │
                    │ PageSetLSN
                    ▼
              Page 头上的 PageLSN
                    │
                    │ FlushBuffer 里强制
                    ▼
         WAL 已持久化到 ≥ PageLSN
                    │
                    ▼
              才允许 smgrwrite(data page)
```

含义：

```text
PageLSN = 10000

表示：这块 page 当前内存状态，至少包含了 LSN ≤ 10000 的修改。
要把这块 page 写回 data file，必须先保证 WAL 10000 已经安全。
```

这就是 **WAL-before-data**。强制点不在 `MarkBufferDirty()`，而在 `FlushBuffer()`：

```text
读取 PageLSN
if 永久关系（BM_PERMANENT）:
    XLogFlush(PageLSN)
smgrwrite(8KB page)          交给内核，通常还不是 data file 的 fsync
```

未日志表跳过 `XLogFlush`。data file 的 fsync 主要在 checkpoint；crash 后还在 OS cache 里的 data page 可以丢，靠 WAL replay 补。

COMMIT 成功 **只表示 WAL 够安全**（默认同步提交），**不表示** 对应 heap page 已经写入数据文件。

# 二十三、一次 UPDATE 的完整过程（Shared Buffer + WAL）

```sql
UPDATE t SET a = 10 WHERE id = 1;
```

## 23.1 找到 page，pin 住

```text
ReadBuffer()
  → PinBufferForBlock()
  → BufferAlloc()
       BufTableLookup(BufferTag)
```

Hit：`PinBuffer()`，共享 refcount++（同一 backend 已 pin 过则只加私有计数），usage_count 可能 +1。

Miss：

```text
GetVictimBuffer()
  → StrategyGetBuffer()     ring / freelist / clock-sweep
  → 若 victim dirty
        FlushBuffer()       先 XLogFlush(旧 PageLSN)，再 smgrwrite 旧 page
  → 从 BufTable 摘掉旧 tag
  → 挂上新 BufferTag
  → 从 data file 读入 8KB
```

Pin 的意义：**clock-sweep 不能在你用这块 page 时把它抢走。** Pin 不是分配，也不是 content lock。

然后还要 `LockBuffer(EXCLUSIVE)`，保护页内容。

## 23.2 改 page、写 WAL、设 PageLSN

`heap_update()` 在临界区里的**真实顺序**是：

```text
START_CRIT_SECTION
    改 shared buffer 里的 tuple
    MarkBufferDirty()          先标 BM_DIRTY
    XLogInsert()               构造 XLOG_HEAP_UPDATE，拷进 wal_buffers
    PageSetLSN(page, recptr)   把返回的 LSN 写进页头
END_CRIT_SECTION
UnlockBuffer
ReleaseBuffer                  unpin（refcount 可能降到 0）
```

不要记成「先写 WAL 再 MarkDirty」。WAL-before-data 靠的是之后某次 `FlushBuffer()` 用当时的 PageLSN 强制；CRIT_SECTION 保证中间不能 ERROR，把「已改 page、未写 WAL」暴露出去。

此时内存：

```text
Buffer 123
  refcount = 0          没人在用，但还在 pool 里
  dirty    = true       还没写 data file
  PageLSN  = 10000

WAL
  record @ LSN 10000    还在 wal_buffers，不一定已经 fsync
```

## 23.3 COMMIT：保证 WAL 够安全

默认同步提交：

```text
写 COMMIT WAL record
XLogFlush(commit LSN)
  → 如有必要 XLogWrite()
  → issue_xlog_fsync()
COMMIT 返回
```

`synchronous_commit=off`：不立刻 flush，登记 async LSN，交给 walwriter 稍后刷。

到这里：WAL 已经持久化（默认同步提交），data page 仍可能只在 shared buffer 里。崩溃后靠 WAL replay 把这条 UPDATE 补回来。

## 23.4 Data page 何时写回

三种角色都可能刷脏，最终都进 `FlushBuffer()`：

```text
backend 淘汰 victim     GetVictimBuffer 发现 dirty
bgwriter                 后台提前写脏页（不保证全部落盘）
checkpointer             checkpoint 系统刷脏（真正保证）
```

淘汰路径：

```text
旧 page 写完（WAL 已先到 PageLSN）
从 BufTable 删除旧 tag
slot 换成新 BufferTag
读入或初始化新 page
```

# 二十五、面试级压缩表述（适配 PG 18.6）

> PostgreSQL Buffer Manager 用 `BufferTag` 在 `BufTable` 里把 relation block 映射到 shared buffer slot，并用 `BufferDesc` 维护 pin/refcount、`usage_count`、dirty 和 I/O 状态。Pin/Unpin 只决定这个 buffer **现在能不能被淘汰**，不是 page 的分配和释放。
>
> 18.6 的 replacement 仍是 **ring → freelist → clock-sweep**。Clock-sweep 只负责选 `refcount=0` 且 `usage_count=0` 的 victim；若 victim dirty，由 `GetVictimBuffer()` / `FlushBuffer()` 先按 PageLSN 刷 WAL，再 `smgrwrite` 数据页。PG 19 才去掉传统 freelist，改成始终 clock-sweep。
>
> 修改 page 时，backend 在临界区里先 `MarkBufferDirty()`，再 `XLogInsert()` 把 WAL record 写入 WAL buffers，并用 `PageSetLSN` 把 page 和对应 LSN 绑在一起。WAL 既可以由 backend 的 `XLogWrite`/`XLogFlush` 推进，也可以由 walwriter 后台写出；walwriter 不是唯一执行者。同步提交会 `XLogFlush(commit LSN)`，异步提交则交给 walwriter。
>
> Dirty page 被 bgwriter、checkpointer 或 backend 写回 data file 时，必须先保证 WAL 已持久化到 PageLSN，即 WAL-before-data。COMMIT 成功只表示 WAL 够安全，不表示 heap page 已经写入数据文件。

一句话：

> **Shared Buffer 管 page 的缓存、pin、dirty、IO 和 replacement；WAL 管 page 修改的持久化日志。二者通过 PageLSN 建立 WAL-before-data 的强制顺序。**

# 二十六、源码阅读时容易建错的心智模型

第二十～二十五节已经接近 PG 18.6 源码。下面按 **需要修正 / 需要补充 / 建议如何串源码** 收口，专门拆那些读 `bufmgr.c` / `xlog.c` 时最容易画歪的图。

## 26.1 需要修正

### Buffer ID / BufferDesc / BufferBlocks 不要糊成一个「slot」

概念图可以说「一个 buffer 槽」。源码分析必须拆成，并且分清 **两套编号**：

```text
对外的 Buffer（ReadBuffer 返回值）：1 .. NBuffers，0 无效
数组下标 / BufferDesc.buf_id：      0 .. NBuffers-1

Buffer 123  （公有 ID，1-based）
       │
       │  GetBufferDescriptor(123 - 1)
       │  BufferDescriptorGetBuffer() = buf_id + 1
       ▼
buf_id = 122
       │
       ├──────────────→ BufferDesc[122]      控制块
       │                   ├─ buf_id = 122
       │                   ├─ tag
       │                   ├─ state
       │                   └─ content_lock
       │
       └──────────────→ BufferBlocks[122]    8KB page frame
```

BufTable 存的也是 **0-based 的 `buf_id`**，不是公有 `Buffer`。不要写成 `Buffer ID 123 → BufferDesc[123]`。

> **公有 Buffer 是 1 起的句柄；`buf_id` 才是数组下标。BufferDesc 是控制块；BufferBlocks 是 page 存储区。**

### BufTable 不是「按 block 查找」

`block number` 不够。`rel A block 100` 和 `rel B block 100` 不是同一页。

```text
logical page identity
        │
        ▼
    BufferTag (spcOid, dbOid, relNumber, forkNum, blockNum)
        │
        ▼
     BufTable
        │
        ▼
    Buffer ID
      /     \
     ▼       ▼
BufferDesc  BufferBlocks
```

映射是 **BufferTag → Buffer ID**，不是 block → buffer。

### Pin、content lock、header state 是三套保护

这是读 `bufmgr.c` 最值得钉死的一点。

```text
             Buffer
                │
      ┌─────────┼──────────┐
      │         │          │
      ▼         ▼          ▼
    Pin      Content      State
             Lock
      │         │          │
      ▼         ▼          ▼
 能不能淘汰  能否读/改 page  buffer 生命周期
```

| 机制 | 解决什么 | 不解决什么 |
|---|---|---|
| Pin / 共享 refcount | 这个 buffer **能不能被 replacement 淘汰** | 不保护 page 内容一致性 |
| content lock（`LockBuffer` SHARE/EXCLUSIVE） | 谁能读、谁能改 **BufferBlocks[i]** | 不阻止别人 pin；clock 也不看它 |
| BufferDesc.state | `BM_DIRTY` / `VALID` / `IO_IN_PROGRESS`、refcount、usage | 不是 page 内容锁 |

一个 backend 完全可以：`Pin + EXCLUSIVE`，或 `Pin + SHARE`。`Pin ≠ LockBuffer`。

### `usage_count` 不是「访问次数」

不要理解成每访问一次 +1。它是 replacement 用来表达「最近被使用程度」的**粗粒度近似指标**。

```text
PinBuffer（默认策略，第一次共享 pin）
    → usage 不到 5 则 +1；同一 backend 再 pin 不加
clock sweep 看到 refcount==0 且 usage>0
    → usage--，继续扫
usage 变成 0 且仍无人 pin
    → 才可能成为 victim
```

所以：

> PostgreSQL 的 buffer replacement **不是严格 LRU**，而是 **clock-sweep + usage_count**（很粗的 second chance / approximate LRU）。上限 5，热页最多绕 6 圈才肯动。

### 18.6 的 freelist 不要记成「所有缺页都先问 freelist」

对 **PG 18.6** 可以继续讨论 `ring → freelist → clock-sweep`，但更准确的分层是：

```text
Buffer Access Strategy
       │
       ├── 普通 / NULL（BAS_NORMAL）
       │       ↓
       │   shared replacement
       │       ↓
       │   先偷看 freelist（启动空槽、invalidate 还回的）
       │   没有再 clock-sweep
       │
       └── ring（BAS_BULKREAD / BAS_BULKWRITE / BAS_VACUUM）
               ↓
          先问自己维护的一小圈 buffer
          给不出再退回 shared replacement
```

池子跑热之后 freelist 常常是空的，**日常满池淘汰的主路径是 clock-sweep**。不要形成「所有 buffer 都先从 freelist 找」的印象。PG 19/master 才去掉传统 freelist。

### `XLogCtl` 不是 WAL Buffer 本身

```text
                    XLogCtl          ← 控制面
                       │
        ┌──────────────┼───────────────┐
        ▼              ▼               ▼
   insert state    write state     flush state
                       │
                       ▼
                 pages / wal_buffers   ← 真正的 WAL bytes
```

### `XLogInsert` 和 `XLogFlush` 不要画成直接箭头

```text
XLogInsert() / XLogInsertRecord()
       │
       ▼
   wal_buffers
       │
       ▼
  需要推进时
       │
       ├─ 只写出（walwriter / 有人已经 write 过）→ XLogWrite() → OS / 文件
       │                                              │
       │                                              │ 切 WAL 段时，Write 自己也会 fsync
       │
       └─ 要 durable（COMMIT / FlushBuffer）
              XLogFlush(LSN)
                 │
                 ├─ 若 Flush 位置已经 ≥ LSN → 直接返回（barrier 已满足）
                 └─ 否则持 WALWriteLock，内部调用 XLogWrite()，再 issue_xlog_fsync()
```

不要把 `XLogWrite` 和 `XLogFlush` 画成两条并列管道。`XLogFlush` 是 barrier；真正干活时它**调用** `XLogWrite`，而不是另外走一套 write。

**Write**：WAL buffer → 内核/文件，不代表 crash-safe（切段时除外，那时 Write 也会 fsync）。  
**Flush**：保证 `logFlushResult >= 目标 LSN`。已经满足就是空操作。

### `XLogFlush(PageLSN)` ≠ 「每次刷 page 都一定 fsync 一次」

```text
PageLSN = 10000
LogwrtResult.Flush = 15000

XLogFlush(10000)   → 已经满足，可能什么都不干
```

它是 **WAL durability barrier**，不是「马上 fsync 一次 WAL」。

### PageLSN 再精确一点

作为 WAL-before-data 的解释，「写回 data file 前 WAL 至少要到这个 LSN」是对的。源码层面：

> **PageLSN = 这个 page 上「最后一条需要 WAL 保护的修改」对应记录的结束位置**（页头注释：`next byte after last byte of xlog record`）。`XLogInsert()` 返回的就是这个 EndPos，`PageSetLSN` 写进去。

所以 `FlushBuffer` 里 `XLogFlush(PageGetLSN(page))` 的意思是：把**当前这个版本**的 page 写到 data file 之前，WAL 至少 flush 到 X。

hint bit 可以只 `MarkBufferDirty` 而不推进 PageLSN（除非 `wal_log_hints` / checksum 走了 hint WAL）。因此「dirty 的 page，PageLSN 一定是刚才那次修改」并不总成立。

### `MarkBufferDirty → XLogInsert → PageSetLSN` 是 heap 主路径，不是所有路径

`heap_update()` 确实是这个顺序。但不要推成 Buffer Manager 的普遍定律：hint bit 常常只 dirty、不插 WAL；部分 inplace / hint WAL 路径甚至会先 `XLogInsert` 再 `MarkBufferDirty`。共性只是临界区里必须把 **dirty、WAL record、PageLSN** 收成一致状态，之后 `FlushBuffer` 用 PageLSN 做 barrier。

## 26.2 需要补充

### Ring 的意义：bulk workload 不污染整个 pool

```text
shared_buffers = 1GB
VACUUM 扫 500GB 表
```

若走普通 replacement，顺序扫描会把热点页挤光。所以 `BAS_BULKREAD` / `BAS_VACUUM` / `BAS_BULKWRITE` 自己转一小圈 buffer，循环复用。这是对「这个 workload 不值得污染整个 buffer pool」的优化，不是第三种 freelist。

### WAL 不是 page cache

Shared Buffer 可以问「relation X block 100 在哪个 buffer？」（hash lookup → 固定 slot）。  
WAL 的坐标是 **LSN**，本质是 **append-only log**，不能按 relation/block 反查「这条日志在哪个 wal_buffer」。

### COMMIT 和 dirty page flush 是两条时间线

```text
T1 UPDATE → page dirty + WAL record + PageLSN
COMMIT    → XLogFlush(commit LSN) → 事务成功

此时：
  shared buffer dirty = true
  data file 可能仍是旧数据
  WAL 已经 durable（默认同步提交）

很久以后：
  checkpoint / bgwriter / victim
      → FlushBuffer → data file 更新
```

> **COMMIT ≠ data page 已经落盘。**

为什么这样设计：每次 UPDATE 都 fsync 对应 data page 会把随机写摊到提交路径上。WAL 把提交路径变成 **顺序写日志 + 提交时保证 WAL durable**，data page 交给后台慢慢刷。

崩溃后：WAL 已有 LSN 1000、data page 仍是旧版 → startup 从 checkpoint 起 replay → 旧页被 redo 成新页。WAL 就是 data page 延迟落盘期间的保险。

### 三个写盘角色不要都叫 flush process

```text
WAL 路径
  backend     COMMIT / FlushBuffer 时 XLogFlush
  walwriter   后台把 WAL buffer 写出；也扛 async commit

Data page 路径
  backend     淘汰 dirty victim 时自己 FlushBuffer
  bgwriter    提前写一部分脏页，降低 backend 被迫写脏的概率
  checkpointer  形成 checkpoint consistency point，系统刷脏
```

bgwriter **不保证**所有脏页落盘；那个职责属于 checkpointer。

### `fsync` 和 `synchronous_commit` 不要混

```text
WAL record → WAL buffer → write 到 OS/文件 → fsync → durable storage
```

`synchronous_commit` 控制的是：**事务提交时，backend 要不要等待 WAL 到达相应 durability 点。**

- `on`：COMMIT 等到 WAL flush 再返回
- `off`：COMMIT 可先返回，walwriter 稍后 flush；crash 时**已返回成功的事务可能消失**——原因是 commit WAL 当时还没 durable，不是因为 data page 没写

## 26.3 四个坐标系（继续读源码时最有用）

```text

LSN                WAL 的顺序坐标（insert / write / flush / recovery）
PageLSN            把「这块 page 的当前版本」绑到「WAL 必须到哪」
```

串起来：

```text
Buffer ID → BufferDesc → Page → PageLSN → LSN → WAL subsystem
```

概念对照：

| 概念 | 真正解决的问题 |

| `BufferDesc` | 这个 Buffer 当前是什么状态？ |
| `BufferBlocks` | page 数据实际放在哪里？ |
| `Pin/refcount` | 当前有人使用它吗？能淘汰吗？ |
| `content_lock` | 谁能读/修改这个 page？ |
| `usage_count` | 这个 buffer 最近是否值得保留？（近似，不是访问计数） |
| `ring` | bulk workload 如何避免污染 buffer pool？ |
| `freelist` | 有没有可以直接拿的空闲 buffer？（18.6 启动/失效槽；不是日常主路径） |
| `clock sweep` | 满了以后哪个 buffer 可以当 victim？ |
| `BM_DIRTY` | 这个内存 page 是否比 data file 新？ |
| `WAL record` | 这个修改是什么？ |
| `LSN` | 这个 WAL 修改在日志中的位置？ |
| `PageLSN` | 这个 page 当前状态依赖 WAL 到哪里？ |
| `XLogWrite` | 把 WAL 从 buffer 写出去（未必 durable） |
| `XLogFlush` | 确保 WAL **至少**达到要求的持久化位置（可能是空操作） |
| `WAL writer` | 后台推进 WAL 写出 / 异步提交 |
| `bgwriter` | 提前写部分 dirty data pages |
| `checkpointer` | 执行 checkpoint 所需的数据页 / WAL 协调 |
| `FlushBuffer` | 把一个 dirty shared buffer **安全**写回 data file |

## 26.4 建议下一步怎么串源码

不要再停在架构图。沿着这一条调用链逐函数走（PG 18.6）：

```text
ReadBufferExtended
    → PinBufferForBlock / BufferAlloc     并发：哈希命中 vs 抢 victim
    → StrategyGetBuffer                   ring / freelist / clock-sweep
    → PinBuffer                           私有 pin vs 共享 refcount；usage
    → heap_update                         CRIT_SECTION：Dirty → Insert → PageLSN
    → XLogInsert / XLogInsertRecord
    → COMMIT 路径 XLogFlush               barrier，不是每次都 fsync
    → FlushBuffer                         写 page 前检查 PageLSN
```

最值得深挖的三块：

1. **`BufferAlloc()`** 如何处理并发（lookup 后被别人插入、victim 被重新 pin/dirty）
2. **`StrategyGetBuffer()`** 如何处理 clock-sweep（以及 18.6 里 freelist / ring 的真实位置）
3. **`FlushBuffer()`** 为什么写 page 前必须 `XLogFlush(PageLSN)`（以及它为什么常常是空操作）

这三块一旦搞清楚，shared buffer + WAL 的核心机制基本就通了。
