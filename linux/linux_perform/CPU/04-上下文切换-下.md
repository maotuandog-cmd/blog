# 04 | CPU 上下文切换是什么？（下）

原文：[time.geekbang.org/column/article/70077](https://time.geekbang.org/column/article/70077)

接 [[03-上下文切换-上]]：原理讲完，这一讲用工具把「切换过多」查出来。

## 系统级：vmstat

```bash
vmstat 1
```

必看四列：

| 列 | 含义 |
|----|------|
| **cs** | 每秒上下文切换次数 |
| **in** | 每秒中断次数 |
| **r** | 就绪队列（Running + 等 CPU），持续 > 核数 = 在抢 CPU |
| **b** | 不可中断睡眠（D） |

空闲机器 cs 往往只有几十。案例里用 sysbench 打到 **cs ≈ 139 万**、**sy=84%**、**r=8（2 核）**、**in≈1 万**。

## 进程/线程级：pidstat

```bash
pidstat -w 5          # 进程的切换
pidstat -w -u 1       # 切换 + CPU
pidstat -wt 1         # 必须加 -t 才看得到线程
```

| 指标 | 含义 | 高了说明什么 |
|------|------|----------------|
| **cswch/s** | 自愿切换 | 等资源（I/O、锁、内存…） |
| **nvcswch/s** | 非自愿切换 | 被强制调度，在抢 CPU |

Linux **调度单位是线程**。只看进程会严重低估：案例里 sysbench 主线程切换不多，子线程 `nvcswch/s` 到十万级。

## 中断类型：/proc/interrupts

```bash
watch -d cat /proc/interrupts
watch -d 'cat /proc/interrupts | sort -nr -k2'
```

案例中涨最快的是 **RES（重调度中断）**：SMP 上调度器叫醒空闲核去跑新任务，属于处理器间中断（IPI）。跟「线程太多、调度太勤」一致。

窗口太窄时 RES 列可能看不到，拉宽终端或 `sort`。

## 实验

```bash
apt install sysbench sysstat
# CentOS 的 sysbench 默认 max-requests=10000，会很快结束，加大请求数：
sysbench --threads=10 --time=300 --thread-locks=1 threads run
# 旧语法：
# sysbench --num-threads=10 --max-time=300 --max-requests=10000000 --test=threads run

# 另两个终端
vmstat 1
pidstat -wt 1
```

## 多少次算多？

没有绝对阈值。作者经验：

- 稳定在 **数百～一万以内** 常见  
- **超过约 1 万**，或出现 **数量级跳升**，就要当问题查  

对照类型再拆：

1. 自愿切换多 → 先查 I/O / 锁 / 资源  
2. 非自愿切换多 → CPU 争用  
3. 中断次数多 → `/proc/interrupts` 看是哪一种（网卡、RES、定时器…）

## 和前两讲串起来的套路

```text
uptime          → 负载高不高
mpstat / pidstat → us 高？wa 高？还是在等 CPU？
vmstat          → cs / in / r / b
pidstat -wt     → 哪个线程在切、自愿还是非自愿
/proc/interrupts → 中断类型
```

CPU 使用率不高但 load 很高，也要想到：**大量切换、大量线程、大量等资源**，不要只盯 %usr。
