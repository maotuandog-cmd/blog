# 12 | CPU 性能优化的几个思路

原文：[time.geekbang.org/column/article/73151](https://time.geekbang.org/column/article/73151)

定位完瓶颈再优化。动手前先问三件事。

## 方法论：动手前三问

1. **效果怎么量？** 优化前、后都要有数。
2. **多个问题时先改哪个？** 不是所有问题都值得改。
3. **多种方法选哪个？** 提升最大的不一定最好。

例子：直接 I/O 导致 iowait 90%。换成缓存 I/O 后 iowait 接近 0、没有别的瓶颈、也不破坏功能 → 可以立刻改。现实往往没这么干净：改一个指标可能把另一个弄坏。

### 评估效果：三步走

1. 定量化指标
2. 测优化前
3. 测优化后

不要只看 CPU。至少两个维度：

| 维度 | 例（Web） |
|------|-----------|
| 应用 | 吞吐量、请求延迟 |
| 系统 | CPU 使用率 |

应用指标是最终目的；系统指标用来找瓶颈来源。Web 可用 `ab` 测并发和延迟，同时用 `vmstat` / `pidstat` 看 CPU。

测压注意：

- 压测工具和被测服务**不要同机**（专栏 Nginx 案例就是两台虚拟机）。
- 优化前后机器配置、外部依赖要一致。

### 多个问题同时存在

二八原则：80% 问题来自 20% 代码。先分析全部瓶颈，去掉有因果关系的，再测剩下的，选收益最大的那个。

简化：

- 资源已经打满（CPU 100%）→ **先修资源瓶颈**。
- 同类指标里，变化幅度最大的优先（例如 us +10%、sy +50% → 先看 sy）。

### 多种方法怎么选

优化有成本：复杂度↑、可维护性↓、可能牺牲别的指标。DPDK 绕开内核协议栈很快，但要独占一核 + 大页，CPU 还常年 100%。核少就亏。不要一步登天，也不要原封不动抄别人的方案。

## 应用侧

最好的办法：砍掉不必要的工作（少循环层次、少递归、少动态分配）。

常见手段：

- 编译器：gcc `-O2` 等
- 算法：大数据量用 O(n log n) 代替 O(n²)
- 异步：轮询改事件通知
- 多线程代替多进程（切换更轻）
- 缓存热点数据和中间结果

## 系统侧

目标：用好 CPU 缓存本地性；控制进程互抢。

- **绑核**：提高 cache 命中，少跨 CPU 调度
- **独占**：CPU 分组 + 亲和性，不许别人用
- **nice**：核心应用抬优先级，非核心降低
- **cgroups**：限制 CPU 上限，防某个应用把机器吃光
- **NUMA**：尽量只访问本地内存
- **中断均衡**：`irqbalance` 或 `smp_affinity`

## 过早优化

“过早优化是万恶之源”。需求会变，针对当前情况的优化可能挡后续功能。先满足当前性能要求，瓶颈出现再按评估结果改最重要的那个。

CPU 不是唯一因素。把某一个指标推到极致，整体不一定更好。
