# 35 | 基础篇：C10K 和 C1000K 回顾

原文：[time.geekbang.org/column/article/81268](https://time.geekbang.org/column/article/81268)

C = Client。C10K = 单机 1 万并发，C1000K = 100 万，C10M = 1000 万。

连接用五元组标识（协议+源 IP+源端口+目的 IP+目的端口）。**客户端**单 IP 出站受 65535 端口限制；**服务端**接受连接不受这个限制。

## C10K（1999）

物理够：2GB / 千兆网，每连接 <200KB、<100Kbit 就行。瓶颈是 **同步阻塞 I/O**：一请求一进程/线程，调度和内存撑不住。

要解决两件事：一线程里处理多路 I/O；更少线程服务更多请求。

### 事件通知

| | 水平触发 | 边缘触发 |
|--|----------|----------|
| 何时通知 | 只要还能非阻塞 I/O | 状态变化那一次 |
| 应用要干啥 | 随时查状态再读写 | 尽量读/写到 EAGAIN；漏了这次就没下次 |

### I/O 模型

| 方式 | 要点 | 坑 |
|------|------|-----|
| select | 固定位图，32 位默认 1024 | O(N) 轮询；每次把 fd 集合拷进内核再拷出 |
| poll | 变长数组，无 1024 上限 | 仍 O(N)，仍来回拷集合 |
| **epoll**（2.6） | 内核红黑树管 fd；只报有事件的 | 边缘触发必须读干净 |
| AIO | 发起一堆 I/O，完成再通知 | 当年 glibc AIO 不完善，难用 |

### 工作模型

1. **主进程 + 多 worker**：主进程 bind/listen，worker 里 accept / epoll_wait。Nginx 经典模型。`accept` 惊群 2.6 已解；epoll 惊群要到 4.5 的 `EPOLLEXCLUSIVE`。Nginx 用 `accept_mutex` 让只有一个 worker 进 epoll。
2. **多进程同端口 + `SO_REUSEPORT`**（内核 ≥3.9）：内核做负载均衡，天然不惊群。Nginx 1.9.1 起支持。

C10K 用 epoll 就解决了；C100K 多半再加硬件容量就够。

## C1000K

物理：100 万 × 16KB ≈ 15GB；20% 活跃 × 1KB/s ≈ 1.6Gb/s → 要万兆或 Bonding。

软件：fd 上限、conntrack、socket/TCP 缓冲。

中断：多队列网卡、irqbalance、绑核、RPS/RFS、TSO/GSO、LRO/GRO。

本质还是 epoll，但要从应用到内核到硬件整条链一起抠。

## C10M

内核协议栈路径太长（硬中断→软中断→各层→应用），参数调到头也不够。两条路：

- **DPDK**：用户态轮询，绕过协议栈；PPS 极高时轮询划算。加大页、绑核、对齐、流水线。
- **XDP**（内核 ≥4.8，eBPF）：包进协议栈前处理，无缓存队列。常见于 IDS、DDoS、Cilium。

多数业务用集群拆请求比单机 C10M 更划算。DPDK/XDP 都要额外开发。
