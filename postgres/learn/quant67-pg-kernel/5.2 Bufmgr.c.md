


我们下一步直接进入 **PG18 `bufmgr.c` 的核心路径**，不再停留在概念层。建议从一次 **Buffer Miss** 开始，因为这条路径会把 Shared Buffer 最重要的东西全部串起来：

```text
ReadBuffer()
   ↓
ReadBufferExtended()
   ↓
ReadBuffer_common()
   ↓
BufferAlloc()
   ↓
BufTableLookup()
   ↓
MISS
   ↓
GetVictimBuffer()
   ↓
StrategyGetBuffer()
   ↓
Clock Sweep / Ring
   ↓
Victim Buffer
   ↓
Dirty?
   ├── No → 直接复用
   └── Yes → WAL flush → Data page flush
   ↓
安装新的 BufferTag
   ↓
StartReadBuffer()
   ↓
WaitReadBuffers()
   ↓
BM_VALID
   ↓
返回 Buffer
```

我们可以把这一段拆成 **5 个小节**：

1. **`ReadBuffer()` 到 `ReadBuffer_common()`：调用入口到底怎么走**
    
2. **`BufferTag` + `BufTableLookup()`：PG 怎么判断 HIT/MISS**
    
3. **`BufferAlloc()`：MISS 后怎么抢一个 buffer**
    
4. **`StrategyGetBuffer()`：Clock Sweep 到底怎么找 victim**
    
5. **victim 是 dirty 时：怎么和 WAL、IO、并发控制串起来**
    

其中第 3、4 节是 Shared Buffer 的核心，也是最容易真正看懂源码的地方。

我们下一步就从 **`ReadBuffer()` → `ReadBuffer_common()`** 开始，直接按 PG18 源码逻辑走。

这一节只做一件事：**把 PG18 的 `ReadBuffer()` → `ReadBufferExtended()` → `ReadBuffer_common()` 这条入口路径搞明白。**

先不急着讲 Clock Sweep。因为如果入口没吃透，后面 `BufferAlloc()`、victim、IO 很容易变成背函数名。

---

# 1. 从最简单的 `ReadBuffer()` 开始

PG18 源码里：

```c
Buffer
ReadBuffer(Relation reln, BlockNumber blockNum)
{
    return ReadBufferExtended(reln,
                              MAIN_FORKNUM,
                              blockNum,
                              RBM_NORMAL,
                              NULL);
}
```

也就是说，`ReadBuffer()` 本身几乎什么都不干。([Doxygen PostgreSQL](https://doxygen.postgresql.org/bufmgr_8h.html?utm_source=chatgpt.com "PostgreSQL Source Code: src/include/storage/bufmgr.h File Reference"))

它只是把：

```text
ReadBuffer(relation, block)
```

转换成：

```text
ReadBufferExtended(
    relation,
    MAIN_FORKNUM,
    block,
    RBM_NORMAL,
    NULL
)
```

这里已经出现了几个重要概念：

```text
MAIN_FORKNUM
    ↓
main fork

RBM_NORMAL
    ↓
正常读取 page

NULL strategy
    ↓
使用默认 Buffer Access Strategy
```

所以：

```text
ReadBuffer()
```

可以理解为：

> **“我要正常读取这个 relation 的 main fork 的某个 block，使用默认的 buffer replacement 策略。”**

---

# 2. 为什么 PostgreSQL 还要有 `ReadBufferExtended()`？

因为 PostgreSQL 不只有普通 heap table 的 main fork。

一个 relation 可能有：

```text
main fork
fsm fork
vm fork
init fork
```

例如：

```text
base/
  16384/
    16390        ← main fork
    16390_fsm    ← FSM
    16390_vm     ← VM
```

所以更完整的接口是：

```c
ReadBufferExtended(
    Relation reln,
    ForkNumber forkNum,
    BlockNumber blockNum,
    ReadBufferMode mode,
    BufferAccessStrategy strategy
)
```

PG18 中它最终直接调用：

```c
buf = ReadBuffer_common(
    reln,
    RelationGetSmgr(reln),
    0,
    forkNum,
    blockNum,
    mode,
    strategy
);
```

源码就是这么走的。([Doxygen PostgreSQL](https://doxygen.postgresql.org/bufmgr_8c.html?utm_source=chatgpt.com "PostgreSQL Source Code: src/backend/storage/buffer/bufmgr.c File Reference"))

所以调用链目前是：

```text
ReadBuffer()
    │
    ▼
ReadBufferExtended()
    │
    ▼
ReadBuffer_common()
```

---

# 3. `ReadBuffer_common()` 才是真正的核心入口

PG18 的函数签名：

```c
static pg_always_inline Buffer
ReadBuffer_common(
    Relation rel,
    SMgrRelation smgr,
    char smgr_persistence,
    ForkNumber forkNum,
    BlockNumber blockNum,
    ReadBufferMode mode,
    BufferAccessStrategy strategy
)
```

源码中这个函数从大约 1276 行开始。([Doxygen PostgreSQL](https://doxygen.postgresql.org/bufmgr_8c.html?utm_source=chatgpt.com "PostgreSQL Source Code: src/backend/storage/buffer/bufmgr.c File Reference"))

你可以先不要被参数吓到。

把它翻译成人话：

```text
ReadBuffer_common(
    我要访问哪个 relation,
    它的 storage manager 是谁,
    relation 是什么持久化类型,
    哪个 fork,
    哪个 block,
    用什么读取模式,
    用什么 buffer strategy
)
```

它才是真正负责：

```text
“把这个 Page 搞到一个 Buffer 里面，并把 Buffer 返回给调用者。”
```

---

# 4. 先搞清楚这几个参数

## `Relation rel`

这是 PostgreSQL relcache 中的 relation 对象。

可以理解成：

```text
Relation
   │
   ├── relation metadata
   ├── relfilenode
   ├── tablespace
   ├── persistence
   └── SMgrRelation
```

所以它帮助 PostgreSQL 确定：

> **我要访问的是哪个物理 relation。**

---

# 5. `SMgrRelation smgr`

这是 Storage Manager 对象。

你之前已经看过整个层次：

```text
Buffer Manager
      │
      ▼
Storage Manager
      │
      ▼
md.c
      │
      ▼
OS
```

所以：

```text
ReadBuffer_common()
```

拿到 `smgr` 后，最终才能把：

```text
relation + fork + block
```

转换成真正的：

```text
data file + offset
```

去做 IO。

---

# 6. `ForkNumber forkNum`

这个很简单：

```text
MAIN_FORKNUM
FSM_FORKNUM
VISIBILITYMAP_FORKNUM
INIT_FORKNUM
```

比如普通：

```c
ReadBuffer(rel, 100)
```

实际就是：

```text
fork = MAIN_FORKNUM
block = 100
```

所以最终要找的 Page 身份实际上是：

```text
Relation
+
Fork
+
Block
```

但这里还缺 tablespace/database 等信息。

这些会组合成 BufferTag。

---

# 7. `BlockNumber blockNum`

这个就是：

```text
第几个 8KB block
```

例如：

```text
blockNum = 123
```

就是：

```text
relation 的第 123 个 page
```

如果：

```text
BLCKSZ = 8192
```

那么物理 offset 大致就是：

```text
123 × 8192
```

当然 PostgreSQL 实际不会简单在 Buffer Manager 里自己这么算然后直接 `pread()`，而是继续走 Storage Manager。

---

# 8. `ReadBufferMode`

最常见的是：

```text
RBM_NORMAL
```

意思：

> 正常读取这个 Page。

但 PostgreSQL 还有其他模式，例如：

```text
RBM_ZERO_ON_ERROR
RBM_ZERO_AND_LOCK
RBM_ZERO_AND_CLEANUP_LOCK
```

这些主要用于一些特殊的 buffer/page 创建、错误处理、加锁场景。

所以不要把：

```text
ReadBuffer()
```

理解成永远只是：

```text
“从磁盘读 8KB”
```

它其实是一个**统一的 Buffer 获取接口**。

---

# 9. 最容易被忽略的：`BufferAccessStrategy`

这个东西非常重要。

我们前面讲过：

```text
默认：
Clock Sweep

特殊 workload：
Ring Buffer
```

这里：

```c
BufferAccessStrategy strategy
```

就是把这个策略传进 Buffer Manager。

普通：

```c
ReadBuffer(rel, block)
```

传：

```text
strategy = NULL
```

意味着：

> 使用默认策略。

而 VACUUM、顺序扫描等特殊场景可能传入自己的 strategy。

所以你可以把：

```text
ReadBuffer()
```

理解成：

```text
我要一个 Page
    │
    ├── Page 是谁？
    │      ↓
    │   Relation/Fork/Block
    │
    └── Buffer 从哪里拿？
           ↓
        Strategy
```

# 11. `ReadBuffer_common()` 第一件重要的事情是什么？

PG18 源码一开始先做了一些参数/特殊 relation 检查。

例如源码中特别检查：

```c
RELATION_IS_OTHER_TEMP(rel)
```

也就是：

> 当前 backend 不能通过 Shared Buffer 去访问其他 session 的 local temporary relation。

这是因为 PostgreSQL 的临时表可能使用 **local buffers**，而不是普通 shared buffers。源码明确把这个检查放在 `ReadBuffer_common()`，以覆盖所有走这个入口的调用者。([Doxygen PostgreSQL](https://doxygen.postgresql.org/bufmgr_8c.html?utm_source=chatgpt.com "PostgreSQL Source Code: src/backend/storage/buffer/bufmgr.c File Reference"))

这个细节你暂时不用深挖。

你现在只需要记住：

```text
普通 permanent/unlogged relation
        ↓
Shared Buffer

某些 temporary relation
        ↓
Local Buffer
```

所以：

> **不是所有 PostgreSQL Page 都经过 Shared Buffer。**

---

# 12. 接下来真正关键的事情：PG18 把 Read 分成了 Start / Wait

这是 PG18 和很多旧版本资料最容易产生认知冲突的地方。

PG18 `bufmgr.c` 的 principal entry points 已经明确列出了：

```text
ReadBuffer()
StartReadBuffer()
StartReadBuffers()
WaitReadBuffers()
```

其中：

```text
Start
```

和：

```text
Wait
```

被拆开了。([Doxygen PostgreSQL](https://doxygen.postgresql.org/bufmgr_8c_source.html?utm_source=chatgpt.com "PostgreSQL Source Code: src/backend/storage/buffer/bufmgr.c Source File"))

你可以先建立这个模型：

```text
                    ReadBuffer
                        │
                        ▼
                 ReadBuffer_common
                        │
                        ▼
                  Start Read
                        │
                        ▼
                    IO running
                        │
                        ▼
                    Wait Read
                        │
                        ▼
                   Page ready
```

这就是 PG18 Buffer Manager 读 IO 的一个重要变化。

---

# 13. 为什么要拆 Start 和 Wait？

因为数据库最怕这种：

```text
Backend
  │
  ▼
发起 IO
  │
  ▼
傻等磁盘
  │
  ▼
IO 完成
  │
  ▼
继续干活
```

如果一次只读一个 page：

```text
Page A
Page B
Page C
Page D
```

CPU/IO 的重叠空间有限。

PG18 可以更自然地形成：

```text
Start A ────────────────┐
                        │
Start B ───────────┐    │
                   │    │
Start C ───────┐   │    │
               │   │    │
CPU work       │   │    │
               ▼   ▼    ▼
             Wait A/B/C
```

尤其是：

```text
StartReadBuffers()
```

本身就是针对多个 block 的读取路径。源码中还存在 `MAX_IO_COMBINE_LIMIT`、`io_combine_limit` 等参数，用于控制可以组合处理的 IO 大小。([Doxygen PostgreSQL](https://doxygen.postgresql.org/bufmgr_8c_source.html?utm_source=chatgpt.com "PostgreSQL Source Code: src/backend/storage/buffer/bufmgr.c Source File"))

所以 PG18 的 Buffer Manager 已经明显开始把：

> **“Buffer 管理”与“IO 调度”**

结合得更紧密。

# 14. 但是现在先不要跳到 AIO

因为我们现在真正要搞懂的是：

> **Page 到底怎么从“不在 Buffer”变成“在 Buffer”。**

所以我们先把最重要的逻辑抽象出来：

```text
ReadBuffer_common()
       │
       ▼
找到/分配一个 Buffer
       │
       ▼
Buffer 与 BufferTag 建立关系
       │
       ▼
判断：
这个 Buffer 里有没有我要的 Page？
       │
   ┌───┴────┐
   │        │
  HIT      MISS
   │        │
   ▼        ▼
 Pin      找 Victim
   │        │
   │        ▼
   │      处理旧 Page
   │        │
   │        ▼
   │      新 Page IO
   │        │
   └────────┤
            ▼
          Return
```

这里有一个非常关键的问题：

# **PG 怎么判断一个 Page 是否已经在 Shared Buffer？**

答案就是：

```text
BufferTag
       ↓
Hash Table
       ↓
Buffer ID
```

# 15. 这就是下一层：`BufTableLookup()`

我们终于来到真正的：

```text
HIT / MISS
```

判断。

PostgreSQL 有一个 Buffer Mapping Hash Table。

概念上：

```text
                   BufferTag
                       │
                       │ hash
                       ▼
              ┌──────────────────┐
              │ Buffer Mapping   │
              │ Hash Table       │
              ├──────────────────┤
              │ Tag → Buffer ID  │
              └────────┬─────────┘
                       │
                       ▼
                  Buffer 5231
                       │
                       ▼
                  BufferDesc
                       │
                       ▼
                    Page
```

对应源码主要在：

```text
src/backend/storage/buffer/buf_table.c
```

而 `ReadBuffer_common()` 会利用它判断：

```text
这个 BufferTag
是不是已经存在？
```

---

# 16. 一个非常重要的认知

不要把 Shared Buffer 想成：

```text
Buffer[0]
Buffer[1]
Buffer[2]
...
```

然后：

```text
每个 Buffer 自己看看是不是我要的 Page
```

那样查找成本是：

```text
O(N)
```

假设：

```text
shared_buffers = 64GB
```

那得扫描海量 Buffer。

PG 的设计是：

```text
BufferTag
   │
   ▼
Hash
   │
   ▼
Mapping Table
   │
   ▼
Buffer ID
```

因此 Page lookup 是 hash table lookup，而不是扫描整个 buffer pool。

这也是为什么：

> **BufferTag 是 Shared Buffer 的“身份证”，而 Buffer ID 只是“座位号”。**

这个区别非常重要。

---

# 17. 现在你应该能理解一次 HIT

假设：

```text
我要：
rel A / main / block 123
```

构造：

```text
BufferTag(A, MAIN, 123)
```

然后：

```text
BufTableLookup(tag)
```

结果：

```text
Buffer ID = 5231
```

然后：

```text
BufferDesc[5231]
```

发现：

```text
BM_VALID = 1
```

并且：

```text
tag == 我要找的 tag
```

于是：

```text
PinBuffer()
```

最终：

```text
return 5231
```

整个过程：

```text
ReadBuffer
   ↓
ReadBufferExtended
   ↓
ReadBuffer_common
   ↓
BufferTag
   ↓
BufTableLookup
   ↓
HIT
   ↓
Pin
   ↓
return Buffer
```

**这个就是 Buffer Hit。**

---

# 18. MISS 就从这里分叉

如果：

```text
BufTableLookup(tag)
```

找不到：

```text
MISS
```

那么问题立刻变成：

> **“那我应该把这个 Page 放进哪个 Buffer？”**

于是进入：

```text
BufferAlloc()
```

然后：

```text
GetVictimBuffer()
```

然后：

```text
StrategyGetBuffer()
```

最后：

```text
Clock Sweep / Ring
```

这就是下一阶段。

---

# 19. 你现在先记住三个函数

接下来读源码的时候，把这三个函数钉死：

```text
ReadBuffer_common()
        │
        ▼
BufferAlloc()
        │
        ▼
GetVictimBuffer()
```

再往下：

```text
GetVictimBuffer()
        │
        ▼
StrategyGetBuffer()
```

其中：

```text
ReadBuffer_common()
```

解决：

> 我要哪个 Page？

```text
BufferAlloc()
```

解决：

> 这个 Page 已经在 cache 了吗？如果没有，准备怎么分配？

```text
GetVictimBuffer()
```

解决：

> 从 Buffer Pool 里拿哪个槽位给它？

```text
StrategyGetBuffer()
```

解决：

> **具体按照什么 replacement 策略找 victim？**

# 20. 下一节最关键

下一节我们就直接进入：

```text
BufferAlloc()
```

然后我会重点给你讲一个非常经典的并发场景：

```text
Backend A                 Backend B

Lookup(Page X)            Lookup(Page X)
    ↓                         ↓
  MISS                      MISS
    ↓                         ↓
找 victim                  找 victim
    ↓                         ↓
两个 backend
同时发现 Page X 不在 cache
```

这时候 PostgreSQL **怎么避免两个 backend 把同一个 Page 重复加载两次**？

这个问题会把：

```text
Buffer Mapping Lock
BufferDesc state
Pin
IO_IN_PROGRESS
BufferTag
victim
```

全部串起来。

**这才是 Shared Buffer 源码真正有意思的地方。**
