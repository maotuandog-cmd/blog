# 40 | 案例篇：网络请求延迟变大了，我该怎么办？

原文：[time.geekbang.org/column/article/82833](https://time.geekbang.org/column/article/82833)

**网络延迟**多指 RTT（双向）。**应用延迟** = 传输 + 处理。ICMP 常被关，改用：

```bash
hping3 -c 3 -S -p 80 baidu.com
traceroute --tcp -p 80 -n baidu.com   # 无响应打 *
```

## 案例：同样 Nginx，并发后一个慢

官方 80 口 vs 案例 8080 口。`hping3` 单次都 ~7ms；`wrk -c 100` 后 80 口均延迟 9ms，8080 口 **44ms**，QPS 从 1.2 万掉到 2k。

tcpdump → Wireshark Follow TCP Stream / Flow Graph：第一次响应正常，第二次客户端收到第一段后 **等 40ms 才 ACK**。

## 根因：Delayed ACK × Nagle

| 机制 | 干什么 | 默认 |
|------|--------|------|
| Delayed ACK | 等一会儿（常 40ms）看有没有数据可捎带 ACK | 除非套接字设 `TCP_QUICKACK` |
| Nagle | 未确认分组最多一个，小包合并后再发 | 除非 `TCP_NODELAY` |

两端一起开：Server 发完第一段等 ACK → Client 等 40ms 才 ACK → Server 才发第二段。HTTP header 和 body 被拆成两段时特别明显。

`strace` 见 wrk 只设了 `TCP_NODELAY`，没设 `TCP_QUICKACK`。案例 Nginx 配置 `tcp_nodelay off;`。改成 `on` 后延迟回到 ~9ms。官方镜像默认就是 on。

客户端 `TCP_QUICKACK` 也能解，但客户端常不在你手里。Delayed ACK 超时多数发行版改不了（RHEL 有 `tcp_delack_min`）。

## 排查顺序

1. hping3 / wrk：单次 vs 并发
2. traceroute：路由和每跳
3. tcpdump + Wireshark：包时序
4. strace：套接字选项
