# 56 | 套路篇：优化性能问题的一般方法

原文：[time.geekbang.org/column/article/89278](https://time.geekbang.org/column/article/89278)

瓶颈找到，优化方向就有了。系统和应用两边动手，但**最佳位置仍是应用内部**（乱系统调用、烂 SQL 改内核不如改代码）。先看响应时间、吞吐、错误率——这才是终局指标。

避免过早优化：优化加复杂度、伤可维护性。逐步、动态，先满足当前要求，再按分析结果改最痛的那一块。

## 系统

| | 典型招 |
|--|--------|
| CPU | 绑核用缓存、中断多核均摊、Cgroups 限 CPU、核心应用提高优先级 |
| 内存 | 能关就关 Swap；Cgroups 限内存；核心应用降 `oom_score`；大页/内存池少动态分配、少缺页 |
| I/O | SSD/RAID；调度：SSD/VM 用 `noop`，库用 `deadline`；调脏页刷新和限额、dentry/inode 回收倾向；盘隔离、预读、队列长度 |
| 网络 | 加大 socket 缓冲、conntrack、半连接、fd、本地端口；缩短超时/SYNACK 重传/keepalive；端口复用、rp_filter、MTU。网卡 GRO/GSO/RSS/VXLAN 卸载、多队列、加大缓冲。C10M 绕内核：DPDK 用户态轮询，或 XDP 进栈前处理 |

## 应用

- **CPU**：简化代码、算法、异步、编译器优化
- **数据**：缓存、写时复制、加大 I/O 尺寸
- **内存**：大页、内存池预分配
- **网络**：I/O 多路复用、长连接、DNS 缓存
- **模型**：异步、多线程/多进程吃满 CPU
- **架构**：消息队列、CDN、负载均衡，单机活摊到多机
