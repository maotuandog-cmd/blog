可以。你如果是想**从 PostgreSQL 源码角度把 WAL 整条链路串起来**，我建议不要一上来啃 `xlog.c`，而是先建立这条主线：

> **一次数据修改 → 生成 WAL record → 写入 WAL buffer → WAL flush → 数据页落盘 → checkpoint/recovery → standby replay**

下面我按 PG 源码里的实际调用关系讲，主干对 **PG 16/17/18** 都适用。实现细部：[[04-wal-internals]]。

# 1. 先建立一个整体模型

假设执行：

```sql
UPDATE t SET name = 'hello' WHERE id = 1;
```

底层大概经历：

```text
Executor
   │
   ▼
heap_update()
   │
   ├── 修改 shared buffer 中的数据页
   │
   └── XLogInsertRecord()
           │
           ▼
       WAL Buffer
           │
           ▼
       XLogFlush()
           │
           ▼
       WAL segment
       pg_wal/000000...
```

注意一个非常重要的原则：

```text
WAL 必须先于 Data Page 落盘
```

也就是：

```text
WAL LSN = 1000
Data Page 上记录的 PageLSN = 1000

只有 WAL 已经 flush 到 >= 1000，
这个 Data Page 才允许真正落盘。
```

这就是 PostgreSQL 的 **WAL rule**。

# 4. PostgreSQL 并不是直接 memcpy WAL

这是很多人第一次看源码容易误解的地方。

你可能以为：

```c
XLogInsert(...)
```

就是：

```text
malloc WAL
memcpy
write()
```

实际上不是。

PG 把 WAL record 的构造拆成了几个阶段：

```text
XLogBeginInsert()
        │
        ▼
XLogRegisterData()
XLogRegisterBuffer()
        │
        ▼
XLogInsert()
        │
        ▼
XLogInsertRecord()
        │
        ▼
WAL Buffer
```

也就是说：

> **先描述我要记录什么，然后统一组装成 WAL record。**

# 5. XLogRegisterData 是干什么的？

例如 UPDATE 需要记录一些数据：

```c
XLogRegisterData((char *) &xlrec, sizeof(xlrec));
```

意思是：

```text
把这段内存作为 WAL record 的 main data
```

还有：

```c
XLogRegisterBuffer(0, buffer, REGBUF_STANDARD);
```

意思是：

```text
这个 WAL record 和某个 buffer/page 有关系
```

所以一个 WAL record 可能逻辑上长这样：

```text
WAL Record
├── Header
├── xl_heap_update
├── Block 0
│    ├── RelFileNode
│    ├── Block Number
│    └── block image / delta
└── Data
```

# 6. 为什么要 RegisterBuffer？

这是 PostgreSQL WAL 很核心的设计。

例如：

```c
XLogRegisterBuffer(0, buffer, REGBUF_STANDARD);
```

表示：

> 这个 WAL record 修改了这个数据页。

WAL record 里面可以保存：

```text
relation
block number
fork
page image / changed data
```

这样 crash recovery 时：

```text
找到 WAL record
      │
      ▼
知道修改的是哪个 page
      │
      ▼
重新执行修改
```

# 7. Full Page Write 是这里非常重要的一个概念

如果：

```conf
full_page_writes = on
```

那么 checkpoint 后，一个 page **第一次被修改**时，WAL 可能不只是记录：

```text
delta
```

而是：

```text
整个 8KB page image
```

例如：

```text
Page before
+----------------+
|                |
|     old data   |
|                |
+----------------+

        UPDATE

WAL:

+----------------+
| full page image|
|     8KB        |
+----------------+
```

为什么？

因为数据库 page 写盘不是天然原子的。

比如 8KB page：

```text
OS write
   │
   ├── 写了前 4KB
   │
   └── crash
```

磁盘可能得到：

```text
4KB old
4KB new
```

这种 page 叫：

> torn page

恢复的时候，仅靠：

```text
delta WAL
```

不一定能从一个损坏的 page 正确恢复。

所以第一次修改时保存：

```text
完整 page image
```

Recovery：

```text
FPI
 ↓
直接恢复整个 page
```

write / flush / OS cache 必须拆开的细部，以及 FPI 如何把 WAL 撑大，见 [[#30. 必须拆开：FPI、write LSN、flush LSN、OS cache]]。FPI 与 InnoDB doublewrite 的关系、例外（`full_page_writes=off`、WAL 损坏）见 [[#31. FPI 不是 doublewrite，但解决同类 torn page 问题]]。

# 8. WAL record 生成以后，最重要的是 LSN

假设：

```c
XLogInsert(...)
```

返回：

```text
LSN = 0/12345678
```

这个 LSN 非常重要。

你可以把它理解成：

> WAL 日志流里的全局位置。

例如：

```text
WAL

0/10000000
0/10000100
0/10000500
0/10001000
       ↑
       UPDATE record
```

# 9. PageLSN 是 WAL 和数据页之间的纽带

数据页的 page header 里有：

```c
pd_lsn
```

对应：

```c
PageGetLSN(page)
```

当 page 被修改以后：

```c
PageSetLSN(page, recptr);
```

也就是：

```text
Data Page
+-----------------------+
| Page Header           |
|                       |
| pd_lsn = 0/12345678   |
+-----------------------+
| tuple                 |
| tuple                 |
+-----------------------+
```

然后 WAL：

```text
WAL LSN = 0/12345678
```

于是建立：

```text
PageLSN <= WAL flushed LSN
```

这个关系就是 crash recovery 的核心之一。

# 10. 为什么 WAL 必须先写？

假设：

```text
PageLSN = 1000
```

然后：

```text
WAL 1000
```

还只在内存里。

此时如果直接：

```text
fsync(data page)
```

然后：

```text
crash
```

磁盘状态：

```text
Data Page:
    PageLSN = 1000

WAL:
    没有 1000
```

Recovery：

```text
发现 page 已经是 LSN 1000
但 WAL 里根本没有这条日志
```

就无法保证一致性。

所以必须：

```text
WAL 1000
   ↓
WAL flush
   ↓
Data Page write
```

这就是：

> **Write-Ahead Logging**

# 11. XLogInsert 到底把东西放哪里？

这里进入 PostgreSQL 最核心的 WAL buffer。

PG 有：

```text
shared memory
```

里面有 WAL buffers：

```conf
wal_buffers
```

例如：

```text
WAL Buffer

+------+------+------+------+------+
|      |      |      |      |      |
+------+------+------+------+------+
                 ↑
              current
```

`XLogInsertRecord()` 最终会把 WAL record 放进 WAL buffer。

源码中你会不断看到：

```c
XLogCtl
```

这个结构非常值得重点看。

大概可以理解成：

```text
XLogCtl
├── Insert
├── Write
├── Flush
├── ckpt
├── ...
```

其中最重要的几个 LSN：

```text
insert LSN
write LSN
flush LSN
```

# 12. 这三个 LSN 一定要搞懂

这是读 WAL 源码的核心。

假设：

```text
insert = 5000
write  = 4000
flush  = 3000
```

意味着：

```text
WAL buffer 中已经生成到 5000

磁盘 WAL 文件已经 write 到 4000

磁盘 WAL 已经 flush/fsync 到 3000
```

所以：

```text
insert >= write >= flush
```

可以粗略理解成：

```text
                 WAL Buffer
                     │
                     │
INSERT               ▼
5000 ─────────────────────────────
                     │
                     │ write()
                     ▼
WRITE                4000
                     │
                     │ flush/fsync
                     ▼
FLUSH                3000
                     │
                     ▼
                 durable WAL
```

这三个概念以后你看：

```sql
SELECT * FROM pg_stat_wal;
```

或者 replication：

```text
write_lsn
flush_lsn
replay_lsn
```

都会非常有帮助。

注意：这里的 write **不能**理解成「OS cache 的位置」。`write()` 通常经过 page cache，但 **write LSN 表示的是 PostgreSQL 已经把 WAL 写到 WAL 文件的哪个 LSN**；**flush LSN 才是已经要求底层持久化到哪里**。严格拆开见 [[#30. 必须拆开：FPI、write LSN、flush LSN、OS cache]]。

# 13. XLogFlush 又是什么？

事务提交时非常关键。

例如：

```text
UPDATE
  ↓
XLogInsert()
  ↓
LSN = 5000
```

但是此时：

```text
WAL 5000
```

可能还只在 shared WAL buffer。

然后：

```sql
COMMIT;
```

提交的时候必须保证：

```text
WAL LSN >= transaction commit record
```

已经持久化。

所以最终会走：

```c
XLogFlush(commit_lsn);
```

大致：

```text
XLogFlush()
     │
     ▼
检查 Flush 已经到哪里
     │
     ├── 已经 >= target
     │       └── return
     │
     └── 没到
           │
           ▼
       XLogWrite()
           │
           ▼
       write()
           │
           ▼
       issue_xlog_fsync()
```

# 14. COMMIT 的 WAL 又是怎么来的？

这里还有一个非常重要的点：

```text
UPDATE WAL
```

和：

```text
COMMIT WAL
```

不是一回事。

比如：

```sql
BEGIN;

UPDATE t SET ...;

COMMIT;
```

WAL 可能：

```text
LSN 1000
  HEAP UPDATE

LSN 1100
  HEAP UPDATE

LSN 1200
  HEAP UPDATE

LSN 1300
  XLOG_XACT_COMMIT
```

然后：

```text
XLogFlush(1300)
```

只有：

```text
1300 durable
```

这个事务才真正满足 WAL durability。

# 15. 那数据页什么时候写磁盘？

这里很多人会产生一个误解：

> COMMIT 是不是把数据 page 一起写盘？

**不是。**

PG 的：

```text
WAL
```

和：

```text
Data Page
```

是两个完全不同的 IO 路径。

COMMIT：

```text
主要保证 WAL flush
```

Data Page：

```text
什么时候脏页被 Buffer Manager / bgwriter / checkpointer 写出去
```

可能晚很多。

例如：

```text
COMMIT
  ↓
WAL fsync
  ↓
返回客户端

此时：

shared_buffers:
    page = dirty

磁盘:
    page = old
```

完全可以。

# 16. 那脏页落盘的时候怎么保证 WAL rule？

关键在：

```c
FlushBuffer()
```

大致在：

```text
src/backend/storage/buffer/bufmgr.c
```

写一个 dirty buffer 前，会检查：

```text
PageLSN
```

然后：

```c
XLogFlush(recptr);
```

逻辑类似：

```text
FlushBuffer(buffer)
       │
       ▼
PageLSN = 5000
       │
       ▼
检查 WAL flush position
       │
       ▼
如果 WAL < 5000
       │
       ▼
XLogFlush(5000)
       │
       ▼
写 data page
```

所以：

```text
WAL durable
       ↓
Data Page durable
```

这个顺序必须成立。

# 17. Checkpoint 又是什么？

Checkpoint 可以理解成：

> 给 recovery 设置一个“已知安全点”。

例如 WAL：

```text
LSN

100
200
300
400
500
600
700
```

Checkpoint 开始：

```text
CHECKPOINT
```

它会尽量把：

```text
dirty buffers
```

写到磁盘。

最后得到：

```text
checkpoint REDO point = 500
```

于是 crash recovery：

```text
从 checkpoint
     ↓
500
     ↓
开始 replay
     ↓
600
     ↓
700
```

而不是：

```text
从 WAL 文件最开始
```

全部 replay。

还是：

```text

```

重点函数：

```c
CreateCheckPoint()
```

你可以沿着这个函数往下读。

大致流程：

```text
CreateCheckPoint()
      │
      ├── 获取 checkpoint LSN
      │
      ├── flush dirty buffers
      │
      ├── 写 checkpoint record
      │
      └── 更新 control file
```

不过真实源码比这个复杂很多，包括：

```text
WAL flush
buffer checkpoint
replication
archive
timeline
shutdown checkpoint
restartpoint
```

# 19. Crash Recovery 怎么读取 WAL？

数据库启动时：

```text
StartupXLOG()
```

然后进入 recovery。

核心组件：

```text
XLogReader
```

负责：

```text
从 pg_wal 读取 WAL record
```

然后：

```text
ReadRecord()
      ↓
XLogReadRecord()
      ↓
Decode WAL record
```

之后进入 replay：

```text
Apply WAL
```

不同资源管理器：

```text
RM_HEAP_ID
RM_BTREE_ID
RM_XACT_ID
RM_SMGR_ID
...
```

都有自己的 redo 函数。

# 20. 例如 HEAP UPDATE 的 replay

原来：

```text
heap_update()
```

生成：

```text
XLOG_HEAP_UPDATE
```

Recovery 时：

```text
XLOG_HEAP_UPDATE
       ↓
heap_redo()
       ↓
heap_xlog_update()
```

大致：

```text
WAL
 │
 ▼
heap_redo()
 │
 ▼
找到 relation/block
 │
 ▼
ReadBuffer()
 │
 ▼
修改 page
 │
 ▼
PageSetLSN()
 │
 ▼
MarkBufferDirty()
```

最终：

```text
recovery page
```

恢复成 WAL 描述的状态。

# 21. Recovery 为什么看 PageLSN？

这是另外一个特别漂亮的设计。

假设 WAL：

```text
LSN = 5000
```

对应 page：

```text
PageLSN = 5000
```

Recovery 又读到这条 WAL：

```text
WAL LSN = 5000
```

它发现：

```text
PageLSN >= WAL LSN
```

说明：

> 这个 WAL record 对 page 的修改已经做过了。

于是可以：

```text
skip
```

而不是重复执行。

所以 recovery 中经常看到类似：

```c
if (PageGetLSN(page) >= lsn)
    ...
```

这就是 WAL replay 的幂等性/重复恢复保护的重要基础。

# 22. Replica 的 WAL 流程又是什么？

如果是 Streaming Replication：

```text
Primary
```

产生：

```text
WAL
```

然后：

```text
WAL Sender
    ↓
network
    ↓
WAL Receiver
    ↓
standby pg_wal
    ↓
Startup Process
    ↓
Replay
```

整体：

```text
                 Primary
                    │
             XLogInsert
                    │
                    ▼
                WAL Buffer
                    │
             XLogWrite/Flush
                    │
                    ▼
               WAL segment
                    │
                    ▼
               WAL Sender
                    │
                  TCP
                    │
                    ▼
              WAL Receiver
                    │
                    ▼
              standby pg_wal
                    │
                    ▼
              Startup Process
                    │
                    ▼
                 redo()
                    │
                    ▼
              shared_buffers
```

所以：

> **Streaming Replication 本质上就是把 primary 的 WAL record 流给 standby，然后 standby replay。**

# 30. 必须拆开：FPI、write LSN、flush LSN、OS cache

第 7、12、13 节已经有 FPI 和三个 LSN 的粗线。这里把 **write LSN / flush LSN / OS cache / 磁盘持久化** 严格分开——这是 PG WAL 最容易混淆的地方。18.6 源码里对应 `XLogCtl` 的 `logInsertResult` / `logWriteResult` / `logFlushResult`。

## 30.1 FPI 是什么？

FPI = **Full Page Image**，全页镜像。默认：

```conf
full_page_writes = on
```

正常 UPDATE 的 WAL 不必记下整个 8KB page，只记 delta：

```text
"对 block 123 做了这个修改"
```

问题是：数据页落盘**不一定原子**。8KB 写一半 crash：

```text
原来：AAAAAAAA
写一半：AAAA
         BBBB
```

磁盘上就是 **torn page**。若 WAL 里只有「把 A 改成 B」，recovery 拿到撕裂页后，没法可靠地继续做增量 redo。

所以某些情况下，WAL 会带上**整页 8KB**：

```text
WAL Record
+-------------------+
| WAL header        |
+-------------------+
| relation / block  |
+-------------------+
| Full Page Image   |
|      8KB          |
+-------------------+
| update delta      |
+-------------------+
```

这就是 FPI。Recovery 时直接用镜像盖掉整页，再（如有需要）套后面的增量。

### 什么时候产生 FPI？

**不是每次 UPDATE 都产生。** 粗线是：

> **checkpoint 之后，一个 page 第一次被修改时，可能需要 FPI。**

```text
checkpoint
    ↓
page A 第一次修改  → FPI
page A 第二次修改  → 通常不再 FPI
page B 第一次修改  → FPI
```

源码判断大致看 page 的 LSN 是否 ≤ 当前 `RedoRecPtr`（再叠加 `full_page_writes` / backup）。因此：

```text
checkpoint 越频繁
    → 更多 page 被重新视为「checkpoint 后首次修改」
    → FPI 增多
    → WAL 增多
```

排查 **WAL 暴增** 时，FPI 和 `checkpoint_timeout` / `max_wal_size` 是第一嫌疑。详见第 26 节。

---

## 30.2 WAL Flush 会不会先到 OS cache？

**会经过 OS cache 的是 `write()`，不是 `flush` 这个动作本身。**

```text
PostgreSQL WAL Buffer
        │
        │ write()
        ▼
OS Page Cache / Kernel Buffer
        │
        │ fsync() / fdatasync()   ← 这才是 flush
        ▼
Storage Device
        │
        ▼
持久化介质
```

> 「wal flush 也会先到 OS cache，这个就是 write 吗？」——**基本方向对，但 flush ≠ write。**

`write LSN` **不是**「OS cache 里的位置」。它表示：**PostgreSQL 已经把 WAL 写到 WAL 文件的哪个 LSN**（通常经过 page cache，对 kernel 可见，对 crash 仍不安全）。

---

## 30.3 用三个 LSN 看同一条 WAL

假设：

```text
insert LSN = 2000
write  LSN = 1000
flush  LSN = 800
```

```text
PG WAL Buffer        已经生成到 2000     ← insert
WAL File / OS        已经 write 到 1000  ← write（多半还在 page cache）
Storage durable      只保证到 800        ← flush
```

通常：

```text
insert >= write >= flush
```

| 名字 | 18.6 字段 | 含义 |
|---|---|---|
| insert LSN | `logInsertResult` | WAL 已经在 buffer 里构造到哪里 |
| write LSN | `logWriteResult` | 已经 `write()` 到 WAL 文件哪里 |
| flush LSN | `logFlushResult` | 已经要求底层把 WAL **持久化**到哪里 |

---

## 30.4 `write()` 到底干了什么？

源码最终类似：

```c
write(fd, wal_buffer, nbytes);
```

Linux 下通常：

```text
PostgreSQL → VFS → Page Cache（标 dirty）→ write LSN 可以往前推
```

此时 **不能**认为 WAL 已经真正持久化。若 `write=1000`、`flush=800`：OS 看见文件内容到 1000，可靠持久化只保证到 800。机器在 fsync 前断电，1000 可能丢。

---

## 30.5 `XLogFlush()` 做什么？

COMMIT 记录在 LSN 1200 时：

```c
XLogFlush(1200);
```

目标 **不是**「把 1200 写到 OS cache」，而是：

> **确保 WAL 至少持久化到 1200。**

它是 **durability barrier**：

```text
若 flush LSN 已经 ≥ 1200  → 直接返回（可能什么都不干）
否则
    持 WALWriteLock
    内部调用 XLogWrite()     ← 把缺的那段 write 出去
    issue_xlog_fsync()       ← fsync / fdatasync
    flush LSN ≥ 1200
```

不要把 `XLogWrite` 和 `XLogFlush` 画成两条并列管道。Flush 需要干活时**调用** Write；Write 在切 WAL 段时自己也会 fsync。

默认同步提交下，`flush >= commit LSN` 之后 COMMIT 才返回客户端。此时 data page 仍可只在 `shared_buffers` 里。

---

## 30.6 为什么要拆 write 和 flush？

如果每来一条 WAL 都 write + fsync，IOPS 会很难看。PG 把多个事务的 WAL 聚在一起：

```text
Txn A / B / C / D
        ↓
   WAL Buffer
        ↓
   一次 write
        ↓
   一次 fsync
        ↓
   A/B/C/D 一起 durable
```

这是 group commit 的基础。`XLogFlush` 还会尽量把目标往后捎（piggyback），让一次 fsync 覆盖更多 LSN。

---

## 30.7 再把 COMMIT 串起来

```sql
BEGIN;
UPDATE t SET a = 100;
COMMIT;
```

```text
UPDATE
  → XLogInsert()           insert LSN = 1000   （HEAP WAL，可能带 FPI）
  → COMMIT record          commit LSN = 1100
  → XLogFlush(1100)
       → 如有必要 XLogWrite()   write LSN → 1100
       → fsync / fdatasync      flush LSN → 1100
  → COMMIT 返回客户端

Data Page：可能还在 shared_buffers，完全正常
```

`synchronous_commit=off` 时 COMMIT 不在这条路径上立刻等 flush，而是登记 async LSN，交给 walwriter 稍后 `XLogBackgroundFlush()`。

## 30.8 把 FPI 和这条链连上

checkpoint 之后第一次改 page A：

```text
普通 UPDATE WAL：header + block info + 几十/几百字节 delta
带 FPI：          上面那些 + 整页 8KB
```

所以 WAL generation 突然很高时，先问：

```text
checkpoint 是否很频繁？
FPI 是否很多？
full_page_writes 是否 on？
```

---

## 30.9 只要记住这一张图

```text
                 WAL 生成
                    │
                    ▼
              WAL Buffer
                    │
               insert LSN
                    │
                 write()
                    ▼
              OS Page Cache
                    │
                write LSN          ← 已写入 WAL 文件（通常未持久化）
                    │
                fsync()
                    ▼
             Durable Storage
                    │
                flush LSN          ← 已持久化
                    ▼
             COMMIT 可以返回


Data Page 是另一条线：

       shared_buffers dirty page
             │
          FlushBuffer
             │  PageLSN = 1200
             ▼
       XLogFlush(1200)             ← WAL durability barrier
             │
        WAL durable
             │
        write Data Page
```

**核心关系：**

```text
PageLSN <= WAL Flush LSN     才能安全写出这个 data page
```

而：

```text
insert LSN ≠ write LSN ≠ flush LSN
```

分别是：

```text
生成了多少
写到 WAL 文件多少（多半经 OS cache）
真正持久化多少
```

三个搞清楚以后，再看 `XLogInsertRecord()` 和 `XLogWrite()` 会顺很多。

一句话：

> **`write()` 把 WAL buffer 交给内核（推进 write LSN）；`flush/fsync` 才要求介质持久化（推进 flush LSN）。FPI 是 checkpoint 后该页首次修改时，为防 torn page 而打进 WAL 的整页镜像。**

**关键限定：** FPI **不是** PostgreSQL 的 doublewrite buffer，但它解决的是和 doublewrite 很相似的一类问题：防止数据页 torn write。对照、例外、以及和 PageLSN 怎么串，见下一节。

---

# 31. FPI 不是 doublewrite，但解决同类 torn page 问题

> **FPI 不是 PostgreSQL 的 “doublewrite buffer”，但它解决的是和 doublewrite 很相似的一类问题：防止数据页 torn write。**

PG 的思路：

```text
checkpoint
    ↓
page A 第一次修改
    ↓
WAL 中记录 page A 的完整镜像 FPI
    ↓
后续修改 page A
    ↓
通常只记录增量 WAL
```

Crash 后，如果磁盘上的 page A 是撕裂的，Recovery 用 FPI 把 page A 恢复成一个完整的一致版本，再继续 replay 后面的 WAL。

---

## 31.1 不是每次修改都 FPI

```text
checkpoint
    ↓
A: FPI + update1
    ↓
A: update2          ← 普通增量 WAL
    ↓
A: update3
```

而 **不是**：

```text
checkpoint
    ↓
A: FPI
A: FPI
A: FPI
```

---

## 31.2 InnoDB doublewrite 在干什么

```text
Buffer Pool → Doublewrite Buffer → Data File
```

data page 写一半 crash，recovery 从 doublewrite area 拿出完整页盖回去。这是 **写 data file 时** 再备一份完整页。

---

## 31.3 PG 没有传统 doublewrite buffer

完整 page image 放进 **WAL**：

```text
旧 page A  --UPDATE--> 新 page A
                │
                ▼
WAL Record
+-----------------------+
| Full Page Image 8KB   |
+-----------------------+
| update information    |
+-----------------------+
```

然后 data page 日后才写盘。FPI 是 **修改发生时** 打进日志流，不是 flush data page 时再抄一份。

---

## 31.4 Crash 时 torn write 怎么救

磁盘上可能：

```text
Page A：前半新、后半旧
```

Recovery：

```text
torn page → 用 FPI(Page A) 盖成完整页 → replay 后续 update2 / update3 / ...
```

所以：

> **FPI 是 crash recovery 时这个 page 的基准快照（replay 起点），不是 checkpoint 给全库做的 snapshot。**

---

## 31.5 为什么 checkpoint 是关键？

Checkpoint **不是**「保存整个数据库」。它建立一个 **recovery 基准点**（redo LSN）。

```text
LSN 100  checkpoint
    110  page A update   ← A 首次修改 → FPI
    120  page B update   ← B 首次修改 → FPI
    130  page A update   ← 增量
    140  page C          ← 没改过，磁盘上的 C 就是 checkpoint 时的状态，不需要 FPI
```

Recovery 从 checkpoint 起：找到该页的 FPI → 恢复完整状态 → 继续 replay 这页后面的 WAL。

**第一次修改才需要 FPI**，是因为：从 checkpoint 往后再遇到这个 page 的第一条 WAL 时，必须有一个可靠的 page 基准。从未改过的页，磁盘上的页本身就是基准。

---

## 31.6 会不会有特殊情况导致 FPI 救不了？

**有，而且很关键。** 前提是：

```text
FPI 本身已经可靠地存在于 durable WAL 中
```

所以整条链是：

```text
Data Page 可能 torn
    → WAL 里有 FPI
    → WAL 本身必须 durable（flush LSN）
    → Recovery 读 FPI、校验、恢复 page
```

这也是 WAL durability 必须早于 data page 的原因之一。

### `full_page_writes = off`

就不能靠 FPI 防 torn page。checkpoint 后只有增量 WAL + 撕裂的 data page，recovery 可能无法正确恢复。因此默认 `on`，官方文档明确把它和 partial page write / torn page 绑在一起。

### WAL 本身损坏

data page torn、FPI 所在 WAL record 也坏（CRC 不过、record 不完整）→ 没办法。不能理解成「开了 `full_page_writes`，page 永远不会坏」。更准确：

> **在正常硬件和存储语义下，PG 利用 WAL 中的 FPI，使 recovery 能从 torn data page 恢复。**

---

## 31.7 为什么 FPI 自己不怕 torn write？

8KB data page 会 torn，FPI 也是约 8KB，为什么 FPI 更可靠？

因为 FPI **不是** `write(fd, 8KB page)` 另写一块 data file，而是嵌在 **WAL stream** 里：

```text
WAL record header / WAL page header / CRC / LSN / record length
write →（必要时）fsync
Recovery 读 WAL 时校验；CRC 不过则无法继续正常 replay
```

WAL 自己按 WAL page 组织，record 可以跨 page；跨页有专门的 page/record header。所以：

```text
FPI → WAL Record → WAL page → WAL segment → WAL durability
```

不是「再找一个普通 data page 当 doublewrite」。

底层 sector 常是 512B / 4KB，而 `BLCKSZ` 默认 8KB，一页可能被拆成多次介质写——这正是需要 FPI 的原因。即使某些存储宣称 8KB atomic write，PG 也不能假设所有设备都如此。

---

## 31.8 不要和 `wal_log_hints` 搞混

```conf
wal_log_hints = on
```

影响的是 **hint bit** 这类「不是 INSERT/UPDATE/DELETE 语义」的 page 修改，要不要走 WAL（进而可能打 FPI）。checksum 场景下常和 `full_page_writes` 一起出现。`full_page_writes` 管 torn page；`wal_log_hints` 管 hint 修改是否进 WAL。

---

## 31.9 FPI 不是「备份 page」

FPI **不是**：每个 page 都备份一份；也 **不是**：checkpoint = 给所有 page 做 snapshot。

而是：

> **在 WAL recovery 语义下，为 checkpoint 之后首次修改的 page，提供一个可以作为 replay 基准的完整 page image。**

也不要简单理解成：

```text
FPI = 把最终 data page 完整 dump 一遍
```

源码里它就是 **WAL record 中的 full-page image**（还可以按 `REGBUF_STANDARD` 抠 hole）。具体 FPI 和操作记录怎么拼、PageLSN 怎么设，是 `XLogRecordAssemble()` 的细节。

---

## 31.10 和 Doublewrite 对照

| | PostgreSQL FPI | InnoDB Doublewrite |
|---|---|---|
| 核心目的 | 防 torn page | 防 torn page |
| 保存位置 | WAL | Doublewrite area |
| 保存内容 | 完整 page image | 完整 page |
| 何时产生 | checkpoint 后该页**首次修改**时 | **flush data page** 时先写 doublewrite |
| Recovery | 从 WAL 恢复 | 从 doublewrite 恢复 |
| 是否等价 | **不是** | **不是** |

```text
InnoDB:     Data Page → Doublewrite → Data Page
PostgreSQL: Data Page 修改 → FPI 进 WAL →（日后）写 Data Page
```

PG 把「防 torn page 的完整 page image」放进 WAL 体系里解决。

---

## 31.11 抗 crash 的三层

```text
第一层：WAL
  「修改发生过什么」不会因为 data page 尚未落盘而丢失

第二层：FPI
  data page torn write 时，recovery 有完整 page 作为恢复基础

第三层：PageLSN
  recovery 判断某条 WAL 对这个 page 是否已经应用
```

```text
        WAL
         │
  ┌──────┴──────┐
  │             │
normal WAL     FPI
  │        torn page recovery
  └──────┬──────┘
         ▼
      Recovery + PageLSN → 正确重放
```

所以 PageLSN 到这里就串起来了：

> **FPI 给 page 一个可靠的恢复基准；后续增量 WAL 把这个 page 重放到 crash 前状态；PageLSN 告诉 recovery 这个 page 已经重放到 WAL 的哪个位置。**

---

## 31.12 下一步对着源码看什么

18.6 里，一个 buffer 要不要打 FPI，是在 `xloginsert.c` 的 `XLogRecordAssemble()` 里决定的。注册 buffer 时这些 flag 值得逐个看（`src/include/access/xloginsert.h`）：

```text
REGBUF_WILL_INIT    本条 WAL replay 时会整页重建，不必为旧内容打 FPI
REGBUF_STANDARD     标准页布局，FPI 可以去掉 pd_lower..pd_upper 之间的 hole
REGBUF_KEEP_DATA    即使打了 FPI，仍然附带增量 data
REGBUF_FORCE_IMAGE  强制打 FPI（例如某些 repair / 一致性检查路径）
```

再叠加 `doPageWrites`（`full_page_writes` 或正在 backup）以及 **页 LSN ≤ 当前 `RedoRecPtr`**。这部分一旦看懂，FPI 就从概念落到源码。

---

# 32. 主线之外：按重要程度还没展开的 WAL

前面只讲了最核心的：

```text
数据修改 → FPI → WAL buffer → write/flush → recovery
```

要从**源码**和**运维**两边真正吃透 WAL，还有一大块没覆盖。下面按重要程度列地图，不是把每一块讲完。

已经吃过的：WAL Record 粗结构、FPI、PageLSN、WAL Buffer 概念、insert/write/flush LSN、WAL Rule、Crash Recovery 粗线。

---

## 32.1 WAL Record 的真实结构

目前只说了 Header / Block Reference / FPI / Main Data。源码里还有：

```text
XLogRecord
XLogRecordBlockHeader
XLogRecordDataHeader
```

以及：

```text
rmid / info / xl_tot_len / xl_xid / xl_prev
```

`rmid` + `info` 决定：**这条 WAL 是谁生成的，该由哪个 rmgr redo**。例如 `RM_HEAP_ID`、`RM_BTREE_ID`、`RM_XACT_ID`、`RM_SMGR_ID`、`RM_STANDBY_ID`。这是理解 recovery 分发的关键。

---

## 32.2 WAL Insert：并发写 WAL

多个 backend 同时 `XLogInsertRecord()`，不可能一个全局大锁串行写完。源码里是：

```text
XLogCtlInsert
WALInsertLock（insertion locks / reservation / slots）
```

这部分决定：几十、几百个 backend 怎么并发生成 WAL。看 `XLogInsertRecord()` 一定会遇到。

---

## 32.3 WAL Buffer 的环形结构

`wal_buffers` 不是无限增长的 malloc，而是环形区域。需要搞清：

```text
curridx / xlblocks / XLogCtlInsert / WAL buffer page
```

一页什么时候能复用：**对应 WAL 必须已经 write/flush 到足够位置。** 否则就是 WAL buffer pressure。

---

## 32.4 WAL Page ≠ Data Page

```text
BLCKSZ          数据页，默认 8KB
XLOG_BLCKSZ     WAL stream 里的 page
```

WAL 自己有 `XLogPageHeaderData` / `XLogLongPageHeaderData`：magic、timeline、page address。所以 WAL 也能被 recovery 检查，不是「另一堆 8KB heap page」。

---

## 32.5 WAL Record 跨 WAL Page

一条 record 可以跨 WAL page N 和 N+1。`XLogReader` 负责重新组装。理解 WAL corruption、CRC、`pg_waldump` 时必须记住这一点。

---

## 32.6 WAL Segment 文件名

```text
pg_wal/00000001000000000000000A
        TLI      log      seg
```

例如 Timeline=1、Log=0、Segment=10。不要把它们理解成普通「日志文件编号」。

---

## 32.7 Timeline

Primary crash / standby promote 会分叉出新 timeline。PITR、Failover、Promotion、Fork 都靠它。识别一条 WAL 路径时：**LSN 不够，还要 Timeline。**

---

## 32.8 Replication Slot

Slot 告诉 PG：某些 WAL 消费者可能还要用，**不能 recycle**。slot 长时间不消费 → `pg_wal` 膨胀 → 爆盘。这是运维经典事故。

---

## 32.9 Archiving

```text
WAL generated → written → flushed → segment completed → archive_command → archive storage
```

这是 PITR 的基础，不只是 Primary → Standby。

---

## 32.10 PITR

Point-In-Time Recovery = **Base Backup + WAL Archive**，用 `recovery_target_time` 等停在目标 LSN。WAL 不只是 crash recovery 日志，也是 PostgreSQL 的时间机器。

---

## 32.11 Synchronous Replication

本地 COMMIT 的 `XLogFlush` 之外，还可能等 standby 的 receive / write / flush / replay。形成不同 durability：local flush、remote write、remote flush、remote replay。直接决定 commit latency、replication latency、data loss window。

---

## 32.12 `synchronous_commit` 的几个模式

```text
off            不等本机 WAL durable（walwriter 稍后刷）
local          本机 WAL durable
remote_write   standby 已 write
on             默认同步：有同步 standby 时等到 remote flush
remote_apply   standby 已 replay
```

具体语义还要结合同步 standby 配置，不能理解成「等级越高越好」。

---

## 32.13 Group Commit

100 个事务不必 100 次 fsync。`XLogFlush()`、`WaitXLogInsertionsToFinish()` 以及等待队列，把多个 commit LSN 捎在一次 write+fsync 上。

---

## 32.14 WAL 写入和 WAL Flush 是两个性能问题

```text
insert=100GB  write=100GB  flush=80GB   → fsync 跟不上（storage latency）
insert=100GB  write=80GB   flush=80GB   → write 跟不上（wal_buffers / contention / 带宽）
```

排查不能只看 WAL generated，要看 **insert / write / flush 之间的距离**。

---

## 32.15 WAL Compression

`wal_compression` 主要压 **FPI**（8KB → 可能几 KB）。WAL volume ↓，CPU ↑。WAL 很大且 CPU 有余量时值得看。

---

## 32.16 `wal_level`

```text
minimal   本地 crash recovery
replica   物理复制 / PITR
logical   逻辑解码需要更多信息
```

直接决定 WAL 里要记录什么。

---

## 32.17 Logical Decoding

物理复制：WAL → standby replay。逻辑复制：WAL → decode → INSERT/UPDATE/DELETE。涉及 `ReorderBuffer`、`SnapBuild`、`LogicalDecodingContext`。Debezium / CDC 走这里。

---

## 32.18 WAL 和 MVCC / XID

heap update 不只记 page change，还带 XID；提交是 `XLOG_XACT_COMMIT`。Recovery 后 tuple 可见性 = **WAL + CLOG/pg_xact + XID + MVCC**。

---

## 32.19 WAL 和 Hint Bit

hint bit 也改 page，但不是普通 UPDATE。可能不产生普通 WAL，于是有 `wal_log_hints`，并和 `full_page_writes`、data checksums、FPI 缠在一起。

---

## 32.20 Checksum 和 WAL

`data_checksums=on` 时读页可发现 corruption。层次不同：

```text
FPI        recovery 时处理 torn page（修复基准）
checksum   检测 page 是否损坏（不是修复机制）
```

---

## 32.21 WAL Recycling

segment 会 reuse / recycle / remove，受 checkpoint、replication slots、archive、replication、`wal_keep_size` 约束。`pg_wal` 目录大小 ≠ 「最近产生了多少 WAL」。

---

## 32.22 `max_wal_size` 不是硬上限

`max_wal_size=10GB` 是 checkpoint 触发和 WAL 保留的**目标尺度**，不是天花板。slot / archive / 长事务 / backup 要求保留时，`pg_wal` 可以到 50GB 甚至更多。

---

## 32.23 Restart LSN

slot 的 `restart_lsn`：从消费者角度看，这之后的 WAL 仍可能要留。排查「`pg_wal` 为什么不释放」的关键指标之一。

---

## 32.24 `pg_waldump`

把 WAL Record 结构直接打出来：rmgr、record type、lsn、prev、tx、len、block、FPW。适合把 **源码 ↔ WAL record ↔ 磁盘文件** 对上。

```bash
pg_waldump 000000010000000000000001
```

---

## 32.25 Recovery 还没钉死的几个词

```text
REDO / UNDO / Consistency Point / Replay LSN
End-of-Recovery / Timeline Switch / RestartPoint
```

PG crash recovery 主要是 **REDO**：从 checkpoint 读 WAL、重新执行修改。事务回滚（UNDO 语义）和 crash recovery 不是一回事。

---

## 32.26 建议的源码学习顺序

```text
                    PostgreSQL WAL
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   WAL Generation    WAL Storage       WAL Recovery
        │                │                │
 XLogInsertRecord    WAL Buffer       XLogReader
 WAL Record          XLogWrite        rmgr redo
 FPI                 XLogFlush        PageLSN
 WAL Insert Lock     fsync            Replay
                     WAL Segment
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
          Archive      Replica      Slot
            PITR       Streaming    Retention
```

**以现在的问题深度，下一步最该打开的黑盒是 `XLogInsertRecord()`：**

```text
heap_update()
  → XLogBeginInsert()
  → XLogRegisterBuffer() / XLogRegisterData()
  → XLogInsert()
  → XLogInsertRecord()     ← 这里到底发生了什么？
```

尤其：

```text
XLogCtlInsert
WALInsertLock
xl_prev
XLogRecord / XLogRecordBlockHeader
REGBUF_FORCE_IMAGE / REGBUF_STANDARD / REGBUF_WILL_INIT
```

这一段吃透后，才是真正明白 **一个 UPDATE 怎么变成 `pg_wal` 里的一串二进制**，而不只是知道 WAL 的概念。
