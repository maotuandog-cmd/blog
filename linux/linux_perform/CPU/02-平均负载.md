# 02 | 到底应该怎么理解「平均负载」？

原文：[time.geekbang.org/column/article/69618](https://time.geekbang.org/column/article/69618)

## 一句话

**平均负载 ≠ CPU 使用率。**  
它是单位时间内「可运行（R）+ 不可中断（D）」的平均活跃进程数，理想值约等于 **逻辑 CPU 个数**。

## 怎么读 uptime

```text
load average: 0.63, 0.83, 0.88
              1分钟  5分钟  15分钟
```

| 对比 | 含义 |
|------|------|
| 三个值差不多 | 负载平稳 |
| 1 分钟 ≪ 15 分钟 | 最近在降 |
| 1 分钟 ≫ 15 分钟 | 最近在升，持续观察 |
| 高于 CPU 个数 | 已经过载 |

先数核：

```bash
nproc
grep 'model name' /proc/cpuinfo | wc -l
```

经验：负载持续高于 **CPU 个数的 70%** 就要查。更靠谱的是看历史趋势（翻倍再查），不要死磕一个绝对值。  
评估用的是 **逻辑核**（含超线程），不是物理核。

## 负载高的三种来源

| 来源 | 负载 | CPU 使用率 | iowait |
|------|------|------------|--------|
| CPU 密集 | 升 | 升（一致） | 低 |
| I/O 密集（大量 D） | 升 | 不一定高 | 常升高 |
| 太多进程抢 CPU | 升 | 高，且 %wait 高 | 低 |

## 实验（2 核机器，装 stress + sysstat）

三个终端：压测 / `watch -d uptime` / `mpstat` 或 `pidstat`。

**场景一：CPU 打满**

```bash
stress --cpu 1 --timeout 600
watch -d uptime          # 1 分钟负载趋向 1
mpstat -P ALL 5          # 某一核 %usr=100, iowait=0
pidstat -u 5 1           # 定位到 stress
```

**场景二：I/O 压力**

```bash
stress -i 1 --timeout 600
mpstat -P ALL 5 1        # iowait 升高
pidstat -u 5 1           # 能看到 stress 的 %system
pidstat -d 5 1           # 更直接看进程 IO（作者后补）
```

作者置顶：`stress -i` 走的是 `sync()`，新虚拟机缓冲区小，可能只抬高 **%sys**、抬不高 iowait。改用 **stress-ng** 更容易打出 IO。

**场景三：进程数远超核数**

```bash
stress -c 8 --timeout 600   # 2 核上跑 8 个
uptime                      # 负载可到 ~8
pidstat -u 5 1              # 每个进程 %wait 约 75%
```

`pidstat` 的 **%wait** 要 sysstat ≥ 11.5.5（老 CentOS yum 包没有）。

## 排查顺序

1. `uptime` / `top` 看 1/5/15 分钟趋势  
2. `nproc` 判断是否过载  
3. `mpstat -P ALL 1` 看 us / sy / wa / st  
4. `pidstat -u 1` 找 CPU；`pidstat -d 1` 找 IO；`ps -eo pid,stat,wchan,comm` 看 D 状态

## 小结

- 负载看的是「有多少活在排队或卡在不可中断」  
- 只看 load 找不到瓶颈，必须拆 us / wa / 等待队列  
- 工具：`uptime`、`mpstat`、`pidstat`、`stress`
