继续。这里我们进入 **Shared Buffer 最核心的一段：`BufferAlloc()` 到 victim selection**。

上一节我们停在：

```text
ReadBuffer_common()
        │
        ▼
    Buffer lookup
        │
   ┌────┴────┐
   │         │
  HIT       MISS
   │         │
   ▼         ▼
 Pin      BufferAlloc()
```

这次我们重点搞懂：

> **MISS 之后，PG18 到底怎样找到一个 Buffer，并且处理并发情况下“别人也在加载同一个 Page”的问题。**

---

# 1. `BufferAlloc()` 到底负责什么？

先不要把它理解成：

> “给我分配一块内存。”

因为 Shared Buffer 的内存早就预分配好了。

`BufferAlloc()` 真正干的是：

> **给一个新的 BufferTag 找一个可以承载它的 Buffer。**

所以：

```text
Page X 不在 cache
        │
        ▼
BufferAlloc(Page X)
        │
        ├── Page X 其实被别人放进去了？
        │       ↓
        │      HIT
        │
        └── 确实不存在
                ↓
             找 victim
```

这个设计非常重要。

---

# 2. 为什么 `BufferAlloc()` 还要重新检查一次 Lookup？

你可能马上会产生一个疑问：

前面不是已经：

```text
BufTableLookup()
```

检查过了吗？

为什么到了 `BufferAlloc()` 还要查？

答案就是：

# **并发。**

考虑两个 backend：

```text
Backend A                 Backend B

请求 Page X                请求 Page X
    │                         │
    ▼                         ▼
Lookup(X)                   Lookup(X)
    │                         │
   MISS                      MISS
    │                         │
    ▼                         ▼
继续往下                    继续往下
```

这完全可能发生。

因为：

```text
A Lookup(X)
```

和：

```text
B Lookup(X)
```

之间不是原子操作。

于是：

```text
A: X 不存在
B: X 不存在
```

同时成立。

---

# 3. 如果没有并发保护，会发生什么？

假设：

```text
A → 找到 Buffer 100
B → 找到 Buffer 200
```

然后：

```text
A:
Buffer100 ← Page X
```

同时：

```text
B:
Buffer200 ← Page X
```

最终：

```text
Buffer Mapping

X → Buffer100

但 Buffer200 里面也有 X
```

这就产生了：

> **同一个 BufferTag 在 Buffer Pool 中出现两份。**

这对数据库来说是非常危险的。

因为：

```text
Backend A
修改 Buffer100 中的 Page X

Backend B
修改 Buffer200 中的 Page X
```

现在：

> 到底哪个才是 Page X？

直接进入灾难。

所以 PostgreSQL 必须保证：

# **同一个 BufferTag 在 Shared Buffer 中只能对应一个有效 Buffer。**

---

# 4. Buffer Mapping Lock 就是解决这个问题的重要机制

我们前面讲过：

```text
BufferTag
    ↓
Hash Table
    ↓
Buffer ID
```

这个 Hash Table 不是裸奔的。

它有：

```text
Buffer Mapping Locks
```

用于保护：

```text
BufferTag → Buffer ID
```

映射表的并发修改。

可以粗略理解成：

```text
              Buffer Mapping Table
                       │
               Mapping Partition
                       │
          ┌────────────┼────────────┐
          │            │            │
       Backend A    Backend B    Backend C
```

不是整个 Buffer Pool 一把大锁。

而是使用分区/partition 的方式降低竞争。

---

# 5. 为什么需要“重新 Lookup”？

现在回到：

```text
A                      B

Lookup X → MISS        Lookup X → MISS
```

假设 A 比 B 快。

A：

```text
找到 victim
    ↓
开始把 X 装进去
```

B：

```text
还没真正完成
```

如果 B 后面完全不再检查：

```text
B
  ↓
找 victim
  ↓
加载 X
```

就可能重复。

所以 PG 的逻辑本质上是：

```text
第一次 Lookup
     ↓
发现 MISS
     ↓
做一些准备
     ↓
再次在正确的并发保护下确认
     ↓
确认仍然 MISS
     ↓
真正安装 BufferTag
```

这类：

> **先乐观检查，真正修改前重新确认**

在数据库内核里非常常见。

---

# 6. 这里你需要区分两个完全不同的东西

这是读 `bufmgr.c` 时最容易混淆的地方：

```text
Buffer Mapping Lock
```

和：

```text
Buffer Header / state
```

不是一回事。

---

## Buffer Mapping Lock

保护：

```text
BufferTag → Buffer ID
```

也就是：

> **这个 Page 到底在哪个 Buffer？**

---

## Buffer Header state

保护：

```text
这个 Buffer 当前是什么状态？
```

比如：

```text
refcount
usage_count
dirty
valid
IO in progress
...
```

所以可以把它们记成：

```text
Mapping Lock
    ↓
“Page 在哪个槽位？”

Buffer State
    ↓
“这个槽位现在什么状态？”
```

---

# 7. 找到 victim 之前，还会遇到一个重要问题

假设：

```text
Page X MISS
```

我们找到：

```text
Buffer 500
```

准备作为 victim。

但这个 Buffer 里面可能是：

```text
Page Y
```

而且：

```text
Page Y
```

可能正在被另一个 backend 使用。

所以不能简单：

```text
Buffer 500 → overwrite
```

必须先判断：

```text
Buffer 500
    │
    ├── pinned?
    ├── IO in progress?
    ├── dirty?
    └── content lock?
```

这就是为什么：

```text
GetVictimBuffer()
```

并不是：

```text
return first_unused_buffer;
```

它其实是一个并发协调过程。

---

# 8. 进入 `StrategyGetBuffer()`

真正找 victim 的核心函数在：

```text
src/backend/storage/buffer/freelist.c
```

核心：

```c
StrategyGetBuffer()
```

大致逻辑：

```text
StrategyGetBuffer()
        │
        ▼
有没有 BufferAccessStrategy？
        │
   ┌────┴────┐
   │         │
  YES       NO
   │         │
   ▼         ▼
 Ring      Clock Sweep
   │         │
   └────┬────┘
        ▼
   Candidate Buffer
        │
        ▼
   检查 refcount
        │
   ┌────┴────┐
   │         │
  >0        =0
   │         │
 skip      candidate
```

PG18 的源码中 `StrategyGetBuffer()` 确实会先考虑 strategy ring，然后进入普通的 clock-sweep 路径；被选中的 buffer 必须当前没有 pin。

---

# 9. Clock Sweep 现在重新看一次

假设：

```text
Buffer 0   usage=2
Buffer 1   usage=0
Buffer 2   usage=1
Buffer 3   usage=5
Buffer 4   usage=0
```

Clock hand：

```text
                hand
                 ↓
Buffer0 → Buffer1 → Buffer2 → Buffer3 → Buffer4
```

假设：

```text
Buffer0:
refcount = 1
```

跳过。

继续：

```text
Buffer1:
refcount = 0
usage = 0
```

可以成为 victim。

如果：

```text
usage > 0
```

则通常不是马上淘汰，而是：

```text
usage--
```

然后继续扫描。

所以 Clock Sweep 的核心思想就是：

```text
pin > 0
    → 绝对不能淘汰

pin = 0
usage > 0
    → 给它一次“机会”

pin = 0
usage = 0
    → 可以淘汰
```

---

# 10. 为什么 `usage_count` 最大不是无限的？

PG 的 Buffer Descriptor 中 usage count 有明确的有限范围。

你可以先把它理解成：

```text
0 ~ BM_MAX_USAGE_COUNT
```

而不是：

```text
0 ~ infinity
```

这很重要。

否则一个热点页面：

```text
SELECT ... 热点 Page
```

不断被访问：

```text
usage++
usage++
usage++
...
```

它可能永远无法被淘汰。

所以 PG 给 usage count 设置上限。

这也是 Clock Sweep 能够稳定工作的基础。

---

# 11. 但注意：Pin 和 Usage Count 的意义完全不同

再强调一次，因为这个地方非常重要：

```text
Pin
```

是硬约束：

```text
pin > 0
→ 不能淘汰
```

而：

```text
Usage Count
```

是软倾向：

```text
usage > 0
→ 尽量给机会
```

所以：

```text
Pin = “现在有人占着”

Usage Count = “最近比较热门”
```

这两个概念以后你看到源码变量一定要分开。

---

# 12. Ring Strategy 又是怎么插进来的？

假设：

```text
VACUUM
```

或者：

```text
large sequential scan
```

调用方创建：

```text
BufferAccessStrategy
```

然后：

```text
ReadBuffer(..., strategy)
```

一路传下来：

```text
ReadBuffer
   ↓
ReadBufferExtended
   ↓
ReadBuffer_common
   ↓
BufferAlloc
   ↓
GetVictimBuffer
   ↓
StrategyGetBuffer
   ↓
GetBufferFromRing
```

于是 PG 会优先考虑：

```text
Ring Buffer
```

而不是马上把整个 shared buffer pool 拿来做 Clock Sweep。

---

# 13. 为什么 Ring 可以防止 Buffer Pool 污染？

假设：

```text
shared_buffers = 8GB
```

但是：

```text
顺序扫描 = 500GB
```

如果没有 ring：

```text
Page1
Page2
Page3
...
Page 500GB
```

不断进入：

```text
Shared Buffer
```

会把：

```text
真正热点页面
```

大量挤出去。

有 ring：

```text
small ring
   ↓
Page A
Page B
Page C
...
   ↓
循环复用
```

所以：

```text
500GB sequential scan
```

不会天然变成：

```text
“把 8GB cache 全换一遍”
```

---

# 14. 现在回到 victim

假设：

```text
StrategyGetBuffer()
```

最终选中了：

```text
Buffer 500
```

这时候才进入：

```text
GetVictimBuffer()
```

接下来要解决：

> **这个 Buffer 现在里面的 Page 能不能被赶走？**

---

# 15. 第一关：Pin

假设：

```text
Buffer 500
Page Y
refcount = 3
```

说明：

```text
Backend A ──┐
Backend B ──┼── Pin Buffer500
Backend C ──┘
```

那么：

```text
Buffer500
```

绝对不能作为 victim。

所以：

```text
StrategyGetBuffer()
       ↓
candidate
       ↓
refcount > 0
       ↓
reject
       ↓
继续找
```

这就是为什么 replacement 不只是：

```text
找 usage_count 最小的
```

而必须首先考虑：

```text
Pin
```

---

# 16. 第二关：Buffer Content Lock

即使：

```text
refcount = 0
```

也不意味着所有问题都结束了。

Buffer 的 page 内容还需要考虑：

```text
content lock
```

因为 Buffer Manager 需要确保：

> **我要把这个 Page 写出去/复用之前，不会有人同时修改它。**

所以在 victim 处理阶段会涉及 Buffer Content Lock 等同步机制。

你现在不用死记每个 lock acquisition 的位置。

先建立层次：

```text
Buffer Mapping Lock
    ↓
保护“Page → Buffer”的映射

Buffer Header State
    ↓
保护 Buffer 管理状态

Buffer Content Lock
    ↓
保护 Buffer 里的 Page 内容
```

这是三个不同层面的同步。

---

# 17. 第三关：Dirty

假设：

```text
Buffer500
```

里面：

```text
Page Y
```

是：

```text
dirty = false
```

那很好：

```text
Page Y
   ↓
直接丢
```

但是如果：

```text
dirty = true
```

那么：

```text
Page Y
   ↓
必须 flush
```

于是进入我们之前讲的：

```text
PageLSN
   ↓
XLogFlush()
   ↓
data page write
```

---

# 18. 这里有一个非常重要的并发 race

假设你检查：

```text
dirty = false
```

然后准备复用。

但就在你检查之后：

```text
Backend B
```

可能又把这个 Page 改脏了。

所以：

```text
“我刚才看到它是 clean”
```

不能简单理解成：

> 永远 clean。

这就是为什么 PG18 的 `GetVictimBuffer()` 周围源码会有比较复杂的重新检查和同步逻辑。

数据库内核经常不是：

```text
check
↓
do
```

这么简单。

而是：

```text
check
↓
acquire synchronization
↓
recheck
↓
do
```

因为中间可能有人改变状态。


# 21. 这就是为什么 Shared Buffer 的核心不是“数组”

你现在应该开始看到：

Shared Buffer 实际上是：

```text
                    Shared Buffer
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
       ▼                 ▼                 ▼
 Page Identity       Buffer State      Replacement
       │                 │                 │
 BufferTag            refcount         Clock Sweep
       │               dirty           Ring
       ▼               valid           usage_count
 Hash Table            IO state
       │
       ▼
 Buffer ID
       │
       ▼
 BufferDesc
       │
       ▼
 8KB Page
```

再加：

```text
              ┌───────────────┐
              │      WAL      │
              └───────┬───────┘
                      │
                      ▼
                  dirty flush
```

以及：

```text
              ┌───────────────┐
              │      AIO      │
              └───────┬───────┘
                      │
                      ▼
                  Page IO
```

所以它其实是一个完整的：

> **并发 Page Cache + Replacement + IO Coordination 系统。**

# 23. 到这里先停一下，你应该掌握这条主线

```text

    ↓

    ↓

    ↓

    │     ↓

    │     ↓
```
